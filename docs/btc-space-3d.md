# BTC 스페이스 3D 규격서

> 버전: v0.25
> 기준일: 2026-10-31
> 제공 방식: `/space` 라우트의 전체 화면 3D 공간
> 상태: 2단계 위치 동기화·공간 채팅 구현, 로컬 검증 완료·Cloudflare 배포 및 실기기 실측 대기
> 수용 규모: 방 하나당 동시 접속 50명

Three.js 기반 3D 공간에 비트코인 실시간 가격 전광판을 세우고, 사용자가 3인칭 캐릭터로 돌아다니며 다른 접속자와 대화하는 기능이다. 전광판 좌우에는 라이트닝 결제로 판매하는 광고판을 둔다.

구현은 3단계로 나눈다. 1단계에서 싱글 씬·전광판·50명 렌더 구조를 만들었고, 2단계에서는 `SpaceRoom` 한 연결에 위치 동기화와 공간 채팅을 함께 구현했다(§11). 실시간 가격 소켓과 차트는 기존 데이터 계층을 계속 이용한다. 3단계 라이트닝 광고는 §12의 사전 설계 상태다. 2단계 코드는 서버 배포 전까지 운영 접속에 사용할 수 없으며, 실제 다중 브라우저·모바일 검증은 별도로 남는다.

이 문서에서 좌표 1 유닛은 1 m, 각도는 도(°), 시간은 초(s)를 뜻한다.

## 1. 확정값

| 항목 | 값 | 비고 |
| --- | --- | --- |
| 렌더 스택 | `@react-three/fiber` 9 + `@react-three/drei` 10 + `three` 0.187 | fiber 9 의 react peer 는 `>=19 <19.4`, 현재 19.2.6 으로 충족 |
| 카메라 | 3인칭 추적 | 기본 거리 11 m, 손가락 기기 시작 18 m, 휠·핀치로 5~18 m 조절 |
| 조작 | 데스크톱 WASD·방향키, 모바일 가상 조이스틱 | Shift 달리기, Space 점프(데스크톱 전용) |
| 접근 조건 | 모든 브라우저 | 채팅과 달리 PWA standalone 게이트를 두지 않음 |
| 라우트 | `/space` | 헤더·하단 내비 숨김, 전체 화면 |
| 번들 | 라우트 단위 `dynamic` + `ssr: false` | 다른 페이지 번들에 three 를 넣지 않음 |
| **동시 접속 상한** | **50명** | 초과 입장에 `full` 응답 후 연결 종료, 대기열·자동 방 분할 없음 |
| 월드 | 바닥 64 × 48, 가용 52 × 32 | 50명 기준 33.3 m²/인 |
| 스폰 | 중심 `(0, 0, 0)` 반지름 5~14 산포 | `clientKey` 해시로 결정적 분산 |
| 아바타 간 충돌 | 없음 (겹침 허용) | 경계 클램프만 적용 |
| 전광판 | 9.6 × 5.4, 중앙 뒷벽 | `CanvasTexture` 1600 × 900, 가격 2행·24시간 차트 |
| 광고판 | 6 × 4 (3:2) × 2면 | 전광판 좌우, 안쪽 15° 회전 |
| 가격 소스 | `useBitcoinStore` | 전역 `Initializer` 의 거래소 소켓을 그대로 구독 |
| 아바타 렌더 | `InstancedMesh` 50 슬롯 | 50명 전체가 드로우 콜 3개 |
| 명찰 표시 상한 | 25 m 이내 & 가장 가까운 16명 | DOM 노드 폭발 방지 |
| 말풍선 표시 상한 | 동시 12개, TTL 5 s | 25 m 이내 가까운 순, 좌석당 최신 발화만 표시 |
| 성능 목표 | 데스크톱 60 fps, 중급 모바일 30 fps 이상 | 아바타 50명 상태 기준 |
| 위치 배치 | 이동 수신 시 최대 10 Hz, 전원 공유 버퍼 | 유휴 상태의 상시 틱 없음(§11) |
| 멀티플레이 | `SpaceRoom` Durable Object | 위치·입퇴장·공간 채팅, 배포 대기 |

전광판 가격 표시는 `drei` 의 `<Text>`(troika SDF) 가 아니라 `CanvasTexture` 로 그린다. 숫자용 폰트 아틀라스를 추가로 받지 않아도 되고, LED 도트 매트릭스 질감을 셰이더 없이 낼 수 있다. 한글이 들어가는 닉네임 명찰은 `drei` 의 `<Html>` 로 DOM 을 띄운다. 한글 글리프를 SDF 아틀라스로 만들면 용량이 수 MB 가 되므로 3D 텍스트로 만들지 않는다. 대신 DOM 명찰은 개수가 곧 레이아웃 비용이므로 위 표의 표시 상한을 둔다.

명찰 16개·말풍선 12개 상한은 **동시 접속 수에 비례하는 값이 아니라 DOM 렌더 비용의 상한**이다. 접속 50명 기준으로는 방 인원의 약 3분의 1이 이름표를 달고 보이는 셈이며, 그보다 멀거나 많은 쪽은 색만으로 구분한다.

아바타 간 충돌 처리는 넣지 않는다. 50명이 전광판 앞으로 몰리는 상황에서 밀어내기(separation)를 넣으면 클라이언트마다 밀어낸 결과가 달라져 위치 동기화가 어긋나고, 서버에서 권위적으로 풀면 틱당 비용이 `O(n²)` 로 올라간다. 아바타는 서로 통과하며 겹친다.

## 2. 아키텍처

```text
Next.js (/space)
  └─ SpaceView ──dynamic, ssr: false──> SpaceCanvas
       ├─ SpaceScene ─ Ground · SceneLighting · PlayerAvatar
       │                  ├─ RemoteAvatars (InstancedMesh, 최대 50)
       │                  ├─ Nameplates · ChatBubbles (DOM, 거리·개수 컬링)
       │                  ├─ PriceBillboard ──> useBitcoinStore (전역 거래소 소켓)
       │                  ├─ TextAdBanner ──> 1단계: 빈 텍스트 슬롯
       │                  └─ AdBoard × 2 ────> 1단계: 정적 플레이스홀더
       └─ SpaceHud (DOM 오버레이) ─ VirtualJoystick · 조작 안내 · 접속자 수 · SpaceChatPanel

[공간 세션]
  SpaceCanvas ──WebSocket──> Cloudflare Worker(/v1/space/ws)
                                 └─> SpaceRoom Durable Object (SQLite 등록, 좌석·위치는 socket attachment)
```

| 구성 | 역할 |
| --- | --- |
| Vercel | `/space` 페이지, 3D 자산 정적 서빙 |
| `useBitcoinStore` | 전광판 가격 원천. 신규 API·소켓을 추가하지 않음 |
| Cloudflare Worker | `/v1/space/ws`. 기존 Origin 검사·IP 가드·경로별 접속 제한 재사용 |
| `SpaceRoom` DO | 좌석 50개·위치·휘발성 채팅 중계. SQLite-backed 등록, 위치/본문 SQL 쓰기 없음 |
| `ChatRoom` DO | 기존 채팅방. 공간 채팅과 **분리** 유지 |

가격은 전역 `Initializer` 가 루트 레이아웃에서 이미 Upbit·Bithumb·Binance·Coinbase 소켓을 띄워 `bitcoinStore` 에 넣고 있다. 전광판은 그 스토어를 구독만 하므로 `/space` 전용 데이터 레이어를 만들지 않는다.

위치 동기화는 기존 `ChatRoom` DO 에 넣지 않는다. `ChatRoom` 은 메시지마다 SQLite 쓰기와 발화 레이트리밋을 수행하는 영속 중심 설계이며, 현재 연결 상한은 500개(`MAXIMUM_ROOM_CONNECTION_COUNT`)다. 위치 프레임은 50명 × 10 Hz 의 휘발성 데이터이므로 같은 DO 에 섞지 않는다. 같은 Worker 안에서 `SPACE_ROOM` 바인딩과 `/v1/space/ws`를 추가하고 Origin 검사·CORS·IP 가드를 재사용했다. 기존 `/v1/chat/*`의 저장·인증 경로는 유지한다.

## 4. 월드 레이아웃

좌표계는 three.js 기본을 따른다. `+Y` 가 위, 플레이어는 `-Z` 방향(전광판)을 바라보고 시작한다.

월드 크기는 접속 50명에서 밀도가 적당해지도록 역산했다. 넓게 잡으면 사람이 흩어져 서로 마주치지 않고, 대화가 일어나지 않는다.

```text
                     z = -18 (뒷벽면)
   ┌──────────────────────────────────────────────┐
   │  [광고판 L]      [ 전광판 ]      [광고판 R]    │
   │   6×4, +15°       9.6×5.4        6×4, -15°  │
   │   x=-8.91          x=0            x=+8.91    │
   │                                              │
   │            ◌  ◌ 스폰 링 r=5~14 ◌  ◌           │
   │          ◌        ● 중심 (0,0,0)       ◌      │
   │            ◌  ◌                 ◌  ◌         │
   └──────────────────────────────────────────────┘
      바닥 64 × 48 │ 이동 경계 -26 ≤ x ≤ 26, -16 ≤ z ≤ 16
```

| 오브젝트 | 크기 (W×H) | 위치 (x, y, z) | 회전 |
| --- | --- | --- | --- |
| 바닥 | 64 × 48 | (0, 0, -2) | `-90°` X축 |
| 전광판 패널 | 9.6 × 5.4 | (0, 6, -18) | 없음 |
| 전광판 프레임 | 10.2 × 6 | (0, 6, -18.1) | 없음 |
| 텍스트 광고 배너 | 9.6 × 0.8 | (0, 9.6, -18) | 없음 |
| 전광판 광원 | - | (0, 4, -15.5) | 패널과 분리, **축소 그룹 바깥** |
| 광고판 L | 6 × 4 | (-8.91, 6, -17.4) | `+15°` Y축 |
| 광고판 R | 6 × 4 | (8.91, 6, -17.4) | `-15°` Y축 |
| 스폰 링 | 중심 (0, 0, 0) | 반지름 5~14 | 각 스폰 위치에서 전광판 중심을 바라보는 yaw |

| 밀도 항목 | 값 |
| --- | --- |
| 가용 면적 | 52 × 32 = 1,664 m² |
| 50명 기준 밀도 | 33.3 m²/인 (한 변 5.8 m) |
| 스폰 링 면적 | 약 537 m² → 입장 직후 10.7 m²/인 |
| 전광판 최장 시청 거리 | 스폰 링 끝 32 m, 경계 코너 42.8 m |
| 전광판 프레임 상단 | 9.0 m |
| 텍스트 배너 상단 | 10.0 m (손가락 기기 시작 거리에서 스폰 링 전 구간 가시) |
| 전광판–광고판 간격 | 0.91 m (광고판 안쪽 끝 6.01, 전광판 프레임 끝 5.10) |

스폰은 단일 지점이 아니라 링 안에 분산한다. 50명이 같은 좌표에서 시작하면 아바타가 완전히 겹쳐 입장 직후 화면이 무너진다. `clientKey` 해시로 각도와 반지름을 결정하므로 재접속 시 같은 자리로 돌아온다.

광고판은 전광판과 **세로 중심을 맞춘다**(`y = 6`). 두 판의 높이가 달라서(5.4 vs 4) 아랫변을 맞추면 윗변이, 윗변을 맞추면 아랫변이 어긋난다. 중심을 맞춰야 세 판이 한 줄로 읽힌다. 광고판 4 m 는 전광판 5.4 m 안쪽에 들어오므로 위아래로 0.7 m 씩 물린다.

시선 위계는 높이가 아니라 **크기 차이**로 준다(전광판 9.6 × 5.4 vs 광고판 6 × 4). 15° 안쪽 회전은 스폰 링 어디에서든 세 패널이 한 화면에 잡히게 하는 값이다.

패널 배치의 불변식(세로 중심 일치, 광고판이 전광판 세로 범위 안, 3:2 비율, 프레임 비겹침, 바닥 위)은 `spaceWorld.test.ts` 에서 고정한다.

### 4.1 관제 스테이션 분위기

바닥·전광판 벽·조명은 노드 관제 스테이션 톤으로 구성한다. 월드 크기와 이동 경계, 전광판·광고판 위치, 텍스트 배너의 패널과 동일한 폭은 유지한다.

- **바닥**: 청회색 금속 판재를 8 × 6 m 단위로 구분한다. 전광판으로 향하는 가는 안내선과 앞쪽 집결 영역의 작은 코너 표시를 2048 × 1536 캔버스 텍스처에 함께 구워 바닥 메시 1개로 그린다. 새 바닥은 높이 0이며 실시간 반사나 후처리를 사용하지 않는다.
- **전광판 벽**: 64 × 16 m 뒷벽에 큰 금속 패널·수직 구조 리브·청록 라이트바를 배치한다. 메인 전광판과 좌우 광고판 뒤에는 장비 하우징·림·하단 상태 바를 둔다. 하우징은 전광판과 같은 기준점·배율, 광고판과 같은 회전을 사용해 좁은 화면에서도 표시 면 뒤에 남는다.
- **조명**: 청회색 반구광(위 `#b7cfdf`, 아래 `#172333`)과 중성 키라이트, 약한 청록 보조광으로 입체감을 만든다. 전광판 주변은 기존 오렌지 점광원으로 강조한다. 실시간 그림자는 데스크톱 키라이트 하나에만 적용하고 점광원 그림자는 사용하지 않는다.

`ControlWall` 은 고정 벽 1개와 정적 `InstancedMesh` 6개, 총 7개 렌더 배치로 구성하며 부품 행렬은 초기 배치 때만 갱신한다. 바닥은 1개 렌더 배치다. 이 수치는 코드 구조 기준이며 전체 씬의 FPS·드로우 콜 실측은 §8.2의 미측정 상태를 유지한다.

### 5.1 점프와 높이 축

바닥이 평평하므로 `PlayerTransform.y` 는 **점프로만** 0 이 아니다. 지면 판정은 `y <= 0` 하나로 끝난다.

- **누르고 있으면 착지할 때마다 다시 뛴다.** 누름 순간만 잡으려면 입력 계층에 상태를 더 둬야 하는데, 복셀 게임에서는 연속 점프가 흔한 조작이다.
- **공중에서는 궤적을 바꿀 수 없다.** 중력만 받는 포물선이다. 수평 이동은 그대로 적분하므로 뛰면서 앞으로 나아간다.
- **공중에서는 걷기 모션을 멈춘다.** 뛰는 중에 다리가 돌면 허우적대 보인다.
- **접지 그림자는 바닥에 남긴다.** 같이 떠오르면 높이가 읽히지 않는다.
- **카메라 주시점이 높이를 그대로 따라간다.** 고정해 두면 뛰었을 때 캐릭터가 화면 위로 빠져나간다. 카메라 위치는 `dampVector` 가 이미 감쇠하므로 따로 완충하지 않는다.
- 명찰과 말풍선도 높이를 더해 함께 올라간다.

**모바일에는 점프 수단이 없다.** 조이스틱은 2축이고 별도 버튼을 두지 않았다.

#### 프로토콜

`y` 를 스냅샷에 1바이트로 더해 좌석당 **7 → 8 바이트**가 됐다. 50명 10 Hz 기준 초당 500 B 가 늘어난다.

| 항목 | 값 |
| --- | --- |
| 정밀도 | 1 cm (`uint8`, 0~2.55 m) |
| 상한 | `SPACE_MAX_JUMP_HEIGHT` = 2.5 m. 실제 정점 1.13 m 보다 여유를 둔다 |
| 검증 | 디코더가 상한 초과 바이트를 거절하고, 서버도 `move` 프레임의 `y` 범위를 본다 |
| 보간 | x·z 와 같은 선형 보간. 100 ms 간격이라 포물선 정점이 조금 깎인다 |

높이를 보내지 않고 "점프 시작" 플래그만 보내는 방식도 가능하다(패킷 크기 불변). 하지만 100 ms 샘플링 때문에 시작 시점이 최대 한 틱 밀리고, 서버가 높이를 검증할 수 없다. 1바이트를 쓰는 쪽이 단순하다.

카메라 위치는 바닥 경계 안과 뒷벽 앞쪽으로 클램프한다. `prefers-reduced-motion: reduce` 인 경우 카메라 추종 감쇠를 `1 - exp(-20 · dt)` 로 올려 흔들림을 줄인다. 현재 아바타에는 아이들 부유 애니메이션이 없다.

### 6.1 그리기 방식

한글 라벨(원화·달러·최근 24시간)과 차트를 함께 써야 해서 `drei` 의 SDF 텍스트가 아니라 캔버스로 그린다. 한글 글리프를 SDF 아틀라스로 만들면 수 MB 가 되고, 차트는 별도 라이브러리가 필요해진다. 캔버스는 둘 다 공짜로 해결한다.

폰트에 기대면 깨지는 두 가지는 도형으로 그린다.

- 비트코인 마크: `₿`(U+20BF) 글리프가 없는 환경의 두부 방지. 주황 원 + 기울인 `B` + 위아래 세로 획
- 상승·하락 삼각형: `▲`·`▼` 글리프 의존 제거

숫자는 등폭 스택, 한글 라벨은 시스템 산세리프 스택을 쓴다. 숫자가 가변폭이면 4 Hz 갱신 때 자리수마다 글자가 떤다.

### 6.2.1 우측 상단 접속 배지

전광판이 살아 있는 값을 보여주는 중인지 한눈에 알리는 표시다. 가격 행의 상태 점은 통화별 소켓을 각각 알려주지만, 멀리서는 반경 7 px 점의 색만으로 판단하기 어렵다.

| 항목 | 값 |
| --- | --- |
| pill | `(1338, 52)` 에서 176 × 60 px, 모서리 반경 30 px, 면 색은 `BTC` pill 과 같은 `tickerSurface` |
| 점 | `(1366, 82)` 반경 9 px. 온라인 `#2ee6a8` / 오프라인 `#ef4444` |
| 문구 | 28 px `온라인` / `오프라인`. 점 오른쪽 남은 폭(1375~1514)의 가운데 x=1445 에 정렬 |
| 확산 펄스 | 최대 반경 34 px, 2.2초 주기, 링 2개를 반 주기 간격. 링 안쪽 반경 비율 0.6, 최대 불투명도 0.7 |

pill 폭은 더 긴 `오프라인` 기준으로 **고정한다.** 글자 길이에 따라 폭이 변하면 점 위치가 흔들려 3D 로 겹치는 펄스가 어긋난다. 문구를 왼쪽 정렬이 아니라 점 오른쪽 공간의 가운데에 두어, 두 문구 모두 좌우 여백이 맞는다(`온라인` 28/27 px, `오프라인` 14/13 px).

**온라인 판정은 두 소켓 중 하나라도 붙어 있으면 참이다**(`resolveBillboardOnlineStatus`). 양쪽을 모두 요구하면 한쪽만 끊겼을 때 숫자가 눈앞에서 바뀌는데도 `오프라인` 이라고 적혀 더 혼란스럽다. 어느 피드가 끊겼는지는 가격 행의 점이 따로 알려준다.

펄스는 차트 끝점과 같은 이유로 텍스처가 아니라 3D 링(`BillboardOnlinePulse`)으로 그린다. 베이스 텍스처는 상태가 바뀔 때만 다시 올리므로 프레임마다 커지는 원을 구울 수 없다. 점과 링이 같은 자리에 붙도록 좌표는 `BILLBOARD_ONLINE_MARKER` 한 곳에서만 정한다. 최대 반경이 아래로 y=116 까지 번지므로 원화 행 상단 y=154 와 38 px 떨어져 있다. 끊긴 동안과 모션 축소 설정에서는 링을 숨기고 정적인 점만 남긴다. 빨간 점이 살아 있는 것처럼 뛰면 안 된다.

### 6.3 차트

| 항목 | 값 |
| --- | --- |
| 표본 | 288개를 180개로 솎음. 플롯 폭 1,320 px, 왼쪽 x=60·끝점 x=1,380 |
| 세로 배치 | 제목 y=470·보조 제목 y=473, 플롯 상단 y=520·높이 250 px·하단 y=770 |
| 마지막 점 | 반드시 보존. 현재가가 잘리면 안 된다 |
| 축 눈금 | 1·2·5 계열 간격으로 데이터를 양쪽에서 한 칸씩 감쌈 |
| 선 색 | 24시간 방향을 따름(상승 초록 / 하락 빨강) |
| 끝점 가격 툴팁 | 표시하지 않음. 오른쪽 가격 축 눈금은 유지 |
| 끝점 표시 | 선과 같은 색의 반경 12 px 점과 최대 반경 64 px 의 1.8초 주기 확산 펄스. 보합은 선과 같은 초록 사용 |
| 시간 라벨 | y=859. 최대 펄스가 차트 하단을 넘어도 라벨과 겹치지 않게 배치 |

눈금 **개수는 고정하지 않는다.** 개수를 맞추려 간격을 키우면 범위가 실제 변동폭의 몇 배로 벌어져 선이 차트 아래쪽에 눌린다. 실측으로 96,500~100,100 데이터가 95,000~105,000 범위에 그려져 플롯 높이의 36% 만 쓰는 문제가 나왔다. 개수를 양보하고 범위를 좁히는 쪽을 택한다.

차트 끝점의 가격 배지·툴팁은 제거하고 선과 같은 색의 점·펄스만 남긴다. 끝점 x=1,380에서 오른쪽 가격 축 라벨 x=1,452까지 72 px 여백을 둬 최대 반경 64 px 펄스가 축 라벨을 침범하지 않게 한다.

펄스 위치는 베이스 차트와 같은 표본·스케일·좌표 계산을 공유한다. 마지막 가격의 현재 값으로 별도 좌표를 만들지 않는다. `BILLBOARD_CHART_MARKER` 의 점 반경 12 px·펄스 최대 반경 64 px 를 정적 점과 링이 공유한다. 두 개의 링을 반 주기 간격으로 확장·감쇠하며, 원거리 가시성을 위해 최대 반경을 16 → 64 px 로 4배 키웠다. 링 안쪽 반경 비율은 0.68, 최대 불투명도는 0.85, 감쇠는 `0.85 × (1 - phase)^1.4` 이다. 링은 3D 메시의 크기·투명도만 갱신하며 큰 전광판 텍스처를 다시 업로드하지 않는다. 모션 축소 설정에서는 링을 숨기고 정적인 끝점만 유지하며, 차트 데이터가 부족하면 표시하지 않는다.

### 6.4 좁은 화면 대응

three 의 원근 카메라는 **수직** FOV 를 고정하고 가로를 종횡비에서 유도한다. 세로로 긴 화면일수록 가로 시야가 좁아진다. 세로 FOV 55° 기준으로 데스크톱(종횡비 1.78)은 가로 85.6° 인데 아이폰 세로(0.46)는 27.0° 뿐이다.

가시 폭의 기준 거리는 **카메라에서 벽까지**다. 스폰 중심을 기준으로 `18 + 시작 거리·cos(12°)` 를 쓴다. 마우스 기기의 시작 거리 11 m 에서는 28.76 m, 손가락 기기의 18 m 에서는 35.61 m 다. 실제 플레이어 위치·카메라 회전·경계 클램프에 따른 가시 범위 전체를 보장하는 계산은 아니다.

| 기기 | 시작 거리 | 종횡비 | 기준 가시 폭 | 무축소 중앙 프레임 점유 | 배율 |
| --- | --- | --- | --- | --- | --- |
| 데스크톱 1920×1080 | 11 m | 1.78 | 53.2 m | 19% | 1.00 |
| 아이폰 세로 393×852 | 18 m | 0.46 | 17.1 m | 60% | 1.00 |
| 갤럭시 세로 360×780 | 18 m | 0.46 | 17.1 m | 60% | 1.00 |
| 좁은 마우스 창 320×900 | 11 m | 0.36 | 10.6 m | 96% | 0.99 |

일반적인 폰 세로에서는 손가락 기기 시작 거리 18 m 에서 중앙 배너까지 들어온다. 축소는 그보다 좁은 화면을 위한 안전장치다.

**축소 방식**: 중앙 스택의 가장 넓은 요소인 전광판 프레임(10.2 m, 텍스트 배너는 패널과 같은 9.6 m)이 기준 가시 폭의 95% 를 넘지 않는 배율을 종횡비와 **실제 시작 카메라 거리**에서 계산하고 `[0.5, 1]` 로 자른다. 배율은 리사이즈·회전 때 다시 계산하며, 휠·핀치로 거리를 바꿀 때마다 갱신하지는 않는다. 이 비율은 크기를 정하는 값이 아니라 넘침을 막는 가드다. 축소 대상은 전광판·프레임·텍스트 배너·광고판이고, 바닥 광원은 그룹 **바깥**에 둔다.

기준점을 그대로 두고 줄이면 패널이 중심을 향해 수축하면서 **아랫변이 떠오른다**. 배율 0.68 에서 프레임 아랫변이 3.00 m → 3.96 m 로 1 m 올라가 벽에 붙은 간판이 공중에 뜬 것처럼 보였다. 아랫변이 제자리에 남도록 기준점을 함께 내린다.

전광판과 텍스트 배너로 이뤄진 중앙 스택만 가시 폭에 맞춘다. 좌우 광고판까지 포함한 벽면 전체를 맞추면 배율이 떨어져 전광판이 지나치게 작아진다. 광고판은 화면 밖으로 나가도 되고, 고개를 돌리면 보인다.

**검토했다가 버린 안**: 카메라 FOV 를 넓히는 방법. 화면에서 차지하는 비율이 같아지므로 글자 크기 이득이 없고, 씬 전체가 어안처럼 왜곡되며 다른 오브젝트까지 작아진다.

### 6.5 가독 거리

패널 폭 9.6 m 가 텍스처 1600 px 에 대응하므로 1 px 는 0.006 m 다. 아래는 `font px × 0.006 m` 로 환산한 **em 높이**다. 글리프의 실제 잉크 영역 높이나 화면에서 보이는 픽셀 수를 측정한 값은 아니다.

| 요소 | 글자 크기 | 축소 전 em 높이 |
| --- | --- | --- |
| 가격 | 최대 108 px | 최대 0.648 m |
| 등락률 | 최대 68 px | 최대 0.408 m |
| 한글 라벨 | 52 px | 0.312 m |
| 축 숫자 | 26 px | 0.156 m |

가격·등락률은 가용 폭에 따라 글자 크기가 줄어들며, 실제 가독성은 글꼴·카메라 거리·원근·벽면 축소 배율·렌더 dpr 의 영향을 받는다. 32 m 는 기존 스폰 링 먼 쪽의 기준 거리이며 이 표만으로 가독 한계를 보장하지 않는다. 패널을 더 줄이면 가격과 축 숫자를 실제 화면에서 함께 확인한다.

자동 축소 글자의 기본 하한은 36 px 다. 실제 브라우저의 원거리 가독성 검수는 §8.2의 렌더 실측과 함께 남겨 둔다.

## 6.6 텍스트 광고 배너

전광판 위에 얹는 **가로가 긴 텍스트 전용 광고 자리**다. 짧은 문구 한 줄을 넓게 펴서 멀리서도 읽히게 한다.

| 항목 | 값 |
| --- | --- |
| 패널 | 9.6 × 0.8 (12:1). 폭은 `SPACE_BILLBOARD.width` 와 같게 유지 |
| 텍스처 | `CanvasTexture` 1440 × 120 (12:1) |
| 위치 | 전광판 프레임 윗변에서 0.2 띄움 → 월드 9.2 ~ 10.0 m |
| 프레임 메시 | 없음. 테두리를 텍스처에 그림 |

프레임 메시를 두지 않는 이유는 높이가 0.8 m 뿐이라, 다른 패널과 같은 0.3 m 테두리를 붙이면 패널보다 테두리가 두꺼워 보이기 때문이다.

문구 길이는 제한하지 않고 **가용 폭에 맞춰 글자를 줄인다**. 길이로 자르면 광고주가 쓸 수 있는 문구가 글자 수에 묶인다. 하한 28 px 아래로는 줄이지 않는다.

```ts
interface AdTextSlot {
  text: string | null;   // null 이거나 공백뿐이면 플레이스홀더
  linkUrl: string | null;
  expiresAt: number | null;
}
```

배너는 슬롯 prop 이 바뀔 때만 다시 그린다. 1단계의 `SpaceScene` 은 항상 빈 슬롯을 넘기므로 플레이스홀더만 표시한다. `linkUrl` 이동과 `expiresAt` 만료 처리는 3단계 범위다.

배너 폭은 메인 전광판 **패널 폭(9.6 m)** 에 직접 연결한다. 높이는 0.8 m 를 유지한다. 좁은 화면 축소 가드(§6.4)는 `max(프레임 10.2, 배너 9.6) = 10.2 m` 를 기준으로 삼는다.

### 6.7 가격 숫자 전환

새 시세는 최대 4 Hz 로 채택하고, 이전에 표시하던 가격에서 새 가격까지 250ms 동안 cubic ease-out으로 이동한다. 상승·하락 모두 목표 범위를 벗어나지 않으며, 중간에 목표가 바뀌면 현재 표시값부터 이어 간다. 같은 목표를 반복 수신해도 전환을 다시 시작하지 않는다.

큰 베이스에는 헤더·두 inset 패널의 그라데이션 표면·통화 라벨·등락률·차트·연결 점을 그린다. KRW·USD 가격 두 칸은 800 × 128 투명 텍스처와 평면으로 분리해 최대 30 Hz 로 갱신하며, 포맷된 문자열이 같으면 업로드하지 않는다. 가격 레이어는 매번 투명하게 지운 뒤 숫자만 그리므로 베이스의 패널 배경·테두리·구분선을 가리지 않는다. 두 레이어는 같은 가격 영역 좌표·폰트·자동 축소 규격을 공유해 정적 숫자와 동적 숫자의 위치가 일치한다. 가격 패치는 패널 상하 2 px 안쪽에 들어오고, 옆 열과의 여백도 유지한다. 추가 렌더 배치는 2개이고 프레임마다 React 상태를 갱신하지 않는다.

최초 유효 시세와 결측값 전환은 즉시 표시한다. 앱 설정의 숫자 애니메이션이 꺼져 있거나 `prefers-reduced-motion` 이 켜져 있으면 보간하지 않는다. 탭 가시성이 바뀌거나 프레임 간격이 길어지면 최신 시세로 맞춘다. 실제 시세가 바뀌지 않으면 숫자를 임의로 흔들지 않는다. 24시간 차트의 15분 갱신 정책은 유지한다.

## 7. 광고판 규격 (1단계)

1단계에서는 결제도 업로드도 없다. `AdSlot` 타입과 플레이스홀더 렌더링을 두며, `AdBoard` 는 현재 배치 정보(`placement`)만 prop 으로 받는다.

```ts
interface AdSlot {
  id: "left" | "right";
  imageUrl: string | null;   // null 이면 플레이스홀더
  linkUrl: string | null;    // 3단계: 클릭 시 이동
  expiresAt: number | null;  // 3단계: 노출 만료
}
```

현재는 항상 "광고 문의" 플레이스홀더 텍스처를 그린다. 3단계에서 `slot` prop 과 이미지 로딩을 연결하고, 이미지가 있으면 3:2 비율로 `cover` 크롭한다. 링크 이동과 만료 처리도 그때 구현한다. 1단계에서는 외부 이미지를 불러오지 않으므로 CORS·CSP 변경이 필요 없다.

### 7.1 노출 스위치

`NEXT_PUBLIC_SPACE_ADS_ENABLED` 로 광고 노출을 끈다. 대상은 **광고판 2장과 전광판 위 텍스트 배너**이며, 끈 동안에는 두 컴포넌트를 렌더하지 않으므로 광고판 768 × 512 캔버스 텍스처 2장과 배너 텍스처도 만들지 않는다.

| 값 | 결과 |
| --- | --- |
| 비어 있음(기본) | 노출 |
| `false` · `0` · `off` · `no` (대소문자·공백 무관) | 숨김 |
| 그 밖의 값 | 노출 |

값이 없을 때 노출하는 쪽이 기본이다. 변수를 빼먹은 배포에서 광고가 조용히 사라지면 원인을 찾기 어렵다.

**벽면 장비함(하우징·림·하단 상태 바)은 이 스위치와 무관하게 남는다.** §4.1 에서 장비함은 전광판과 광고판이 함께 쓰는 벽 구조로 정의했고, 켜고 끌 때 벽 구성 자체가 바뀌면 안 된다. 끈 상태에서는 광고가 걸릴 자리가 빈 액자로 보인다.

파싱은 `shared/config/space.ts` 의 `resolveSpaceAdEnabled` 가 담당하고 `spaceConfig.isAdEnabled` 로 노출한다. `NEXT_PUBLIC_` 이라 빌드 시점에 값이 박히므로, 운영에서 바꾸려면 재배포가 필요하다.

## 8. 성능 예산 (아바타 50명 기준)

모든 수치는 **원격 아바타 50명이 보이는 상태**가 기준이다. 단일 플레이어 상태의 수치는 의미가 없다.

| 항목 | 예산 | 근거 |
| --- | --- | --- |
| 드로우 콜 | 50 이하 | 원격 아바타 50명 = 3 콜(몸통·앞치마 앞판·접지 그림자 각 `InstancedMesh`). **실질 병목은 여기다** |
| 삼각형 | 80k 이하 | 아바타 1인 1,242 tri(몸통 1,216 + 앞판 24 + 그림자 평면 2) × 50 = 62,100 (78%) |
| 인스턴스 행렬 갱신 | 프레임당 50명 × 3메시 = 150개 | `instanceMatrix.needsUpdate`, 색은 플레이어 배열 변경 시 **앞치마 앞판에만** `instanceColor` 로 설정 |
| DOM 명찰 | 최대 16개 | 25 m 이내 & 거리순 상위 16 |

#### 캐릭터 형상

아바타는 **빨간 크루 캡을 쓴 패스트푸드 알바생**이다. 복셀(마인크래프트) 스타일이며 512 × 512 픽셀 아틀라스 한 장으로 배색·로고·명찰을 모두 그린다.

| 항목 | 값 |
| --- | --- |
| 원본 | `public/models/voxel-crew.blend` (메시 94개, 본 22개, Idle·Walk 액션) |
| 런타임 | `public/models/crew.glb` (메시 2개, 1,240 tri, 119 KB) + `crew-walk.bin` (41 KB) |
| 가공 | `scripts/blender/process-voxel-crew.py` |
| 메시 | `crew_body`(아틀라스) · `crew_accent`(앞치마 앞판, 단색) |
| 키 / 원점 | 1.81 m / 발바닥이 원점 |
| 전방 | `-Z` |

##### 원본을 그대로 쓸 수 없는 이유

원본은 부위마다 메시가 따로 있어 **아바타 한 명에 드로우 콜 94개**가 든다. 50명이면 4,700 콜로 예산(50)의 94배다. 가공 스크립트가 세 가지를 바꾼다.

1. **메시 병합** — 94개를 몸통·앞판 2개로 합친다. 머티리얼이 하나뿐이라 병합해도 배색이 유지된다.
2. **스킨 제거 + 본 행렬 베이크** — `InstancedMesh` 는 스키닝을 못 한다. 지오메트리는 레스트 포즈로 굳히고, Walk 한 사이클의 본 스키닝 행렬을 따로 구워 셰이더가 읽게 한다(§아래).
3. **스튜디오 바닥 제외** — `.blend` 에는 200 x 200 m 바닥과 조명·카메라가 함께 있다. 타입만 보고 고르면 바닥이 아바타마다 딸려 간다. **리그에 묶인 메시만** 캐릭터로 본다.
4. **180° 회전** — 원본은 `+Z` 를 본다. 프로젝트 규약(`-Z`)에 맞춰야 `yaw` 를 그대로 쓸 수 있다. `mesh.transform` 으로 정점과 법선을 함께 돌린다. `transform_apply` 오퍼레이터는 백그라운드 실행에서 선택 상태를 타므로 쓰지 않는다.

##### 플레이어 색은 앞치마 앞판에만

유니폼이 고정색이면 50명이 모두 같아 보여 §2 의 "명찰 범위(25 m) 밖에서는 색만으로 구분한다"가 깨진다.

**아틀라스의 앞치마 색은 `#18171a`(밝기 13%)라 텍스처에 `instanceColor` 를 곱하면 검게 남는다.** 그래서 앞치마 전체가 아니라 **앞판 두 장만** 떼어 텍스처 없는 단색 머티리얼로 그린다. 주머니·끈·빨간 트림은 몸통에 남아 텍스처를 유지한다. 앞판은 0.385 × 0.383 m 로 먼 거리 식별에 충분하다.

##### 걷기 모션: 본 행렬 텍스처

`InstancedMesh` 는 스키닝을 못 해 three 의 스킨 경로를 쓸 수 없다. 대신 Walk 한 사이클의 **본 스키닝 행렬을 미리 구워** 셰이더가 직접 읽는다.

| 항목 | 값 |
| --- | --- |
| 자료 | `crew-walk.bin` — Float32, `[프레임][본][행렬 위 3행]` |
| 크기 | 40 프레임 x 22 본 x 12 float = **41 KB** |
| 텍스처 | `DataTexture` RGBA Float, 66 x 40, `NEAREST` |
| 정점 속성 | `_BONEINDEX` (glTF) → `_boneindex` (three) |
| 인스턴스 속성 | `aWalkPhase`(0~1), `aWalkBlend`(0~1) |

**정점 하나가 본 하나에 100% 묶여 있어서**(리지드 바인딩, 정점 960개 전수 확인) 행렬을 한 번만 곱하면 된다. 정점 위치를 통째로 굽는 VAT 보다 자료가 훨씬 작다.

사이클은 **시간이 아니라 걸은 거리**로 돌린다. 시간 기준이면 속도가 바뀔 때 발이 미끄러진다. `metersPerCycle` 은 실제 보폭(약 0.52 m x 2 걸음)보다 길게 잡았는데, 보폭 그대로 쓰면 이동 속도 4.5 m/s 에서 초당 4.3 사이클이 되어 다리가 과하게 빨라진다. 약간의 미끄러짐과 읽히는 속도를 맞바꾼 값이다.

멈추면 `aWalkBlend` 를 0 으로 당겨 **레스트 포즈**로 돌아간다. `Idle` 클립은 전 본 0° 로 움직임이 없어서, 서 있는 자세는 모델 그대로가 정답이다.

프레임은 두 장을 선형 보간해 읽는다. 40 프레임을 1.67초에 재생하면 24 fps 라 끊어 쓰면 다리가 덜컥거린다.

##### 내보내기에서 애니메이션이 사라지는 함정

`.blend` 에 멀쩡한 Walk 가 있어도 glTF 로 내보내면 **키프레임 2개만 남는 일**이 있다. 루프 애니메이션은 첫·끝 포즈가 같아서, 그러면 정지한 것처럼 보인다.

원인은 익스포터의 키프레임 최적화다. 내보낼 때 `export_force_sampling=True`, `export_optimize_animation_size=False` 를 줘야 매 프레임이 남는다. 가공 스크립트는 `.glb` 가 아니라 `.blend` 에서 직접 행렬을 구우므로 이 함정을 아예 피한다.

##### 아틀라스 필터

샘플러의 확대 필터는 `NEAREST`(9728)다. `LINEAR` 로 바뀌면 픽셀 아트가 뭉개진다. 머티리얼을 직접 만들지 않고 glTF 가 만든 것을 그대로 쓰는 이유다.

##### 공유 지오메트리 해제 방지

GLTF 지오메트리·머티리얼을 쓰는 메시에는 **`dispose={null}` 이 필수다.** r3f 는 언마운트 때 객체의 모든 속성을 훑어 `dispose()` 를 부르는데, 그러면 `useGLTF` 캐시가 들고 있는 공유 자원이 해제되어 `/space` 에 다시 들어왔을 때 아바타가 사라진다.

로딩은 `<Canvas>` 가 children 을 `Suspense` 로 감싸므로 별도 경계가 필요 없다. `useGLTF.preload` 로 라우트 진입과 함께 받아둔다.

##### 모델을 바꿀 때

`crewModel.test.ts` 가 `.glb` 를 직접 파싱해 메시 개수·이름·삼각형 예산·원점·전방·아틀라스 필터를 고정한다. 가공 스크립트가 출력하는 `[anchor] headCenterY` 값은 명찰·말풍선이 매달리는 높이이므로 `SPACE_AVATAR.headCenterY` 에 옮겨 적는다.

##### 삼각형 예산을 60k → 80k 로 올린 이유

60k 는 아바타가 캡슐+구 프리미티브(1인 226 tri, 50명 11,300)이던 시절의 값이고, 복셀 모델로 바꾸면서 아바타만 62,100 이 됐다. 아바타 밖 씬은 바닥·전광판·광고판·벽 부품·펄스 링을 다 합쳐 **약 1,000 tri** 로 무시할 수준이라, 60k 중 48k 가 쓰이지 않고 남아 있던 셈이다.

실질 병목은 삼각형이 아니라 **드로우 콜**이다. 50명을 콜 3개에 담고 있고 예산은 50 이다. 모바일 GPU 가 62k 삼각형을 한 프레임에 그리는 것 자체는 문제가 되지 않는다. 80k 는 아바타 62k + 씬 1k 에 헤드룸을 둔 값이다.

원격 아바타는 개별 `<mesh>` 로 만들지 않는다. 50명이면 몸통·앞판·그림자로 **150 드로우 콜**이 되어 바닥·전광판·광고판·조명까지 올라간 모바일 씬에서 예산을 세 배 넘게 초과한다. `InstancedMesh` 3개로 고정하고, 슬롯 인덱스 0~49 를 플레이어에 배정한다. 빈 슬롯은 `count` 를 줄여 숨긴다.

명찰과 말풍선은 `<Html>` DOM 이라 개수가 곧 레이아웃 비용이다. 거리순 선별은 `avatarCulling.ts` 의 순수 함수로 분리해 테스트한다.

`/space` 외 라우트의 번들 크기가 변하지 않아야 한다.

### 8.0 렌더 해상도

모바일 기기는 `devicePixelRatio` 가 3 인데 캔버스를 1.5 로 그리면 **기기 해상도의 50%** 다. 같은 화면의 DOM HUD 는 3 으로 또렷하게 나오므로 나란히 두면 캔버스만 흐려 보인다.

393×852 CSS px, 기기 dpr 3 을 예로 들면 다음과 같다. 패널·글자의 실제 화면 크기는 스폰 위치와 카메라 거리에 따라 달라진다.

| 렌더 dpr | 캔버스 해상도 | 기기 대비 선형 해상도 |
| --- | --- | --- |
| 1.5 | 약 590×1278 | 50% |
| 2.0 | 786×1704 | 67% |
| 3.0 | 1179×2556 | 100% (현재 상한 밖) |

1.5 로 시작해 `PerformanceMonitor` 의 측정값에 따라 `[1, 2]` 사이를 오간다. 처음부터 최대로 올리면 약한 기기의 첫인상이 끊기고, 고정하면 기기 편차를 감당할 수 없다. 해상도는 0.25 단위로 끊는다. 미세하게 계속 바뀌면 화면이 들썩인다.

캔버스 텍스처에는 **이방성 필터를 최대로** 올린다. 기본값 1 로 두면 비스듬히 볼 때 글자가 뭉개진다.

### 8.1 번들 측정 결과 (2026-10-31)

**초기 기록(v0.4)**: 아래는 당시의 단일 three 포함 청크와 라우트 참조 검사 결과다. 이후 변경을 포함한 최신 기본 빌드 결과로 취급하지 않는다.

| 항목 | 측정값 |
| --- | --- |
| three 포함 청크 | 936 KB(비압축) / **246 KB(gzip)** |
| 이 청크를 참조하는 라우트 | `/space` 만 (`react-loadable-manifest`) |
| 전 라우트 초기 HTML 참조 | 0건 (24개 프리렌더 HTML 검사) |
| 공용 `rootMainFiles` | 429 KB(비압축), three 도입 전후 변화 없음 |

초기 검사에서는 three 청크가 `/space` 의 캔버스 마운트 때만 로드되고 공용 번들·초기 HTML 에는 포함되지 않았다. 당시 gzip 목표를 200 KB 에서 260 KB 로 바꾼 근거는 `<Canvas>` 내부의 `extend(THREE)` 가 THREE 네임스페이스를 JSX 카탈로그에 등록한다는 점과 246 KB 단일 청크 측정값이었다. `createRoot` 와 제한된 `extend` 목록으로 전환하는 최적화는 리사이즈·이벤트·컨텍스트 브리지를 직접 관리해야 해 1단계에 도입하지 않았다.

**현재 변경분의 빌드 확인**:

| 실행 | 결과 |
| --- | --- |
| `pnpm build` (기본 Turbopack) | 컴파일 단계에서 수분 동안 추가 출력이 없어 중단. 완료 여부·최신 청크 크기 미확인 |
| `pnpm exec next build --webpack` | 컴파일 16.6초·TypeScript 검사 2.5초 성공. 이후 `/cagr` 의 blockchain.com 2026년 시세 조회가 `fetch failed` 로 끝나 프리렌더 실패 |

이번 webpack 수치는 **SpaceCanvas 비동기 청크 9개의 합**이고 이전 246 KB 는 **three 포함 단일 청크** 기록이다. 측정 범위와 번들러 조건이 다르므로 증가량을 직접 비교하거나 gzip 260 KB 목표를 최신 코드에서 달성했다고 판단하지 않는다. webpack 수치는 컴파일 산출물의 참고값이며 성공한 전체 프로덕션 빌드 결과가 아니다. 외부 시세 조회가 가능한 환경에서 전체 빌드를 완료하고, 기본 Turbopack의 라우트·공용 청크 참조와 같은 범위의 gzip 크기를 다시 측정해야 한다.

### 8.2 렌더 성능 실측 (미측정 — 실행 환경 차단)

개발용 계측 코드는 추가했지만 실제 브라우저 수치는 아직 없다. 2026-10-31 검증 환경에서 Chromium 실행은 macOS sandbox의 MachPort 권한 오류로 차단됐고, 연결 가능한 Chrome·인앱 브라우저도 확보하지 못했다. 이 상태를 성능 검증 완료로 취급하지 않는다.

재현 절차:

1. `pnpm dev` 로 개발 서버를 띄우고 `http://localhost:3002/space?dummies=50&stats=1` 을 연다. 운영 환경에서는 더미와 계측 패널이 비활성화된다.
2. 원격 더미 50명과 로컬 아바타 1명이 함께 렌더되는지 확인한다. 50명 목표보다 로컬 1명을 더한 상태로 여유를 측정한다.
3. 탭을 활성 상태로 유지한다. 셰이더·텍스처 준비 5초를 제외하고 10초 동안 표본을 모아 화면에 `측정 완료` 가 표시될 때까지 기다린다. 새로고침이나 탭 가시성 변경은 측정을 초기화한다.
4. 평균 FPS, 프레임 시간 p95, 최대 드로우 콜·삼각형 수, dpr 범위를 기록한다. 기기·브라우저·뷰포트·그림자 설정도 남기고 실제 중급 모바일 기기에서 같은 절차를 반복한다.

`SpacePerformanceStats` 는 `useFrame` 이후의 `addAfterEffect` 에서 `renderer.info.render.calls`·`triangles` 를 읽는다. 현재 씬의 프레임당 render 1회 기준으로 그림자 패스를 포함한 렌더 값을 수집한다. 요약값은 패널의 `data-space-performance` 속성에도 남긴다. 모바일 뷰포트 에뮬레이션은 실제 중급 모바일 기기의 GPU 성능 검증을 대신하지 않는다.

| 측정 환경 | 뷰포트 / dpr 범위 | 원격 / 로컬 | FPS / p95 | 최대 드로우 콜 | 최대 삼각형 | 판정 |
| --- | --- | --- | --- | --- | --- | --- |
| 데스크톱 브라우저 | 미측정 | 50 / 1 | 미측정 | 미측정 | 미측정 | 실행 환경 차단 |
| 중급 모바일 실제 기기 | 미측정 | 50 / 1 | 미측정 | 미측정 | 미측정 | 실기기 확인 대기 |

번들 수치(§8.1)와 geometry 계산값(§8)은 렌더 성능 실측과 구분한다. 실측과 필요한 기기 검증이 끝나기 전에는 작업 `1-20` 을 완료로 바꾸지 않는다.

## 9. HUD

캔버스 위에 떠 있는 2D 레이어다. 상태와 조작을 DOM 으로 제공한다. 캔버스 안 텍스트에만 의존하면 확대·스크린리더·WebGL 실패 상황에서 모두 읽히지 않는다.

| 위치 | 내용 |
| --- | --- |
| 좌측 상단 | 접속 표시 (상태 점 + 문구) |
| 우측 상단 | 버튼 묶음 (세로로 쌓임) + 조작 안내 패널 |
| 하단 중앙 | 가상 조이스틱 (손가락 기기 전용) |
| 그 외 전체 | 시야 회전·줌 (캔버스가 직접 처리) |

전체 화면 페이지라 브라우저가 노치를 대신 비켜주지 않는다. HUD 전체를 `safe-area-inset` 만큼 안쪽으로 들인다.

### 9.0 모바일 조작

조이스틱은 **하단 중앙에 고정**하고, 차지하는 면적을 제 크기(지름 120 px)로 제한한다. 나머지 화면 전체가 캔버스의 시야 회전·줌 영역이다.

넓은 터치 영역을 두는 방식(화면 왼쪽 절반을 이동 영역으로 쓰는 모바일 게임 표준 배치)을 먼저 시도했다가 되돌렸다. 그 영역이 캔버스를 덮어 **왼쪽 절반에서 시야 드래그와 두 손가락 줌이 동작하지 않았다**. 조작 영역을 나누는 대신 조이스틱을 작게 두는 쪽이 이 화면에는 맞는다.

같은 이유로 HUD 에서 터치를 받는 요소는 **버튼과 조이스틱뿐**이다. 접속 표시와 조작 안내 패널은 읽기 전용이라 `pointer-events: none` 으로 통과시킨다.

손가락 기기는 카메라를 **최대 거리(18 m)에서 시작**한다. 세로로 긴 화면은 세로 시야가 넓고 가로가 좁다. 가까이 붙으면 전광판은 커지지만 위아래가 잘려 전광판 위 텍스트 배너까지 한 화면에 들어오지 않는다. 물러나면 벽면 전체가 잡힌다. 시작값일 뿐이라 핀치로 다가갈 수 있다.

| 카메라 거리 | 카메라→벽 | 아이폰 세로 전광판 점유 | 스폰 중심 가시 상단 |
| --- | --- | --- | --- |
| 5 (최소) | 22.9 m | 93% | 약 9.1 m — 배너(10.0) 잘림 |
| 11 (기본) | 28.8 m | 74% | 약 12.0 m |
| 18 (손가락 기기 시작) | 35.6 m | 60% | 약 15.4 m |

위 표는 스폰 중심·기본 피치에서 축소 전 전광판 **프레임(10.2 m)** 의 점유율과 가시 상단을 계산한 예시다. §6.4의 축소 가드도 텍스트 배너(9.6 m)보다 넓은 이 프레임을 기준으로 삼는다.

띄울지·가까이 붙일지는 화면 폭이 아니라 `(pointer: coarse)` 로 판단한다. 폭으로 가르면 세로로 세운 태블릿(820 px)이 데스크톱으로 분류된다. 첫 렌더에서 동기로 읽어 시작 거리가 한 박자 늦게 바뀌지 않게 한다.

### 9.0.1 제스처 해석

| 입력 | 동작 |
| --- | --- |
| 손가락 하나 — 좌우 | yaw (시야 좌우 회전) |
| 손가락 하나 — 상하 | 피치 (시야 상하 조절) |
| 손가락 둘 | 줌. 사이 거리 변화만 쓴다 |
| 휠 | 줌 (데스크톱) |

손가락이 둘일 때는 시야 회전이 일어나지 않는다. 그때의 이동은 줌 제스처의 일부라 시야까지 같이 돌면 조작이 뒤섞인다.

핀치는 **프레임마다 한 번만** 두 손가락 사이 거리를 비교한다. 포인터 이벤트는 손가락마다 따로 오므로 이벤트마다 비교하면, 두 손가락을 나란히 끌어도 한쪽만 움직인 중간 상태에서 거리가 변해 줌이 걸린다. 프레임 시점에는 두 손가락의 최신 위치가 모두 반영돼 있어 나란한 이동이 정확히 상쇄된다.

손가락이 닿아 있는 동안 들어오는 휠 이벤트는 흘려보낸다. 일부 브라우저가 두 손가락 팬에서 휠을 합성해 보내는데, 핀치와 겹쳐 두 배로 줌이 걸린다.

제스처 해석은 `pointerGesture.ts` 의 순수 함수로 분리해 테스트로 고정한다. 이벤트 핸들러 안에 두었을 때 줌·회전 방향이 뒤섞이는 문제가 반복됐다.

### 9.1 접속 표시

숫자만 띄우면 서버 미설정·접속 실패 중에도 접속자가 있는 것처럼 읽힌다. 상태를 함께 들고 다니며 문구 자체를 바꾼다.

| 상태 | 문구 | 점 |
| --- | --- | --- |
| `online` | `12 / 50` | 초록 |
| `connecting` | 연결 중 | 오렌지, 깜빡임 |
| `offline` | 오프라인 | 회색 |

`SpaceRoom`의 입장 완료·연결·단절 상태를 표시한다. 서버 미설정과 개발 더미 모드도 `offline`이다. 채팅창이 닫혀 있어도 오류 사유와 수동 재접속 버튼을 표시한다.

### 9.2 버튼 묶음

버튼이 늘어나도 배치·크기·접근성 처리를 각자 다시 쓰지 않도록, 모양은 `SpaceActionBar` 에서만 정의한다. 추가할 때는 `SpaceHudAction` 을 만족하는 항목을 배열에 넣는다.

```ts
interface SpaceHudAction {
  id: string;
  label: string;        // 스크린리더 이름이자 툴팁. 아이콘만으로는 뜻이 안 전달된다
  icon: ReactNode;
  isActive?: boolean;   // 토글 버튼이 켜진 상태
  isDisabled?: boolean;
  badgeCount?: number;  // 읽지 않은 수 등. 0 이면 표시하지 않음
  onClick: () => void;
}
```

현재 버튼:

| 버튼 | 동작 | 비고 |
| --- | --- | --- |
| 뒤로 가기 | `router.back()` | 히스토리가 없으면 `/orange` 로 보냄 |
| 전체 화면 | Fullscreen API 토글 | 미지원 환경(iOS 사파리)에서는 버튼 자체를 숨김 |
| 공간 채팅 | 대화창 토글 | 닫힌 동안 안 읽은 메시지 배지 |
| 조작 안내 | 안내 패널 토글 | 데스크톱·모바일 조작을 함께 적음 |

설정·소리 버튼은 후속 확장 시 같은 배열에 추가한다.

### 9.3 접근성·폴백

- WebGL 컨텍스트 생성 실패 시 `SpaceFallback` 을 띄우고 `/overview` 로 가는 링크를 제공한다.
- `webglcontextlost` 이벤트를 받아 복구를 시도하고, 실패 시 폴백으로 전환한다.
- 키보드만으로 이동과 시야 회전이 모두 가능해야 한다(드래그 없이 `Q`/`E` 로 yaw).
- yaw 가 커지면 시야는 **왼쪽**으로 돈다(전방 `(-sin θ, -cos θ)` 가 `-Z` 에서 `-X` 로 간다). 따라서 왼쪽 키가 양수다. 이 부호는 `followCamera.test.ts` 에서 고정한다.
- 아이콘 버튼은 모두 `aria-label` 을 가지고, 토글 버튼은 `aria-pressed` 를 함께 준다.
- `prefers-reduced-motion` 은 §5 대로 처리한다.
- 입장 상한 초과 시 "공간이 가득 찼습니다" 안내와 재시도 버튼을 보여준다.

## 11. 2단계 구현 — 위치 동기화와 공간 채팅

`workers/chat/src/SpaceRoom.ts`와 `features/space-session`을 연결했다. 기존 전체 채팅의 `ChatRoom`과는 별도 방이며, `/space`는 일반 브라우저와 PWA 모두 이용한다. `NEXT_PUBLIC_CHAT_WS_URL`의 호스트를 그대로 쓰고 경로만 `/v1/space/ws`로 바꾸므로 새 프런트 환경변수는 필요 없다. Worker 배포가 선행돼야 운영 연결이 된다.

### 11.1 전송·렌더 구조

| 항목 | 구현 |
| --- | --- |
| 위치 상향 | JSON `move`, 좌표·회전이 바뀔 때만 최대 10 Hz |
| 서버 전송 | 실제 이동 수신 후 100 ms 타이머 하나로 변경 좌석만 모아 전원에게 전송 |
| 바이너리 헤더 | 버전 uint8 + 종류 uint8 + 인원 uint16 LE + 서버 시각 uint32 LE = 8 B |
| 플레이어 레코드 | 좌석 uint8 + x/z int16 LE(0.01 m) + yaw uint8 + 달리기 플래그 uint8 = 7 B |
| 최대 위치 페이로드 | 50명 동시 변경 시 358 B/회, 최대 10 Hz 기준 약 3.5 KB/s/수신자(프레임 헤더 제외) |
| 직렬화 | 전송 배치당 1회, 같은 버퍼를 전원에게 공유 |
| 원격 렌더 | 수신 시각 기준 100 ms 지연 보간, 최단 회전 경로, 외삽 없음 |
| 상태 갱신 | 좌표는 가변 객체에서 처리. 입퇴장·메시지·접속 상태만 React 구독에 반영 |

거리 기반 전송 AOI는 두지 않는다. 렌더 시에는 기존의 50 슬롯 인스턴싱과 명찰·말풍선 거리/개수 제한을 적용한다. 희소 스냅샷에서 빠진 좌석은 이전 위치를 유지하며 `leave`만 퇴장으로 처리한다. 순서가 뒤집힌 스냅샷을 버리고 32비트 시각의 순환을 처리한다. 개발용 `?dummies=N` 측정 중에는 실제 공간 연결을 열지 않는다.

### 11.2 서버와 비용 관리

- Worker의 기존 Origin 검사·IP 프리픽스 해시·업그레이드 rate limiter를 재사용한다. limiter key에 경로를 포함해 전체 채팅과 공간의 접속 횟수를 구분한다.
- `SPACE_ROOM` 바인딩과 `v2` 마이그레이션을 추가하고 **SQLite-backed DO**로 등록한다. SQLite 등록은 저장 방식의 선택이며, 위치나 채팅 본문을 SQL에 쓰지 않는다. Free 플랜도 SQLite-backed DO를 지원한다([Cloudflare 요금 문서](https://developers.cloudflare.com/durable-objects/platform/pricing/)).
- 50석, 입장 대기 연결 최대 10개, IP 프리픽스당 최대 20연결. 입장 프레임은 10초 내에 보내야 한다. 서버가 좌석·색·스폰을 결정한다.
- 같은 사용자 키로 다시 입장하면 기존 좌석과 위치를 새 소켓으로 넘기고 이전 탭을 종료한다. 이전 소켓의 지연 close가 새 좌석을 제거하지 않도록 소유권을 확인한다. 하이버네이션 이후 close에서 종료 메타데이터까지 사라진 경우에는 살아 있는 로스터를 다시 보내 유령 아바타를 제거한다.
- 클라이언트는 15초마다 raw `ping`을 보내고 런타임 auto-response가 `pong`으로 답한다. 이 응답은 DO를 깨우지 않는다. 클라이언트는 45초 무응답 시 재연결하고, 서버는 실제 이벤트가 있을 때 auto-response 시각까지 확인해 60초 이상 비활성 연결을 정리한다.
- **상시 10 Hz 루프나 주기적인 SQL 쓰기가 없다.** 이동이 없으면 배치 타이머도 없으므로, 사람이 접속해 있어도 유휴 상태에서는 하이버네이션 조건을 만족한다. 런타임이 객체를 다시 생성할 때 WebSocket attachment에서 좌석·위치를 복원한다([WebSocket 하이버네이션](https://developers.cloudflare.com/durable-objects/best-practices/websockets/), [수명주기와 타이머 조건](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)).
- 프레임 크기·초당 입력 수·유한 좌표·월드 경계·이동 거리 예산을 서버에서 검증한다. 잘못된 이동에는 서버 좌표를 다시 보내 클라이언트를 보정한다.

위 구조는 불필요한 요청과 실행 시간을 줄이는 구현이며 무료 운영을 보장하지 않는다. 실제 요금은 전체 계정 사용량·활동 인원·이동 빈도·접속 시간에 따라 달라진다.

### 11.3 실제 프로토콜

공유 타입·파서는 `entities/space/model/spaceProtocol.ts`, 바이너리 코덱은 `lib/spaceSnapshot.ts`에 둔다. 버전은 `v: 1`이다. 클라이언트는 텍스트 JSON을 보내고 서버 위치 배치만 바이너리다.

| 방향 | 타입 | 내용 |
| --- | --- | --- |
| C→S | `join` | 기존 채팅과 공유하는 `clientKey`, `nickname` |
| C→S | `move` | `x`, `z`, `yaw`, `isRunning` |
| C→S | `say` | UUID `rid`, `body` |
| S→C | `welcome` | 자기 `self`와 자신을 제외한 `peers` |
| S→C | `peer` | 신규 입장·메타데이터·자기 위치 보정 |
| S→C | 바이너리 배치 | 변경된 좌석들의 좌표와 회전 |
| S→C | `leave` | 반납 좌석 |
| S→C | `say` | 메시지 ID·rid·좌석·닉네임·본문·서버 시각 |
| S→C | `error` / `full` | 오류 또는 정원 초과 |

소켓 세대 번호로 끊긴 연결의 늦은 이벤트를 무시한다. 연결 실패에는 지터가 있는 지수 백오프(최대 30초)를 적용한다. 방이 가득 차거나 다른 탭으로 교체된 경우 자동 재시도를 중단하고 HUD에서 수동 재연결한다. 브라우저가 숨겨지면 위치 전송과 재시도는 쉬며, 복귀 시 최신 상태를 전송하거나 끊긴 연결을 복구한다.

### 11.4 채팅 UI와 말풍선

- HUD의 채팅 버튼으로 대화창을 열고 닫으며, 닫힌 동안 도착한 메시지는 숫자 배지로 표시한다. 데스크톱에서는 `Enter` 로도 열고 바로 입력칸에 포커스한다(열려 있으면 입력칸으로 되돌린다). 손가락 기기에는 물리 키보드가 없고 자판이 화면 절반을 덮으므로 단축키와 자동 포커스를 모두 적용하지 않는다. 입력창·버튼에 포커스가 있을 때는 `Enter` 를 흘려보낸다 — 글자를 치는 중이면 그 키는 입력창 몫이고, 버튼이면 브라우저가 기본 활성화를 처리한다. 판별은 `shouldIgnoreSpaceHotkey` 한 곳에서만 한다. 이 페이지에서 받은 최근 100개만 메모리에 유지하고 과거 메시지를 서버에서 조회하지 않는다.
- 닉네임과 본문은 기존 `textValidation.ts`로 정규화한다. 본문은 최대 300 grapheme, 3초에 한 번, 링크·연락처 제한과 선정성 필터를 적용한다. 별도 Turnstile 인증이나 기존 전체 채팅의 관리자 차단 상태는 공간에 연동하지 않았다.
- 서버가 자기 발화를 echo해야 전송 성공으로 처리해 입력을 비운다. 오류·타임아웃에는 입력을 남긴다. 서버는 최근 32개의 요청 ID와 본문 해시를 attachment에 두고 같은 요청 ID의 중복 방송을 막는다. 이 보장은 하이버네이션·기존 연결 교체까지 유지되며, 연결이 완전히 종료된 뒤의 새 세션에는 이어지지 않는다. 프런트는 발화를 자동 재전송하지 않는다. 채팅 본문은 attachment에 저장하지 않는다.
- 캐릭터 위 말풍선은 로컬 수신 시각부터 5초, 25 m 이내 가까운 12명까지 표시한다. 한 좌석은 최신 발화 하나만 표시한다. DOM 말풍선에는 입력 이벤트가 잡히지 않으며 본문은 일반 텍스트로 렌더한다.
- 입력창·버튼·키보드로 스크롤 중인 채팅 로그에서는 WASD·방향키·Q/E를 이동으로 처리하지 않는다. 입력 포커스·창 이탈·탭 전환 시 눌린 키를 비우고, 채팅 포커스 중 모바일 조이스틱을 숨겨 잔류 이동을 막는다. 한글 조합 중 Enter는 전송하지 않는다.
- 모바일 키보드가 뜨면 visual viewport에 맞춰 대화창 높이와 하단 위치를 조정한다. 스크롤로 예전 대화를 읽는 중에는 새 메시지로 강제 이동하지 않는다.

### 11.5 로컬 실행·배포와 남은 검증

로컬에서는 배포 없이 테스트할 수 있다. `pnpm chat:dev`가 `workers/chat/.dev.vars`의 빠진 개발 키 네 개와 localhost/127.0.0.1 Origin을 준비한 뒤 8787 포트에서 Worker를 실행한다. 기존 키는 덮어쓰지 않으며 파일은 Git에서 제외한다. 프런트의 `NEXT_PUBLIC_CHAT_API_URL=http://localhost:8787`, `NEXT_PUBLIC_CHAT_WS_URL=ws://localhost:8787/v1/chat/ws`를 적용해 `pnpm dev`를 실행한다. 일반 창과 시크릿 창에서 `http://localhost:3002/space`로 접속한다. Worker의 키 파일을 변경했다면 Worker도 재시작한다. 자세한 설정은 `workers/chat/README.md`를 따른다.

1. 기존 Worker 환경에서 `pnpm chat:typecheck`, `pnpm build:chat`로 확인한다.
2. 운영 반영 시 `pnpm chat:deploy`로 `SpaceRoom` 마이그레이션과 `/v1/space/ws`를 배포한다. 기존 secret과 Origin 설정을 재사용한다.
3. 프런트를 배포한 뒤 서로 다른 사용자 키를 가진 브라우저 두 개에서 입퇴장·이동·채팅을 확인한다. 같은 브라우저의 여러 탭은 한 사용자로 취급해 앞 탭이 종료된다.
4. 50석·네트워크 끊김/복귀·모바일 키보드/백그라운드·실제 FPS와 비용 지표를 확인한다. 현재 실행 환경에서는 실제 브라우저 렌더와 Cloudflare 배포 후 통합 검증이 남아 있다.

## 12. 3단계 사전 설계 — 라이트닝 광고

- 결제: 비트코인 라이트닝 인보이스 발행 → 결제 확인 → 광고 슬롯 예약. 제공자(LNbits·Alby·자체 노드 등) 선택과 콜백 검증은 3단계 착수 시 별도 규격서로 분리한다.
- 입력: 사용자 이미지 업로드. 비율 3:2, 용량 상한, 심사 절차가 필요하다.
- 심사: 이미지가 최대 50명이 동시에 보는 공개 공간에 노출되므로 자동 통과는 두지 않는다. 기존 채팅 관리자 인증(`ADMIN_EMAIL_ALLOWLIST`, Google OAuth)을 재사용한 수동 승인 경로를 기본으로 본다.
- 만료: `expiresAt` 경과 시 플레이스홀더로 되돌린다.
- 좌석 50석은 광고 단가의 근거가 되므로, 동시 접속 상한을 바꿀 때 광고 가격 정책도 함께 재검토한다.

이 단계는 결제·업로드·심사·환불이 모두 얽혀 있어 1단계와 설계 결합을 만들지 않는다. 1단계에서는 §7 의 `AdSlot` 타입과 이미지 광고판 플레이스홀더, §6.6의 빈 텍스트 광고 배너만 둔다. 결제·예약·심사·링크·만료·환불 경로는 아직 없다.

## 13. 테스트 전략

- 순수 로직은 vitest 로 검증한다: 이동 적분·경계 클램프, 카메라 감쇠·피치 클램프, 스폰 산포의 결정성·링 범위, 거리순 컬링, 전광판 숫자 포맷·변동률 색.
- 핀치 입력은 순수 계산과 실제 포인터 이벤트 연결을 함께 검증한다. 두 손가락 평행 이동, 벌리기·모으기, 손가락 추가·해제·취소와 프레임당 1회 소비를 회귀 대상으로 둔다.
- 핀치 거리 변화는 프레임 단위로 계산한다. 정상 `pointerup` 이 다음 프레임보다 먼저 오면 마지막 미소비 줌을 보관해 한 번 적용하고, 같은 프레임에 새 핀치가 시작돼도 이어서 합산한다. `pointercancel`·캡처 상실·blur·연결 해제에서는 미소비 입력을 버린다.
- 50명 렌더 비용은 `1-11` 의 더미 하니스로 수동 측정한다. 자동 성능 회귀 테스트는 두지 않는다.
- 3D 렌더 결과는 자동 검증하지 않는다. 사용자가 직접 브라우저에서 확인한다.
- 품질 게이트: `pnpm check`, `pnpm exec tsc --noEmit`, `pnpm test`, `pnpm check:cycles`.

2026-10-31 v0.22 검증에서 전체 Vitest **66개 파일·552개 테스트**, `pnpm exec tsc --noEmit --incremental false`, 관련 코드 65개 파일의 Biome 검사, 순환 의존 0건, `git diff --check` 가 통과했다. Webpack compile 모드도 통과했으며 이 결과와 §8.1의 전체 프로덕션 빌드 미완료·§8.2의 렌더 성능 미측정 상태는 별도로 관리한다. 벽·바닥·조명의 실제 화면 검수는 브라우저 실행 제한으로 아직 수행하지 않았다.

v0.23 가격 전환 검증은 전체 **67개 파일·565개 테스트**, TypeScript, 관련 코드 67개 파일의 Biome 검사, 순환 의존 0건, Webpack compile 모드와 `git diff --check` 가 통과했다. 가격 전환의 최초 시세·상승·하락·범위 보장·재타기팅·같은 목표 반복·모션 축소·탭 복귀를 순수 로직 테스트 13개로 검증했다. 실제 브라우저에서의 모션·모바일 FPS 검수는 계속 대기한다.

v0.24 끝점 펄스 검증은 관련 **3개 파일·56개 테스트**, TypeScript, 변경 코드 4개 파일의 Biome 검사, 순환 의존 0건과 `git diff --check` 가 통과했다. 빈 차트 숨김과 하락·보합 상태에서 실제 차트의 마지막 점·선 색·끝점 색 일치를 회귀 테스트로 확인했다. 링 애니메이션의 브라우저 시각 검수와 FPS 실측은 실행 환경 제한으로 미확인이다.

v0.25 위치 동기화·공간 채팅 검증은 전체 **75개 파일·676개 테스트**, 프런트와 Worker TypeScript, 관련 코드 100개 파일의 Biome 검사, 순환 의존 0건, Webpack compile 모드, Worker 배포 dry-run, `git diff --check`가 통과했다. 연결·재연결·만석·중복 탭 교체·희소 위치 보간·잘못된 프레임·채팅 전송 확인·좌석 재사용 말풍선·입력 격리를 검증했다. Worker 테스트는 Cloudflare API 모의 환경이며, 실제 런타임 하이버네이션과 다중 브라우저 통합 검증 및 운영 배포는 수행하지 않았다. 전체 프리렌더 빌드와 실제 렌더 성능의 기존 제약은 유지된다.

로컬 접속 보완에서는 누락 키로 인한 HMAC 실패를 재현하고 `pnpm chat:dev`에 개발 설정 준비 단계를 추가했다. 설정 준비 회귀 7개를 포함한 Worker 관련 **5개 파일·39개 테스트**, Worker TypeScript, 변경 코드 Biome, 순환 의존 0건과 `git diff --check`가 통과했다. 생성된 로컬 키로 실제 IP guard·공간 identity HMAC 계산이 성공함을 확인했다. 실행 중인 사용자 Worker의 재시작 이후 브라우저 접속 확인은 별도로 남는다.
