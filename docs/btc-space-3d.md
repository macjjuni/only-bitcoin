# BTC 스페이스 3D 규격서

> 버전: v0.3
> 기준일: 2026-10-31
> 제공 방식: `/space` 라우트의 전체 화면 3D 공간
> 상태: 1단계 구현 기준안
> 수용 규모: 동시 접속 50명

Three.js 기반 3D 공간에 비트코인 실시간 가격 전광판을 세우고, 사용자가 3인칭 캐릭터로 돌아다니며 다른 접속자와 대화하는 기능이다. 전광판 좌우에는 라이트닝 결제로 판매하는 광고판을 둔다.

구현은 3단계로 나눈다. **1단계는 싱글 씬**(네트워크 없음)이며 이 문서의 구현 기준은 1단계다. 다만 월드 크기·렌더 구조·성능 예산은 모두 **동시 접속 50명**을 전제로 잡는다. 1단계에서 단일 플레이어용으로 짜놓고 2단계에서 50명을 얹으면 아바타 렌더 경로를 전부 다시 써야 하기 때문이다. 2단계 멀티플레이와 3단계 라이팅 광고는 §11, §12에 사전 설계만 둔다.

이 문서에서 좌표 1 유닛은 1 m, 각도는 도(°), 시간은 초(s)를 뜻한다.

## 1. 확정값

| 항목 | 값 | 비고 |
| --- | --- | --- |
| 렌더 스택 | `@react-three/fiber` 9 + `@react-three/drei` 10 + `three` 0.187 | fiber 9 의 react peer 는 `>=19 <19.4`, 현재 19.2.6 으로 충족 |
| 카메라 | 3인칭 추적 | 캐릭터 뒤 고정 거리, 드래그로 시야 회전 |
| 조작 | 데스크톱 WASD·방향키, 모바일 가상 조이스틱 | Shift 달리기 |
| 접근 조건 | 모든 브라우저 | 채팅과 달리 PWA standalone 게이트를 두지 않음 |
| 라우트 | `/space` | 헤더·하단 내비 숨김, 전체 화면 |
| 번들 | 라우트 단위 `dynamic` + `ssr: false` | 다른 페이지 번들에 three 를 넣지 않음 |
| **동시 접속 상한** | **50명** | 초과 접속은 `full` 로 거절 |
| 월드 | 바닥 64 × 48, 가용 52 × 32 | 50명 기준 33.3 m²/인 |
| 스폰 | 중심 `(0, 0, 0)` 반지름 5~14 산포 | `clientKey` 해시로 결정적 분산 |
| 아바타 간 충돌 | 없음 (겹침 허용) | 경계 클램프만 적용 |
| 전광판 | 12 × 6, 중앙 뒷벽 | `CanvasTexture` 도트 매트릭스 |
| 광고판 | 6 × 4 (3:2) × 2면 | 전광판 좌우, 안쪽 15° 회전 |
| 가격 소스 | `useBitcoinStore` | 전역 `Initializer` 의 거래소 소켓을 그대로 구독 |
| 아바타 렌더 | `InstancedMesh` 50 슬롯 | 50명 전체가 드로우 콜 3개 |
| 명찰 표시 상한 | 25 m 이내 & 가장 가까운 16명 | DOM 노드 폭발 방지 |
| 말풍선 표시 상한 | 동시 12개, TTL 5 s | 가장 가까운 순 |
| 성능 목표 | 데스크톱 60 fps, 중급 모바일 30 fps 이상 | 아바타 50명 상태 기준 |
| 서버 틱 (2단계) | 10 Hz, 전원 공유 버퍼 브로드캐스트 | §11 |
| 멀티플레이 | 1단계 범위 밖 | 2단계에서 `SpaceRoom` Durable Object 추가 |

전광판 가격 표시는 `drei` 의 `<Text>`(troika SDF) 가 아니라 `CanvasTexture` 로 그린다. 숫자용 폰트 아틀라스를 추가로 받지 않아도 되고, LED 도트 매트릭스 질감을 셰이더 없이 낼 수 있다. 한글이 들어가는 닉네임 명찰은 `drei` 의 `<Html>` 로 DOM 을 띄운다. 한글 글리프를 SDF 아틀라스로 만들면 용량이 수 MB 가 되므로 3D 텍스트로 만들지 않는다. 대신 DOM 명찰은 개수가 곧 레이아웃 비용이므로 위 표의 표시 상한을 둔다.

명찰 16개·말풍선 12개 상한은 **동시 접속 수에 비례하는 값이 아니라 DOM 렌더 비용의 상한**이다. 접속 50명 기준으로는 방 인원의 약 3분의 1이 이름표를 달고 보이는 셈이며, 그보다 멀거나 많은 쪽은 색만으로 구분한다.

아바타 간 충돌 처리는 넣지 않는다. 50명이 전광판 앞으로 몰리는 상황에서 밀어내기(separation)를 넣으면 클라이언트마다 밀어낸 결과가 달라져 위치 동기화가 어긋나고, 서버에서 권위적으로 풀면 틱당 비용이 `O(n²)` 로 올라간다. 아바타는 서로 통과하며 겹친다.

## 2. 아키텍처

```text
Next.js (/space)
  └─ SpaceCanvas (dynamic, ssr: false)
       ├─ SpaceScene ─ Ground · SceneLighting · PlayerAvatar
       │                  ├─ RemoteAvatars (InstancedMesh, 최대 50)
       │                  ├─ Nameplates (DOM, 거리·개수 컬링)
       │                  ├─ PriceBillboard ──> useBitcoinStore (전역 거래소 소켓)
       │                  └─ AdBoard × 2 ────> 1단계: 정적 플레이스홀더
       └─ SpaceHud (DOM 오버레이) ─ VirtualJoystick · 조작 안내 · 접속자 수

[2단계 추가분]
  SpaceCanvas ──WebSocket──> Cloudflare Worker(/v1/space/ws)
                                 └─> SpaceRoom Durable Object (메모리 전용, 영속 없음)
```

| 구성 | 역할 |
| --- | --- |
| Vercel | `/space` 페이지, 3D 자산 정적 서빙 |
| `useBitcoinStore` | 전광판 가격 원천. 신규 API·소켓을 추가하지 않음 |
| Cloudflare Worker | 2단계에서 `/v1/space/ws` 라우트만 추가. Origin 검사·IP 가드 유틸 재사용 |
| `SpaceRoom` DO | 2단계. 좌석 50개 관리와 위치 중계 전용. **SQLite 영속 없음** |
| `ChatRoom` DO | 기존 채팅방. 공간 채팅과 **분리** 유지 |

가격은 전역 `Initializer` 가 루트 레이아웃에서 이미 Upbit·Bithumb·Binance·Coinbase 소켓을 띄워 `bitcoinStore` 에 넣고 있다. 전광판은 그 스토어를 구독만 하므로 `/space` 전용 데이터 레이어를 만들지 않는다.

위치 동기화는 기존 `ChatRoom` DO 에 넣지 않는다. `ChatRoom` 은 메시지마다 SQLite 쓰기와 발화 레이트리밋을 수행하는 영속 중심 설계이고, 규격서상 부하 가정도 피크 25명·소켓 50개다. 위치 프레임은 50명 × 10 Hz 의 휘발성 데이터이므로 한 DO 에 섞으면 채팅의 순서 보장과 스토리지 비용이 모두 나빠진다. 같은 Worker 안에 별도 DO 클래스를 추가하면 Origin 검사·CORS·IP 가드는 그대로 쓰면서 상태만 분리된다.

## 4. 월드 레이아웃

좌표계는 three.js 기본을 따른다. `+Y` 가 위, 플레이어는 `-Z` 방향(전광판)을 바라보고 시작한다.

월드 크기는 접속 50명에서 밀도가 적당해지도록 역산했다. 넓게 잡으면 사람이 흩어져 서로 마주치지 않고, 대화가 일어나지 않는다.

```text
                     z = -18 (뒷벽면)
   ┌──────────────────────────────────────────────┐
   │  [광고판 L]      [ 전광판 ]      [광고판 R]    │
   │   6×4, +15°        12×6          6×4, -15°   │
   │   x=-11            x=0            x=+11      │
   │                                              │
   │            ◌  ◌ 스폰 링 r=5~14 ◌  ◌           │
   │          ◌        ● 중심 (0,0,0)       ◌      │
   │            ◌  ◌                 ◌  ◌         │
   └──────────────────────────────────────────────┘
      바닥 64 × 48 │ 이동 경계 -26 ≤ x ≤ 26, -16 ≤ z ≤ 16
```

| 오브젝트 | 크기 (W×H) | 위치 (x, y, z) | 회전 |
| --- | --- | --- | --- |
| 바닥 | 64 × 48 | (0, 0, -2) | `-90°` X축 |
| 전광판 패널 | 9.6 × 5.4 | (0, 6, -18) | 없음 |
| 전광판 프레임 | 10.2 × 6 | (0, 6, -18.1) | 없음 |
| 전광판 광원 | - | (0, 4, -15.5) | 패널과 분리, **축소 그룹 바깥** |
| 광고판 L | 6 × 4 | (-9.9, 6, -17.4) | `+15°` Y축 |
| 광고판 R | 6 × 4 | (9.9, 6, -17.4) | `-15°` Y축 |
| 스폰 링 | 중심 (0, 0, 0) | 반지름 5~14 | yaw `180°` (전광판 응시) |

| 밀도 항목 | 값 |
| --- | --- |
| 가용 면적 | 52 × 32 = 1,664 m² |
| 50명 기준 밀도 | 33.3 m²/인 (한 변 5.8 m) |
| 스폰 링 면적 | 약 537 m² → 입장 직후 10.7 m²/인 |
| 전광판 최장 시청 거리 | 스폰 링 끝 32 m, 경계 코너 42.8 m |
| 전광판 프레임 상단 | 9.0 m (벽까지 8 m 지점의 가시 상단 9.8 m, 여유 0.8 m) |
| 전광판–광고판 간격 | 1.9 m (광고판 안쪽 끝 7.0, 전광판 프레임 끝 5.1) |

스폰은 단일 지점이 아니라 링 안에 분산한다. 50명이 같은 좌표에서 시작하면 아바타가 완전히 겹쳐 입장 직후 화면이 무너진다. `clientKey` 해시로 각도와 반지름을 결정하므로 재접속 시 같은 자리로 돌아온다.

광고판은 전광판과 **세로 중심을 맞춘다**(`y = 6`). 두 판의 높이가 달라서(5.4 vs 4) 아랫변을 맞추면 윗변이, 윗변을 맞추면 아랫변이 어긋난다. 중심을 맞춰야 세 판이 한 줄로 읽힌다. 광고판 4 m 는 전광판 5.4 m 안쪽에 들어오므로 위아래로 0.7 m 씩 물린다.

시선 위계는 높이가 아니라 **크기 차이**로 준다(전광판 9.6 × 5.4 vs 광고판 6 × 4). 15° 안쪽 회전은 스폰 링 어디에서든 세 패널이 한 화면에 잡히게 하는 값이다.

패널 배치의 불변식(세로 중심 일치, 광고판이 전광판 세로 범위 안, 3:2 비율, 프레임 비겹침, 바닥 위)은 `spaceWorld.test.ts` 에서 고정한다.

## 5. 이동·카메라 규격

이동은 고정 타임스텝으로 적분한다. 2단계에서 원격 아바타 보간을 붙일 때 클라이언트마다 적분 결과가 갈리지 않게 하려는 목적이다.

| 항목 | 값 |
| --- | --- |
| 고정 타임스텝 | 1/60 s |
| 프레임당 최대 catch-up | 5 스텝 (초과분은 버림) |
| 걷기 속도 | 4.5 m/s |
| 달리기 속도 | 8.0 m/s (Shift) |
| 가속 | 25 m/s² |
| 감속 | 30 m/s² |
| 캐릭터 yaw 보간 상한 | 12 rad/s |
| 충돌 | 경계 클램프만. 아바타·오브젝트 충돌 없음 |
| 카메라 거리 | 7.0 |
| 카메라 높이 | 3.2 |
| 카메라 기본 피치 | `-12°` |
| 카메라 피치 범위 | `-35°` ~ `+5°` |
| 드래그 yaw 민감도 | 0.25 °/px (오른쪽으로 끌면 월드가 오른쪽으로 따라옴) |
| 키보드 시야 회전 | `Q` 왼쪽 / `E` 오른쪽, 90 °/s |
| 카메라 추종 감쇠 | `1 - exp(-8 · dt)` |
| FOV | 55 |

입력 벡터는 카메라 yaw 기준으로 변환한다. 즉 `W` 는 "화면 안쪽"으로 이동한다. 대각 입력은 정규화해 대각선 가속 버그를 막는다.

`prefers-reduced-motion: reduce` 인 경우 카메라 추종 감쇠를 `1 - exp(-20 · dt)` 로 올려 흔들림을 줄이고, 아이들 상태의 부유 애니메이션을 끈다.

## 6. 전광판 규격

디자인 시안(`public/images/panel`)을 기준으로 한다.

| 항목 | 값 |
| --- | --- |
| 텍스처 | `CanvasTexture` 1600 × 900 (16:9) |
| 패널 geometry | 9.6 × 5.4 (16:9). 텍스처와 비율이 어긋나면 글자가 늘어난다 |
| 갱신 주기 | 가격 변경 시, 최대 4 Hz 쓰로틀 |
| 구성 | 로고·타이틀 / KRW 행 / USD 행 / 24시간 차트 |
| 가격 소스 | `useBitcoinStore` (거래소 WebSocket) |
| 차트 소스 | `usePriceMiniChartData` (바이낸스 BTCUSDT 5분봉 288 = 24h, 15분 갱신) |
| 상승 색 | `#2ee6a8` |
| 하락 색 | `#ef4444` (`--down-rgb`) |
| 브랜드 색 | `#F7931A` (`BITCOIN_COLOR`) |
| 연결 끊김 표시 | 각 행 오른쪽 끝 점이 빨강으로 바뀜 |

텍스처 비율과 패널 geometry 비율은 서로 다른 레이어(`entities/space` / `views/space`)에 있어 한쪽만 바꾸기 쉽다. 두 값이 같다는 것을 `billboardTexture.test.ts` 에서 고정한다.

### 6.1 그리기 방식

한글 라벨(원화·달러·최근 24시간)과 차트를 함께 써야 해서 `drei` 의 SDF 텍스트가 아니라 캔버스로 그린다. 한글 글리프를 SDF 아틀라스로 만들면 수 MB 가 되고, 차트는 별도 라이브러리가 필요해진다. 캔버스는 둘 다 공짜로 해결한다.

폰트에 기대면 깨지는 두 가지는 도형으로 그린다.

- 비트코인 마크: `₿`(U+20BF) 글리프가 없는 환경의 두부 방지. 주황 원 + 기울인 `B` + 위아래 세로 획
- 상승·하락 삼각형: `▲`·`▼` 글리프 의존 제거

숫자는 등폭 스택, 한글 라벨은 시스템 산세리프 스택을 쓴다. 숫자가 가변폭이면 4 Hz 갱신 때 자리수마다 글자가 떤다.

### 6.2 글자 크기 — 자동 축소

모든 글자는 **자기 칸의** 가용 폭에 맞춰 줄어든다. 가격 칸 560 px, 변동률 칸 240 px 다. 캔버스 텍스트 폭은 글자 크기에 선형이므로 최대 크기에서 한 번 재고 비율만 곱한다. 1 px 씩 줄이며 반복 측정하지 않는다.

고정 크기로 두면 가격 자리수가 늘어나는 순간 옆 칸을 침범한다. `₩1,234,567,890`(10자리) 까지 검증한다.

시세가 아직 없으면(`스토어 초기값 0`) 가격과 변동률을 모두 `—` 로 두고 삼각형을 그리지 않는다. 가격은 비었는데 변동률만 `0.00%` 로 보이면 값이 있는 것처럼 읽힌다.

### 6.3 차트

| 항목 | 값 |
| --- | --- |
| 표본 | 288개를 180개로 솎음. 폭 1,375 px 에 288개면 한 점이 4.8 px 라 과하다 |
| 마지막 점 | 반드시 보존. 현재가가 잘리면 안 된다 |
| 축 눈금 | 1·2·5 계열 간격으로 데이터를 양쪽에서 한 칸씩 감쌈 |
| 선 색 | 24시간 방향을 따름(상승 초록 / 하락 빨강) |
| 끝점 배지 | 끝점 왼쪽 위, 차트 영역 안쪽으로 가둠 |

눈금 **개수는 고정하지 않는다.** 개수를 맞추려 간격을 키우면 범위가 실제 변동폭의 몇 배로 벌어져 선이 차트 아래쪽에 눌린다. 실측으로 96,500~100,100 데이터가 95,000~105,000 범위에 그려져 플롯 높이의 36% 만 쓰는 문제가 나왔다. 개수를 양보하고 범위를 좁히는 쪽을 택한다.

끝점 배지는 차트 위쪽 바깥에 두면 오른쪽 가격 축 라벨과 겹친다. 끝점 기준으로 붙이고 차트 영역 안에 가둔다.

### 6.4 좁은 화면 대응

three 의 원근 카메라는 **수직** FOV 를 고정하고 가로를 종횡비에서 유도한다. 세로로 긴 화면일수록 가로 시야가 좁아진다. 세로 FOV 55° 기준으로 데스크톱(종횡비 1.78)은 가로 85.6° 인데 아이폰 세로(0.46)는 27.0° 뿐이다.

가시 폭을 정하는 거리는 **카메라에서 벽까지**다. 카메라는 플레이어 뒤 11 m 에 있으므로 스폰 중심 기준 `18 + 11·cos(12°) = 28.76 m` 다. 플레이어 거리(18 m)로 계산하면 가시 폭을 13.8 m 가 아닌 8.6 m 로 잡게 된다.

| 기기 | 종횡비 | 28.76 m 에서 가시 폭 | 무축소 프레임 점유 | 배율 |
| --- | --- | --- | --- | --- |
| 데스크톱 1920×1080 | 1.78 | 53.2 m | 19% | 1.00 |
| 아이폰 세로 393×852 | 0.46 | 13.8 m | 74% | 1.00 |
| 갤럭시 세로 360×780 | 0.46 | 13.8 m | 74% | 1.00 |
| 좁은 창 320×900 | 0.36 | 10.7 m | 95% | 0.84 |

일반적인 폰 세로는 기본 카메라 거리에서 이미 들어온다. 축소는 그보다 좁은 화면(접는 폰 커버 화면, 좁게 줄인 데스크톱 창)을 위한 안전장치다.

**축소 방식**: 전광판 프레임이 가시 폭의 80% 를 넘지 않는 배율을 종횡비에서 계산하고 `[0.5, 1]` 로 자른다. 축소 대상은 전광판·프레임·광고판이고, 바닥 광원은 그룹 **바깥**에 두어 화면이 좁다고 조명까지 어두워지지 않게 한다.

기준점을 그대로 두고 줄이면 패널이 중심을 향해 수축하면서 **아랫변이 떠오른다**. 배율 0.68 에서 프레임 아랫변이 3.00 m → 3.96 m 로 1 m 올라가 벽에 붙은 간판이 공중에 뜬 것처럼 보였다. 아랫변이 제자리에 남도록 기준점을 함께 내린다.

전광판만 가시 폭에 맞춘다. 광고판까지 포함한 벽면 전체(25.6 m)를 맞추면 배율이 떨어져 전광판이 점처럼 작아진다. 광고판은 화면 밖으로 나가도 되고, 고개를 돌리면 보인다.

**검토했다가 버린 안**: 카메라 FOV 를 넓히는 방법. 화면에서 차지하는 비율이 같아지므로 글자 크기 이득이 없고, 씬 전체가 어안처럼 왜곡되며 다른 오브젝트까지 작아진다.

### 6.5 가독 거리

패널 폭 9.6 m 가 텍스처 1600 px 에 대응하므로 1 px 는 6 mm 다.

| 요소 | 글자 크기 | 월드 높이 | 32 m 에서 | 가독 한계(5 arcmin) 대비 |
| --- | --- | --- | --- | --- |
| 가격 | 73 px | 0.32 m | 34 arcmin | 6.8배 |
| 한글 라벨 | 36 px | 0.16 m | 17 arcmin | 3.3배 |
| 축 숫자 | 26 px | 0.11 m | 12 arcmin | 2.4배 |

축 숫자는 여유가 가장 적지만 가까이서 읽는 용도라 기준으로 쓰지 않는다. 패널을 더 줄이면 가격부터 확인해야 한다.

크기 하한은 계산이 틀렸을 때의 안전장치로 36 px 만 둔다. 경계 코너(42.8 m)는 기준으로 쓰지 않는다. 사람이 서 있을 자리가 아니다.

## 7. 광고판 규격 (1단계)

1단계에서는 결제도 업로드도 없다. 슬롯 모델과 렌더링만 완성해 3단계에서 이미지 URL만 꽂으면 되도록 둔다.

```ts
interface AdSlot {
  id: "left" | "right";
  imageUrl: string | null;   // null 이면 플레이스홀더
  linkUrl: string | null;    // 3단계: 클릭 시 이동
  expiresAt: number | null;  // 3단계: 노출 만료
}
```

`imageUrl` 이 `null` 이면 "광고 문의" 플레이스홀더 텍스처를 그린다. 이미지는 3:2 비율로 `cover` 크롭한다. 1단계에서는 외부 이미지를 불러오지 않으므로 CORS·CSP 변경이 필요 없다.

## 8. 성능 예산 (아바타 50명 기준)

모든 수치는 **원격 아바타 50명이 보이는 상태**가 기준이다. 단일 플레이어 상태의 수치는 의미가 없다.

| 항목 | 예산 | 근거 |
| --- | --- | --- |
| 드로우 콜 | 50 이하 | 원격 아바타 50명 = 3 콜(몸통·머리·접지 그림자 각 `InstancedMesh`) |
| 삼각형 | 60k 이하 | 아바타 1인 192 tri(캡슐 96 + 구 96) × 50 = 9.6k |
| 인스턴스 행렬 갱신 | 프레임당 50개 | `instanceMatrix.needsUpdate`, 색은 `instanceColor` 로 1회 설정 |
| DOM 명찰 | 최대 16개 | 25 m 이내 & 거리순 상위 16 |
| DOM 말풍선 | 최대 12개 | TTL 5 s, 거리순 |
| `dpr` | `[1, 1.5]` 상한 | |
| 그림자 | 아바타는 블롭 텍스처 접지 그림자(인스턴싱). 실시간 그림자 맵은 데스크톱만, 1024 | 50명 실시간 그림자는 예산 초과 |
| 후처리 | 없음 | |
| 탭 비활성 | `document.hidden` 이면 렌더 루프 정지 | |
| `/space` 지연 청크 | gzip 260 KB 이하 | 측정 246 KB. three 코어가 대부분이며 §8.1 참고 |

원격 아바타는 개별 `<mesh>` 로 만들지 않는다. 50명이면 몸통·머리·그림자로 **150 드로우 콜**이 되어 바닥·전광판·광고판·조명까지 올라간 모바일 씬에서 예산을 세 배 넘게 초과한다. 처음부터 `InstancedMesh` 3개로 고정하고, 슬롯 인덱스 0~49 를 플레이어에 배정한다. 빈 슬롯은 `count` 를 줄여 숨긴다.

명찰과 말풍선은 `<Html>` DOM 이라 개수가 곧 레이아웃 비용이다. 거리순 선별은 `avatarCulling.ts` 의 순수 함수로 분리해 테스트한다.

`/space` 외 라우트의 번들 크기가 변하지 않아야 한다.

### 8.1 번들 측정 결과 (2026-10-31)

| 항목 | 측정값 |
| --- | --- |
| three 포함 청크 | 936 KB(비압축) / **246 KB(gzip)** |
| 이 청크를 참조하는 라우트 | `/space` 만 (`react-loadable-manifest`) |
| 전 라우트 초기 HTML 참조 | 0건 (24개 프리렌더 HTML 검사) |
| 공용 `rootMainFiles` | 429 KB(비압축), three 도입 전후 변화 없음 |

three 가 다른 라우트에 섞이지 않는다는 목표는 달성했다. `/space` 를 열어 캔버스를
마운트하는 시점에만 내려받고, `/space` 의 초기 HTML 에도 들어가지 않는다.

다만 최초에 적었던 gzip 200 KB 목표는 `<Canvas>` 를 쓰는 한 달성할 수 없다.
`@react-three/fiber` 의 `<Canvas>` 는 내부에서 `extend(THREE)` 를 호출해 **THREE
네임스페이스 전체를 JSX 엘리먼트 카탈로그로 등록**한다(fiber 소스 주석에 명시됨).
네임스페이스 전체가 참조되므로 번들러가 three 코어를 트리셰이킹하지 못한다.
실제로 `drei` 의 무거운 의존(troika, maath, meshline, detect-gpu)은 모두 빠져 있어
`drei` 쪽은 이미 최소다. 즉 246 KB 는 three 코어 자체의 바닥값에 가깝다.

더 줄여야 할 때의 수단은 `<Canvas>` 를 버리고 `createRoot` 로 루트를 직접 만들어
`extend({ Mesh, MeshStandardMaterial, ... })` 로 쓰는 엘리먼트만 등록하는 것이다.
리사이즈·이벤트·컨텍스트 브리지를 직접 구현해야 하므로, 약 46 KB 를 위해 감수할
복잡도는 아니라고 보고 1단계에서는 하지 않는다.

## 11. 2단계 사전 설계 — 멀티플레이 (50명)

1단계 구현이 이 설계를 막지 않도록 하는 목적의 초안이다. 확정값이 아니다.

### 11.1 전송 예산

위치 프레임을 양자화한다. 슬롯 1 B + `x` int16 2 B + `z` int16 2 B + yaw uint8 1 B + 플래그 1 B = **7 B/인**. int16 에 0.01 m 정밀도면 ±327 m 를 담으므로 월드 전체를 덮는다.

| 항목 | 값 |
| --- | --- |
| 서버 틱 | 10 Hz |
| 틱당 페이로드 | 50명 × 7 B + 헤더 8 B = 358 B |
| 클라이언트당 하향 | 약 3.5 KB/s |
| 50명 전체 하향 | 약 175 KB/s |
| 상향 총합 | 50명 × 10 Hz × 10 B ≈ 4.9 KB/s |
| 틱당 직렬화 | **1회** (전원 공유 버퍼) |

50명 규모에서는 **거리 기반 관심영역(AOI) 컬링을 넣지 않는다.** 전원을 한 버퍼에 담아도 클라이언트당 3.5 KB/s 로 충분히 작고, 그 대가로 틱당 직렬화가 접속자 수만큼(최대 50회)에서 1회로 줄어 DO CPU 가 크게 절약된다. 컬링을 넣으면 클라이언트마다 다른 버퍼를 만들어야 해 비용이 역전된다. 수백 명 규모로 올릴 때 AOI 와 샤딩을 함께 도입한다.

렌더 측 컬링(명찰·말풍선)은 §8 대로 유지한다. 전송은 전원, 표시는 선별이다.

### 11.2 서버 구성

- `workers/chat/src/SpaceRoom.ts` 추가, `wrangler.jsonc` 에 `SPACE_ROOM` 바인딩과 마이그레이션 태그 추가. **SQLite 클래스로 등록하지 않는다**(위치는 휘발성).
- Worker 라우트 `/v1/space/ws` 추가. Origin 검사·IP 가드는 기존 `handleWebSocketUpgrade` 경로를 재사용한다.
- 좌석 50개를 인덱스 배열로 관리한다. 입장 시 빈 인덱스를 배정하고 퇴장 시 반납한다. 이 인덱스가 곧 클라이언트의 `InstancedMesh` 슬롯이다.
- 좌석이 없으면 `{ t: "full" }` 을 보내고 연결을 닫는다.
- 하트비트 20 초 무응답이면 좌석을 회수한다. 모바일 백그라운드 전환으로 생기는 유령 좌석이 50석을 잠식하는 것을 막는다. 좌석이 50개뿐이라 100석 설계보다 유령 좌석의 체감 영향이 크므로 회수 주기를 늘리지 않는다.
- 접속자가 0 이면 틱을 멈춘다. 10 Hz 틱이 돌아가는 동안 DO 는 하이버네이트되지 않으므로 빈 방에서 비용이 새지 않게 한다.
- 기존 `CHAT_UPGRADE_RATE_LIMITER` 는 IP 프리픽스당 60초 30회다. 같은 IPv6 `/64` 뒤에서 30명 넘게 입장하면 429 가 된다. 좌석 50개 중 30개가 한 프리픽스에서 나올 상황은 드물지만, `/space` 전용 네임스페이스로 분리할지는 2단계에서 결정한다.

### 11.3 프레임 초안

제어 프레임은 JSON, 위치 프레임은 바이너리(`ArrayBuffer`)로 보낸다. 기존 채팅 프로토콜이 바이너리를 거부하는 것과 의도적으로 다르다. 프레임 상한은 2 KiB 로 둔다.

| 방향 | 형식 | 타입 | 내용 |
| --- | --- | --- | --- |
| C→S | JSON | `enter` | `clientKey`, `nickname`, 아바타 색 |
| C→S | 바이너리 | `move` | `x`, `z`, yaw (10 Hz 상한, 초과 프레임은 서버에서 드랍) |
| C→S | JSON | `emote` | 고정 목록 이모트 |
| C→S | JSON | `say` | 공간 말풍선 |
| S→C | JSON | `seat` | 배정된 좌석 인덱스, 월드 버전 |
| S→C | JSON | `full` | 좌석 없음 |
| S→C | JSON | `roster` | 좌석별 닉네임·색 (입장 시 1회, 이후 변경분만) |
| S→C | 바이너리 | `delta` | 틱당 전원 위치 버퍼 |
| S→C | JSON | `leave` | 좌석 반납 |

닉네임·색 같은 저빈도 메타데이터는 `roster` 로 분리해 10 Hz 위치 버퍼에서 빼낸다. 50명 × 닉네임을 매 틱 보내면 358 B 짜리 틱이 수 KB 로 불어난다.

클라이언트는 원격 아바타를 두 스냅샷 사이 100 ms 보간으로 그린다. 외삽은 하지 않는다.

### 11.4 공간 채팅

- `ChatRoom` 과 별개로 `SpaceRoom` 에서 휘발성 말풍선으로 처리한다. 영속 로그가 필요해지면 그때 재검토한다.
- 50명이 동시에 말하면 말풍선이 화면을 덮으므로 §8 의 동시 12개·TTL 5 s 상한을 적용한다. 서버는 발화를 전원에게 보내고, 어떤 12개를 띄울지는 클라이언트가 거리순으로 고른다.
- 선정성 필터는 기존 `textValidation.ts` 를 재사용한다.

## 12. 3단계 사전 설계 — 라이팅 광고

- 결제: 비트코인 라이트닝 인보이스 발행 → 결제 확인 → 광고 슬롯 예약. 제공자(LNbits·Alby·자체 노드 등) 선택과 콜백 검증은 3단계 착수 시 별도 규격서로 분리한다.
- 입력: 사용자 이미지 업로드. 비율 3:2, 용량 상한, 심사 절차가 필요하다.
- 심사: 이미지가 최대 50명이 동시에 보는 공개 공간에 노출되므로 자동 통과는 두지 않는다. 기존 채팅 관리자 인증(`ADMIN_EMAIL_ALLOWLIST`, Google OAuth)을 재사용한 수동 승인 경로를 기본으로 본다.
- 만료: `expiresAt` 경과 시 플레이스홀더로 되돌린다.
- 좌석 50석은 광고 단가의 근거가 되므로, 동시 접속 상한을 바꿀 때 광고 가격 정책도 함께 재검토한다.

이 단계는 결제·업로드·심사·환불이 모두 얽혀 있어 1단계와 설계 결합을 만들지 않는다. 1단계에서는 §7 의 `AdSlot` 모양만 지킨다.

## 13. 테스트 전략

- 순수 로직은 vitest 로 검증한다: 이동 적분·경계 클램프, 카메라 감쇠·피치 클램프, 스폰 산포의 결정성·링 범위, 거리순 컬링, 전광판 숫자 포맷·변동률 색.
- 50명 렌더 비용은 `1-11` 의 더미 하니스로 수동 측정한다. 자동 성능 회귀 테스트는 두지 않는다.
- 3D 렌더 결과는 자동 검증하지 않는다. 사용자가 직접 브라우저에서 확인한다.
- 품질 게이트: `pnpm check`, `npx tsc --noEmit`, `pnpm test`, `pnpm check:cycles`.
