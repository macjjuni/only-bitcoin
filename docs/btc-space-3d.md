# BTC 스페이스 3D 규격서

> 버전: v0.50
> 기준일: 2026-11-02
> 제공 방식: `/space` 라우트의 전체 화면 3D 공간
> 상태: 2단계 위치 동기화·공간 채팅 구현, 로컬 검증 완료·Cloudflare 배포 및 실기기 실측 대기
> 수용 규모: 방 하나당 동시 접속 50명

Three.js 기반 3D 공간에 비트코인 실시간 가격 전광판을 세우고, 사용자가 3인칭 캐릭터로 돌아다니며 다른 접속자와 대화하는 기능이다. 전광판 오른쪽에는 블록 현황판을 두고, 전광판 위 텍스트 배너는 라이트닝 결제로 판다.

구현은 3단계로 나눈다. 1단계에서 싱글 씬·전광판·50명 렌더 구조를 만들었고, 2단계에서는 `SpaceRoom` 한 연결에 위치 동기화와 공간 채팅을 함께 구현했다(§11). 실시간 가격 소켓과 차트는 기존 데이터 계층을 계속 이용한다. 3단계 라이트닝 광고는 §12의 사전 설계 상태다. 2단계 코드는 서버 배포 전까지 운영 접속에 사용할 수 없으며, 실제 다중 브라우저·모바일 검증은 별도로 남는다.

이 문서에서 좌표 1 유닛은 1 m, 각도는 도(°), 시간은 초(s)를 뜻한다.

| 가격 소스 | `useBitcoinStore` | 전역 `Initializer` 의 거래소 소켓을 그대로 구독 |
| 아바타 렌더 | `InstancedMesh` 50 슬롯 × **모델별 그룹** | 한 모델 전원이 드로우 콜 4개. 쓰는 모델만 그룹을 띄운다(§8) |
| 아바타 모델 | **크루 · 곰 · 황소 3종, 사용자가 고름** | HUD 아바타 버튼. 서버가 `modelIndex` 를 모두에게 전파(§8) |
| 명찰 표시 상한 | 본인 1개 + **맵 대각선(약 108 m)** 이내 가장 가까운 다른 사람 16명 | DOM 비용은 거리가 아니라 개수가 정한다. 44 m 였을 때는 반대쪽 끝의 아바타만 보이고 이름이 없었다. `distanceFactor` 는 데스크톱 18, 손가락 기기 12 |
| 말풍선 표시 상한 | 동시 12개, TTL 5 s | 본인 포함, 25 m 이내 가까운 순, 좌석당 최신 발화만 표시 |
| 성능 목표 | 데스크톱 60 fps, 중급 모바일 30 fps 이상 | 아바타 50명 상태 기준 |
| 위치 배치 | 이동 수신 시 최대 10 Hz, 전원 공유 버퍼 | 유휴 상태의 상시 틱 없음(§11) |
| 멀티플레이 | `SpaceRoom` Durable Object | 위치·입퇴장·공간 채팅, 배포 대기 |

전광판 가격 표시는 `drei` 의 `<Text>`(troika SDF) 가 아니라 `CanvasTexture` 로 그린다. 숫자용 폰트 아틀라스를 추가로 받지 않아도 되고, LED 도트 매트릭스 질감을 셰이더 없이 낼 수 있다. 한글이 들어가는 닉네임 명찰은 `drei` 의 `<Html>` 로 DOM 을 띄운다. 한글 글리프를 SDF 아틀라스로 만들면 용량이 수 MB 가 되므로 3D 텍스트로 만들지 않는다. 대신 DOM 명찰은 개수가 곧 레이아웃 비용이므로 위 표의 표시 상한을 둔다.

다른 사람의 명찰 16개·말풍선 12개 상한은 **동시 접속 수에 비례하는 값이 아니라 DOM 렌더 비용의 상한**이다. 본인 명찰은 항상 표시한다. 접속 50명 기준으로는 방 인원의 약 3분의 1이 이름표를 달고 보이는 셈이며, 그보다 멀거나 많은 쪽은 색만으로 구분한다.

아바타 간 충돌 처리는 넣지 않는다. 50명이 전광판 앞으로 몰리는 상황에서 밀어내기(separation)를 넣으면 클라이언트마다 밀어낸 결과가 달라져 위치 동기화가 어긋나고, 서버에서 권위적으로 풀면 틱당 비용이 `O(n²)` 로 올라간다. 아바타는 서로 통과하며 겹친다.

## 2. 아키텍처

```text
Next.js (/space)
  └─ SpaceView ──dynamic, ssr: false──> SpaceCanvas
       ├─ SpaceScene ─ Ground · SceneLighting · PlayerAvatar
       │                  ├─ RemoteAvatars (InstancedMesh, 최대 50)
       │                  ├─ Nameplates · ChatBubbles (DOM, 거리·개수 컬링)
       │                  ├─ PriceBillboard ──> useBitcoinStore (전역 거래소 소켓)
       │                  ├─ BlockDashboard ─> useBlockStore (mempool.space 소켓)
       │                  └─ TextAdBanner ──> 광고 지면, 현재 숨김
       └─ SpaceHud (DOM 오버레이) ─ VirtualJoystick · JumpButton · 조작 안내 · 접속자 수 · SpaceChatPanel

[공간 세션]
  SpaceCanvas ──WebSocket──> Cloudflare Worker(/v1/space/ws)
                                 └─> SpaceRoom Durable Object (SQLite 등록, 좌석·위치는 socket attachment)
```

| 구성 | 역할 |
| --- | --- |
| Vercel | `/space` 페이지, 3D 자산 정적 서빙 |
| `useBitcoinStore` | 전광판 가격 원천. 신규 API·소켓을 추가하지 않음 |
| Cloudflare Worker | `/v1/space/ws`. 기존 Origin 검사·IP 가드·경로별 접속 제한 재사용 |
| `SpaceRoom` DO | 좌석 50개·위치·휘발성 채팅 중계. SQLite-backed 등록, 위치/본문 SQL 쓰기 없음 |
| `ChatRoom` DO | 기존 채팅방. 공간 채팅과 **분리** 유지 |

가격은 전역 `Initializer` 가 루트 레이아웃에서 이미 Upbit·Bithumb·Binance·Coinbase 소켓을 띄워 `bitcoinStore` 에 넣고 있다. 전광판은 그 스토어를 구독만 하므로 `/space` 전용 데이터 레이어를 만들지 않는다.

다만 전역 효과 중 **블록 채굴 토스트와 폭죽은 `/space` 에서 띄우지 않는다.** 전체 화면 3D 위에 토스트가 겹치고 폭죽 캔버스가 한 장 더 올라가면 조작과 프레임을 모두 방해한다. `Initializer` 가 `usePathname` 으로 판단해 `useMempoolSocket(shouldShowMiningEffects)` 에 넘기며, 소켓 연결과 `blockStore` 갱신은 다른 라우트와 똑같이 유지한다. 효과 표시 여부는 ref 로 읽어 라우트 이동이 소켓을 다시 연결하지 않게 한다.

위치 동기화는 기존 `ChatRoom` DO 에 넣지 않는다. `ChatRoom` 은 메시지마다 SQLite 쓰기와 발화 레이트리밋을 수행하는 영속 중심 설계이며, 현재 연결 상한은 500개(`MAXIMUM_ROOM_CONNECTION_COUNT`)다. 위치 프레임은 50명 × 10 Hz 의 휘발성 데이터이므로 같은 DO 에 섞지 않는다. 같은 Worker 안에서 `SPACE_ROOM` 바인딩과 `/v1/space/ws`를 추가하고 Origin 검사·CORS·IP 가드를 재사용했다. 기존 `/v1/chat/*`의 저장·인증 경로는 유지한다.

1단계에는 `spaceStore.ts` 가 없다. 로컬 플레이어와 카메라는 `SpaceScene` 의 `useRef` 에, 입력은 `SpaceInputSource` 에 두며 원격 플레이어 자리에는 개발 더미만 전달한다. `VirtualJoystick` 과 `JumpButton` 은 `useTouchInput` 훅을 거치지 않고 입력 객체의 조이스틱 채널을 직접 갱신한다.

컴포넌트는 `AGENTS.md` 의 region 규약(Hooks / Privates / Events / Transactions / Life Cycles, 섹션 간 두 줄)을 따른다. R3F 의 `useFrame` 콜백은 Life Cycles 리전에 둔다.

## 4. 월드 레이아웃

맵은 **비트코인 아일랜드**다. `public/models/bitcoin_island_draco.glb` (0.57 MB, Draco) 한 덩어리이고, 복셀로 모델링해 메시로 구운 결과다. 전에는 이 문서가 방 치수를 **정의**했지만(평평한 바닥 위 사각형 벙커), 이제는 GLB 가 정한 값을 **받아 적는다.** `spaceWorld.ts` 의 좌표는 전부 그 GLB 에서 읽은 것이고 `spaceWorld.test.ts` 가 GLB 의 JSON 청크를 직접 열어 어긋나지 않는지 고정한다.

좌표계는 three.js 기본을 따른다. `+Y` 가 위, 1 유닛 = 1 m, 복셀 한 칸 0.25 m. **입구(선착장)가 +Z, 궁전이 −Z, 무지개 다리가 +X** 쪽이다.

### 4.1 층과 동선

벙커와 가장 크게 달라진 점은 **지면이 평평하지 않다**는 것이다. 층이 넷이고 계단으로 이어진다.

| 층 | 높이 | 내용 |
| --- | --- | --- |
| 바다 | 0 | 600 m 평면. 섬 밖은 전부 여기 |
| 선착장 | 0.5 | +Z 입구. 광장까지 계단 |
| 광장 | 5 | 중앙 ₿ 문양, 전광판 두 개, 카페·화분, 원형극장 아랫단 |
| 테라스 | 7.5 | 원형극장 윗단 |
| 궁전 단 | 11 | 걸어서 닿는 가장 높은 층 |

```text
                  궁전 (−Z)
          ┌──────────────────┐  11 m
          │   ╱ 중앙 계단 ╲   │
        테라스 7.5 ── 원형극장
   ┌───────────────────────────────┐
   │   [전광판]  ● ₿  [현황판]     │  광장 5 m
   │    144°   스폰링 r=4~9   36°  │   ← 액자는 중심에서 14.25 m
   └───────────────────────────────┘
              ╲ 입구 계단 ╱            ⟶ 무지개 다리 (+X, 끝 x≈52.6)
                선착장 0.5
                  (+Z)
```

궁전 첨탑 꼭대기는 34 m 이지만 **걸어서 닿지 않는다.** 올라갈 계단이 없고, 그 위를 막는 것은 서버가 아니라 클라이언트의 지형 충돌이다(§5.2).

### 4.2 경계와 스폰

섬은 원형이고 무지개 다리가 +X 로 뻗어 있어 **사각형으로는 모양을 담지 못한다.** 실제 경계는 충돌 메시가 만들고(바다 쪽 가장자리에 높이 2.5 m 투명 벽), `SPACE_BOUNDS` 는 레이캐스트가 비어 있을 때를 대비한 **바깥 상자**다. 서버도 이 상자만 검증한다 — 섬 모양을 서버가 알 방법이 없다.

| 항목 | 값 |
| --- | --- |
| 바깥 상자 | x −23.25 ~ 57.86, z −39 ~ 33 (충돌 메시 + 1 m) |
| 카메라 상자 | 바깥 상자 ±12, 높이 0.6 ~ 40 |
| 스폰 링 | 광장 중심 `(0, 5, 0)`, 반지름 **4~9**, 궁전(−Z)을 바라봄 |
| 표시 삼각형 | 약 8.1만 (드로우콜 7개) |
| 충돌 삼각형 | 약 2.7만 (`Collision`, 숨김) |

**스폰 링 상한이 9 m 인 이유는 서버다.** `createSpawnPoint` 는 서버도 쓰는데 서버에는 지형이 없어 링 안에서 그대로 세운다. 광장 소품(카페 테이블·화분·퍼걸러)이 모두 중심에서 10.6 m 밖에 있고 원형극장 계단이 12 m 부터라, **소품이 없는 것이 확실한 범위**로 묶어야 소품 안에서 시작하는 일이 없다. 11 m 까지 넓혀 재 보니 스폰의 15%가 화단에 박혔다. 벙커 시절의 "스폰 뒤 소품 밖으로 밀어내기" 보정은 그래서 사라졌다.

**온전한 원이 아니라 궁전 쪽(−Z) 반원인 이유는 카메라다.** 3인칭 카메라는 플레이어 뒤 11~18 m 에 선다. 궁전을 보고 서면 카메라는 +Z 로 물러나는데, +Z 쪽에 스폰하면 카메라가 광장 밖 벚나무·화단·퍼걸러 사이로 들어가 첫 화면이 나무 기둥에 가린다. 충돌 메시에 300개 스폰을 돌려 카메라 주변 1.5 m 안의 벽을 세어 봤다.

| 규칙 | d=11 | d=14 | d=18 |
| --- | --- | --- | --- |
| 궁전 바라보기, 온전한 원 | 16% | 10% | 6% |
| 중심 바라보기 | 52% | 50% | 49% |
| 바깥 바라보기 | 0% | 0% | 0% |
| **궁전 바라보기 + 궁전 쪽 반원** | **0%** | **0%** | **0%** |

"바깥 바라보기"(카메라가 광장 중심으로 물러남)도 0% 지만 스폰하자마자 궁전을 등지게 된다. 반원은 **궁전을 정면에 두면서** 카메라를 광장 위에 남긴다.

대가는 스폰 밀도다. 가용 면적이 204 → 102 m² 로 줄어 50명 만석 기준 2 m²/인이 된다. 아바타끼리는 통과하므로 겹쳐도 막히지 않고, 만석은 이론상 상한이라 실제로는 훨씬 여유롭다.

`y` 도 광장 바닥(5)으로 고정한다. 추측하면 접속 직후 떨어지거나 파묻힌다.

### 4.3 전광판 액자

전광판과 블록 현황판은 **맵이 가진 금장 액자**에 끼운다. 액자는 광장 중심에서 반지름 14.25 m, 각각 144°·36° 에 서서 광장 안쪽을 바라본다. GLB 의 `Screen_BTCUSD` / `Screen_Network` 쿼드가 표시 영역이고, 구울 때 박아 둔 정지 화면은 숨기고 그 자리에 실시간 `CanvasTexture` 패널을 넣는다.

| 항목 | 값 |
| --- | --- |
| 액자 안쪽 홈 | 6.0 × 2.75 m (y 7.25 ~ 10) |
| 전광판 중심 | (−11.318, 8.625, −8.223), Y축 +54° |
| 블록 현황판 중심 | (+11.318, 8.625, −8.223), Y축 −54° |
| 설계 패널 치수 | 9.6 × 5.4 (16:9, 텍스처 1600 × 900) |
| 축소 배율 | 0.5093 (= 2.75 / 5.4) → 실제 4.89 × 2.75 |

**높이에 맞춰 줄인다.** 폭에 맞추면 6.0 / 9.6 = 0.625 라 높이가 3.375 m 가 되어 액자 위아래 금장 베벨을 0.3 m 씩 덮는다. 높이에 맞추면 폭이 4.89 m 라 좌우로 0.56 m 씩 남는데, 그 자리는 액자 안쪽의 어두운 홈이라 베젤로 읽힌다. **글자가 잘리는 것보다 베젤이 두꺼운 쪽이 낫다.**

테두리 메시(`frameWidth` / `frameHeight`)는 없앴다. 금장 액자가 이미 테두리라, 그 안에 또 넣으면 홈이 두 겹으로 보인다.

두 판은 여전히 **같은 규격**(9.6 × 5.4)을 쓴다. 광장 양옆에 대칭으로 걸린 형제라 크기가 다르면 한쪽이 보조처럼 읽힌다. 시선 위계는 크기가 아니라 내용이 만든다 — 가격이 움직이는 쪽이 자연히 먼저 읽힌다.

### 4.4 하늘과 조명 — 노을

하늘은 **360° equirectangular 파노라마** 한 장이다(`public/images/360.webp`). 단색이던 것을 그림으로 바꾼 이유는 수평선이다 — 섬은 사방이 바다라 시선의 절반이 하늘과 수평선인데, 단색이면 600 m 바다 평면이 끝나는 자리가 그냥 색이 바뀌는 띠로 보인다. 파노라마에 먼 섬과 폭포가 그려져 있어 그 띠가 **군도의 수평선**으로 읽힌다.

**해상도가 이 하늘의 한계다.** 원본이 1774 × 887 로 도당 4.9 px 인데 가로 FOV 84° 를 1515 px 에 그리면 3.7배 확대된다. Lanczos 2배 + 약한 샤프닝으로 도당 9.9 px(3548 × 1774, WebP q82, 575 KB)로 올려 뒀다. 없는 정보가 생기지는 않지만 GPU 의 양선형 확대 대신 좋은 필터가 먼저 일한다. 더 선명하게 하려면 **원본을 4096 × 2048 이상으로 다시 뽑아야 한다.** 이방성 필터는 소용없다 — 확대 구간이라 `magFilter` 만 타고 이방성은 축소에서만 동작한다.

파노라마는 맵과 **다른 Suspense 경계**에 둔다. 같은 경계에 묶으면 하늘 한 장 때문에 섬까지 늦게 뜬다. 받는 동안에는 수평선 색 단색(`#b98aa0`)으로 버틴다.

맵이 노을 톤(분홍 하늘·황금 궁전)으로 구워져 있어 조명도 거기에 맞춘다. 한낮의 흰 빛을 쓰면 버텍스컬러에 구워진 따뜻한 색과 싸워서 금장이 누렇게 뜬다.

| 광원 | 값 |
| --- | --- |
| 하늘 배경 | 360° 파노라마. `backgroundRotation.y` 로 그려진 해를 광원 방위에 맞춤 |
| 안개 | `#706186`(파노라마 수평선 아래 물빛), 90 ~ 320 m |
| 반구광 | 하늘 `#ffd9c4` / 바다 반사 `#54708f`, 세기 1.1 |
| 태양 | `#ffc08a`, 세기 2.2, 그림자 2048 맵 |
| 랜턴 | `#ffb259`, 세기 90, 도달 16 m |
| 전광판 바닥광 | 비트코인 오렌지, 세기 150, 도달 26 m |

**섬의 밝기는 사실상 전부 태양에서 나온다.** 벙커는 천장이 닫힌 실내라 전역광을 낮추고 펜던트 몇 개로 밝기를 만들었지만, 섬은 하늘이 열려 있다.

- **안개가 수평선을 지운다.** 바다 평면이 600 m 라 끝이 화면에 잡히면 "판때기 위의 섬" 으로 보인다. 무지개 다리 끝(57 m)까지는 또렷하게 두고 그 너머를 하늘색으로 녹인다. 원평면도 220 → 420 m 로 늘렸다 — 안개가 다 덮기 전에 잘리면 바다가 싹둑 끊긴 가장자리로 보인다.
- **랜턴은 가까운 것만 켠다.** 맵에 랜턴 자리가 20곳 있는데 전부 켜면 포인트라이트 20개가 매 프래그먼트를 돈다. 데스크톱 6개·모바일 3개만 켜고 0.25 초마다 가까운 자리로 **옮긴다.** 광원 개수가 프레임마다 고정이라 셰이더가 다시 컴파일되지 않는다.
- **그림자 상자는 플레이어를 따라다닌다.** 섬 전체(80 m)를 한 상자로 덮으면 1024 맵에서 텍셀이 8 cm 라 아바타 그림자가 뭉개진다. 반폭 26 m 상자 + 2048 맵으로 2.4 cm 까지 줄였다. 상자 밖은 그림자가 없지만, 그림자를 지는 것이 아바타뿐이라 눈에 띄지 않는다.
- **섬 자신은 그림자를 드리우지 않는다.** 표시용 메시가 8만 tri 라 그림자 맵에 한 번 더 그리면 드로우 비용이 두 배가 되는데, 복셀 블록은 이미 버텍스컬러에 면별 음영이 구워져 있어 입체감이 충분하다. 실시간 그림자가 실제로 의미 있는 것은 **움직이는 아바타**뿐이다.

폭포 6개는 텍스처 `offset.y` 를 초당 0.9 UV 씩 내려 흘린다. 실제 낙하보다 한참 느리지만, 복셀 폭포는 느리게 흘러야 물줄기로 보이고 빠르면 노이즈가 된다.
## 5. 이동·카메라 규격

이동은 고정 타임스텝으로 적분한다. 클라이언트마다 적분 결과가 갈리지 않도록 하고 원격 아바타에는 별도의 수신 보간을 적용한다.

| 항목 | 값 |
| --- | --- |
| 고정 타임스텝 | 1/60 s |
| 프레임당 최대 catch-up | 5 스텝 (초과분은 버림) |
| 걷기 속도 | 4.5 m/s |
| 달리기 속도 | 8.0 m/s (Shift) |
| 가속 | 25 m/s² |
| 감속 | 30 m/s² |
| 캐릭터 yaw 보간 상한 | 12 rad/s |
| 점프 초기 속도 | 6.0 m/s (`Space`) |
| 중력 | 16 m/s² |
| 점프 정점·체공 | `v²/2g` = 1.13 m, `2v/g` = 0.75 s. 넘을 수 있는 난간의 상한이기도 하다 |
| 충돌 | 바깥 상자 클램프 + **지형 BVH**. 아바타끼리는 겹친다 |
| 걸어 오를 수 있는 턱 | 0.35 m (복셀 계단 한 칸 0.25 에 여유) |
| 카메라 기본 거리 | 11 m, 휠·핀치 조절 범위 5~18 m |
| 카메라 주시점 높이 | 1.75 m |
| 카메라 높이 | `1.75 - sin(pitch) × distance` (기본 거리·피치에서 약 4.04 m), 최저 0.6 m |
| 카메라 기본 피치 | `-12°` |
| 카메라 피치 범위 | `-35°` ~ `+5°` |
| 드래그 yaw 민감도 | 0.25 °/px (오른쪽으로 끌면 월드가 오른쪽으로 따라옴) |
| 손가락 기기 시작 거리 | 18 (최대값). 광장에서 궁전까지 한 화면에 담기 위함 |
| 키보드 시야 회전 | `Q` 왼쪽 / `E` 오른쪽, 90 °/s |
| 카메라 추종 감쇠 | `1 - exp(-8 · dt)` |
| FOV | 55 |

입력 벡터는 카메라 yaw 기준으로 변환한다. 즉 `W` 는 "화면 안쪽"으로 이동한다. 대각 입력은 정규화해 대각선 가속 버그를 막는다.

### 5.1 높이 축과 점프

벙커에서는 바닥이 평평해 `PlayerTransform.y` 가 **점프로만** 0 이 아니었고 지면 판정이 `y <= 0` 하나로 끝났다. 섬에서는 `y` 가 **층이 다른 지면의 절대 높이**다. 지면은 매 스텝 지형에 물어본다(§5.2).

- **누르고 있으면 착지할 때마다 다시 뛴다.** 누름 순간만 잡으려면 입력 계층에 상태를 더 둬야 하는데, 복셀 게임에서는 연속 점프가 흔한 조작이다.
- **공중에서는 궤적을 바꿀 수 없다.** 중력만 받는 포물선이다. 수평 이동은 그대로 적분하므로 뛰면서 앞으로 나아간다.
- **천장에 닿으면 상승이 끊긴다.** 궁전 안에서 뛰어 지붕 위로 빠져나가면 내려올 길이 없어 갇힌다. 천장은 **올라가는 중에만** 묻는다 — 레이캐스트는 스텝마다 도는 비용이라 공짜가 아니다.
- **공중에서는 걷기 모션을 멈춘다.** 뛰는 중에 다리가 돌면 허우적대 보인다.
- **접지 그림자는 바닥에 남긴다.** 같이 떠오르면 높이가 읽히지 않는다.
- **카메라 주시점이 높이를 그대로 따라간다.** 고정해 두면 뛰었을 때 캐릭터가 화면 위로 빠져나간다.
- 명찰과 말풍선도 높이를 더해 함께 올라간다.
- **공백은 항상 점프다.** 포커스된 버튼의 공백 활성화를 브라우저에 남겨 뒀더니, 채팅을 닫을 때 포커스가 토글 버튼으로 돌아가 그 다음 공백이 점프와 채팅 열기를 한 번에 일으켰다. 버튼은 Tab 으로 가서 **Enter** 로 누를 수 있으니 키보드 조작이 막히지 않는다. 겹칠 때는 게임 조작이 이긴다.
- 반면 **글자 입력 중에는 공백을 그대로 흘려보낸다.** 채팅창에 띄어쓰기를 하는데 캐릭터가 뛰면 안 된다.

**손가락 기기는 우측 하단 점프 버튼을 쓴다.** 조이스틱은 2축이라 점프를 실을 자리가 없어 버튼을 따로 뒀다(§9.0.2).

점프 정점 `jumpSpeed² / (2·gravity) = 1.13 m` 는 이제 **"뛰어 넘을 수 있는 난간" 의 상한**이기도 하다. 그보다 낮은 난간은 넘을 수 있다.

### 5.2 지형 충돌

벙커에서는 소품 사각형 목록(AABB + 윗면 높이)으로 충분했다. 섬은 다층이라 "여기서 발이 닿는 높이" 와 "여기로 갈 수 있는지" 를 **충돌 메시에 직접 물어봐야** 한다. `Collision` 메시(약 2.7만 tri)에 `three-mesh-bvh` 로 BVH 를 씌우고 세 가지만 묻는다.

| 질의 | 방법 |
| --- | --- |
| 발밑 높이 | `feetY + 턱` 에서 아래로 레이캐스트, `FrontSide` (위를 보는 면만) |
| 수평 벽 | 캡슐(반지름 0.28, 높이 1.7) 셰이프캐스트로 되밀어내기 |
| 머리 위 천장 | `feetY + 턱` 에서 위로 레이캐스트, `FrontSide` (아래를 보는 면만) |

**높이와 수평을 분리한 이유는 계단이다.** 맵의 계단 한 칸이 복셀 한 칸(0.25 m)인데, 캡슐로 수평까지 함께 보면 계단마다 턱에 걸린다. 캡슐 아랫점을 **오를 수 있는 턱**(`SPACE_STEP_HEIGHT` = 0.35 m) 위에서 시작해 낮은 턱은 아예 보지 않게 하고, 올라서는 일은 발밑 레이캐스트가 처리한다. 0.35 는 계단 한 칸에 여유를 준 값이고 두 칸(0.5)은 넘지 못한다 — 너무 높게 잡으면 허리 높이 난간을 타고 넘는다.

- **벙커와 달리 자동 올라섬(step up)이 있다.** 맵 전체가 복셀 계단으로 이어져 있어 한 칸마다 점프를 요구하면 걸을 수가 없다.
- **발밑 레이는 위에서 쏘지 않는다.** 위에서 쏘면 머리 위 아치나 다리 상판을 지면으로 잡아 그 밑을 지나갈 수 없다. `feetY + 턱` 에서 아래로 쏘면 **겹친 층**이 제대로 갈린다.
- **`FrontSide` 로 면의 방향을 가른다.** 아래로 가는 레이는 상향면의 앞면과 하향면의 뒷면을 만나는데, 하향면(천장·처마 밑)을 지면으로 쓰면 발이 천장에 붙는다. 반대로 위로 가는 레이가 상향면의 뒷면까지 세면 서 있는 바닥이 천장이 된다.
- **되밀어내기는 수평 성분만 쓴다.** 수직까지 반영하면 비탈면이 캡슐을 들어 올려 높이를 두 곳에서 정하게 된다. 바닥·천장처럼 법선이 거의 수직인 면은 수평 성분이 0 이라 건너뛴다.
- **막힌 축을 통째로 지우지 않고 법선 성분만 지운다.** 비스듬히 다가간 벽에서 x·z 를 둘 다 지우면 닿는 순간 그 자리에 선다. 남는 접선 성분이 벽을 따라 미끄러진다.
- 안쪽 모서리에서는 한쪽을 풀면 다른 쪽을 파고들어 **3회까지 반복**한다. 아바타 지름보다 좁은 틈은 영원히 번갈아 밀리므로 상한을 둔다.
- **카메라도 같은 BVH 를 쓴다.** 주시점에서 카메라 쪽으로 레이를 쏴 먼저 맞은 지점보다 0.4 m 앞에 세운다. 벙커는 방이 사각형이라 상자 클램프로 충분했지만 섬은 언덕·성벽·아치가 사방에 있다. 양면(`DoubleSide`)을 보는 이유는 충돌 메시가 닫힌 입체가 아니어서다.
- **서버는 지형을 모른다.** 바깥 상자와 이동 거리 예산만 검증하므로 고친 클라이언트는 지형을 통과할 수 있다. 외형 문제라 서버 검증까지 끌어올리지 않는다.

지형 질의의 **모양**은 `entities/space/model/spaceTerrain.ts` 가, 구현은 `views/space/lib/islandTerrain.ts` 가 가진다. 적분기(`stepMovement`)까지 three 에 묶으면 테스트에서 GLB 를 로드해야 하고 서버는 아예 쓸 수 없다. GLB 가 도착하기 전 한두 프레임과 단위 테스트는 **광장 높이의 평지**(`createFlatTerrain`)로 돈다.

#### 프로토콜

`y` 의 **의미와 범위가 둘 다 달라져** 프레임 버전을 1 → 2 로 올렸다. 옛 서버가 보낸 "점프 높이 2.0" 을 새 클라이언트가 "해발 2.0 m" 로 읽으면 광장 아래에 선 사람이 생긴다. 호환이 불가능하므로 서로를 거절하게 한다 — **워커를 먼저 올리고 웹을 올린다.**

| 항목 | 벙커 | 섬 |
| --- | --- | --- |
| `y` 의 뜻 | 평평한 바닥 위 점프 높이 | 층이 다른 지면의 절대 높이 |
| 인코딩 | `uint8` 1 cm (0 ~ 2.55 m) | `uint16` 1 cm (0 ~ 655 m) |
| 좌석당 바이트 | 8 | **9** |
| 상한 | `SPACE_MAX_JUMP_HEIGHT` 2.5 | `SPACE_MAX_ALTITUDE` 36 |
| 이동 거리 예산 | x·z 만 | **x·y·z** (수직 순간이동도 실제 이동) |

50명 기준으로 450 B, 초당 10번 보내므로 늘어난 50 B 는 사실상 공짜다. 정밀도를 낮춰 1바이트에 밀어 넣을 수도 있지만(14 cm 격자) 계단 한 칸이 25 cm 라 다른 사람이 계단을 오르는 모습이 뚝뚝 끊긴다.

상한 36 m 는 **느슨한 위생 검사지 정확한 상한이 아니다.** 벙커는 바닥이 평평해 "지면 + 점프 정점" 이 곧 상한이었지만, 섬은 지점마다 지면이 다르고 서버는 지형을 모른다. 충돌 메시의 가장 높은 상향면이 궁전 첨탑(34 m)이라 거기에 점프 정점과 여유를 더했다. 층별로 조이려면 지형 높이맵을 서버에도 올려야 하는데, 좌표를 조작한 클라이언트가 공중에 뜨는 것은 외형 문제라 거기까지 가지 않는다 — `SPACE_BOUNDS` 가 섬 밖으로 나가는 것만 막는 것과 같은 선택이다.

`prefers-reduced-motion: reduce` 인 경우 카메라 추종 감쇠를 `1 - exp(-20 · dt)` 로 올려 흔들림을 줄인다.

### 6.1 그리기 방식

한글 라벨(원화·달러·최근 24시간)과 차트를 함께 써야 해서 `drei` 의 SDF 텍스트가 아니라 캔버스로 그린다. 한글 글리프를 SDF 아틀라스로 만들면 수 MB 가 되고, 차트는 별도 라이브러리가 필요해진다. 캔버스는 둘 다 공짜로 해결한다.

폰트에 기대면 깨지는 두 가지는 도형으로 그린다.

- 비트코인 마크: `₿`(U+20BF) 글리프가 없는 환경의 두부 방지. 주황 원 + 기울인 `B` + 위아래 세로 획
- 상승·하락 삼각형: `▲`·`▼` 글리프 의존 제거

숫자는 등폭 스택, 한글 라벨은 시스템 산세리프 스택을 쓴다. 숫자가 가변폭이면 4 Hz 갱신 때 자리수마다 글자가 떤다.

### 6.2.1 우측 상단 접속 배지

전광판이 살아 있는 값을 보여주는 중인지 한눈에 알리는 표시다. 가격 행의 상태 점은 통화별 소켓을 각각 알려주지만, 멀리서는 반경 7 px 점의 색만으로 판단하기 어렵다.

| 항목 | 값 |
| --- | --- |
| pill | `(1338, 52)` 에서 176 × 60 px, 모서리 반경 30 px, 면 색은 `BTC` pill 과 같은 `tickerSurface` |
| 점 | `(1366, 82)` 반경 9 px. 온라인 `#2ee6a8` / 오프라인 `#ef4444` |
| 문구 | 28 px `온라인` / `오프라인`. 점 오른쪽 남은 폭(1375~1514)의 가운데 x=1445 에 정렬 |
| 확산 펄스 | 최대 반경 34 px, 2.2초 주기, 링 2개를 반 주기 간격. 링 안쪽 반경 비율 0.6, 최대 불투명도 0.7 |

pill 폭은 더 긴 `오프라인` 기준으로 **고정한다.** 글자 길이에 따라 폭이 변하면 점 위치가 흔들려 3D 로 겹치는 펄스가 어긋난다. 문구를 왼쪽 정렬이 아니라 점 오른쪽 공간의 가운데에 두어, 두 문구 모두 좌우 여백이 맞는다(`온라인` 28/27 px, `오프라인` 14/13 px).

**온라인 판정은 두 소켓 중 하나라도 붙어 있으면 참이다**(`resolveBillboardOnlineStatus`). 양쪽을 모두 요구하면 한쪽만 끊겼을 때 숫자가 눈앞에서 바뀌는데도 `오프라인` 이라고 적혀 더 혼란스럽다. 어느 피드가 끊겼는지는 가격 행의 점이 따로 알려준다.

펄스는 차트 끝점과 같은 이유로 텍스처가 아니라 3D 링(`BillboardOnlinePulse`)으로 그린다. 베이스 텍스처는 상태가 바뀔 때만 다시 올리므로 프레임마다 커지는 원을 구울 수 없다. 점과 링이 같은 자리에 붙도록 좌표는 `BILLBOARD_ONLINE_MARKER` 한 곳에서만 정한다. 최대 반경이 아래로 y=116 까지 번지므로 원화 행 상단 y=154 와 38 px 떨어져 있다. 끊긴 동안과 모션 축소 설정에서는 링을 숨기고 정적인 점만 남긴다. 빨간 점이 살아 있는 것처럼 뛰면 안 된다.

| 표본 | 288개를 180개로 솎음. 플롯 폭 1,320 px, 왼쪽 x=60·끝점 x=1,380 |
| 세로 배치 | 제목 y=470·보조 제목 y=473, 플롯 상단 y=520·높이 250 px·하단 y=770 |
| 마지막 점 | 반드시 보존. 현재가가 잘리면 안 된다 |
| 축 눈금 | 1·2·5 계열 간격으로 데이터를 양쪽에서 한 칸씩 감쌈 |
| 선 색 | 24시간 방향을 따름(상승 초록 / 하락 빨강) |
| 끝점 가격 툴팁 | 표시하지 않음. 오른쪽 가격 축 눈금은 유지 |
| 끝점 표시 | 선과 같은 색의 반경 12 px 점과 최대 반경 64 px 의 1.8초 주기 확산 펄스. 보합은 선과 같은 초록 사용 |
| 시간 라벨 | y=859. 최대 펄스가 차트 하단을 넘어도 라벨과 겹치지 않게 배치 |

눈금 **개수는 고정하지 않는다.** 개수를 맞추려 간격을 키우면 범위가 실제 변동폭의 몇 배로 벌어져 선이 차트 아래쪽에 눌린다. 실측으로 96,500~100,100 데이터가 95,000~105,000 범위에 그려져 플롯 높이의 36% 만 쓰는 문제가 나왔다. 개수를 양보하고 범위를 좁히는 쪽을 택한다.

차트 끝점의 가격 배지·툴팁은 제거하고 선과 같은 색의 점·펄스만 남긴다. 끝점 x=1,380에서 오른쪽 가격 축 라벨 x=1,452까지 72 px 여백을 둬 최대 반경 64 px 펄스가 축 라벨을 침범하지 않게 한다.

펄스 위치는 베이스 차트와 같은 표본·스케일·좌표 계산을 공유한다. 마지막 가격의 현재 값으로 별도 좌표를 만들지 않는다. `BILLBOARD_CHART_MARKER` 의 점 반경 12 px·펄스 최대 반경 64 px 를 정적 점과 링이 공유한다. 두 개의 링을 반 주기 간격으로 확장·감쇠하며, 원거리 가시성을 위해 최대 반경을 16 → 64 px 로 4배 키웠다. 링 안쪽 반경 비율은 0.68, 최대 불투명도는 0.85, 감쇠는 `0.85 × (1 - phase)^1.4` 이다. 링은 3D 메시의 크기·투명도만 갱신하며 큰 전광판 텍스처를 다시 업로드하지 않는다. 모션 축소 설정에서는 링을 숨기고 정적인 끝점만 유지하며, 차트 데이터가 부족하면 표시하지 않는다.

### 6.4 좁은 화면 대응

**벽면 자동 축소(`resolveWallDisplayScale`)는 없앴다.** 벙커에서는 두 판이 뒷벽 하나에 나란히 걸려 있어, 세로로 긴 화면에서 가로 시야가 좁아지면 두 판이 함께 잘렸다. 그래서 종횡비와 시작 카메라 거리로 배율을 구해 벽면 전체를 줄였다.

섬에서는 **두 판이 광장 양옆으로 갈라져 각각 안쪽을 바라본다.** 한 화면에 둘을 다 담아야 할 이유가 사라졌다 — 왼쪽을 보면 전광판이, 오른쪽을 보면 현황판이 정면에 온다. 그리고 패널 크기는 이제 화면이 아니라 **맵의 금장 액자**가 정한다(§4.3). 뷰포트에 따라 크기가 변하면 액자에서 떨어져 나온다.

좁은 화면에서 글자가 작아지는 문제는 **다가가서** 푼다. 손가락 기기는 최대 거리(18 m)에서 시작해 섬 전체를 보여주고, 핀치로 5 m 까지 붙을 수 있다. 액자 앞 2~3 m 면 폰 세로에서도 가격이 화면 폭의 절반을 넘는다.

three 의 원근 카메라가 **수직** FOV 를 고정해 세로로 긴 화면에서 가로 시야가 좁아지는 성질 자체는 그대로다(데스크톱 종횡비 1.78 → 가로 85.6°, 아이폰 세로 0.46 → 27.0°). 카메라 FOV 를 넓히는 안은 여전히 버린다 — 화면에서 차지하는 비율이 같아 글자 크기 이득이 없고, 씬 전체가 어안처럼 왜곡된다.

### 6.5 가독 거리

패널 폭 9.6 m 가 텍스처 1600 px 에 대응하므로 1 px 는 0.006 m 다. 아래는 `font px × 0.006 m` 로 환산한 **em 높이**다. 글리프의 실제 잉크 영역 높이나 화면에서 보이는 픽셀 수를 측정한 값은 아니다.

| 요소 | 글자 크기 | 축소 전 em 높이 |
| --- | --- | --- |
| 가격 | 최대 108 px | 최대 0.648 m |
| 등락률 | 최대 68 px | 최대 0.408 m |
| 한글 라벨 | 52 px | 0.312 m |
| 축 숫자 | 26 px | 0.156 m |

가격·등락률은 가용 폭에 따라 글자 크기가 줄어들며, 실제 가독성은 글꼴·카메라 거리·원근·벽면 축소 배율·렌더 dpr 의 영향을 받는다. 32 m 는 기존 스폰 링 먼 쪽의 기준 거리이며 이 표만으로 가독 한계를 보장하지 않는다. 패널을 더 줄이면 가격과 축 숫자를 실제 화면에서 함께 확인한다.

자동 축소 글자의 기본 하한은 36 px 다. 실제 브라우저의 원거리 가독성 검수는 §8.2의 렌더 실측과 함께 남겨 둔다.

## 6.6 텍스트 광고 배너

전광판 위에 얹는 **가로가 긴 텍스트 전용 광고 자리**다. 짧은 문구 한 줄을 넓게 펴서 멀리서도 읽히게 한다.

| 항목 | 값 |
| --- | --- |
| 패널 | 9.6 × 0.8 (12:1). 폭은 `SPACE_BILLBOARD.width` 와 같게 유지 |
| 텍스처 | `CanvasTexture` 1440 × 120 (12:1) |
| 위치 | 전광판 프레임 윗변에서 0.2 띄움 → 월드 9.2 ~ 10.0 m |
| 프레임 메시 | 없음. 테두리를 텍스처에 그림 |

프레임 메시를 두지 않는 이유는 높이가 0.8 m 뿐이라, 다른 패널과 같은 0.3 m 테두리를 붙이면 패널보다 테두리가 두꺼워 보이기 때문이다.

문구 길이는 제한하지 않고 **가용 폭에 맞춰 글자를 줄인다**. 길이로 자르면 광고주가 쓸 수 있는 문구가 글자 수에 묶인다. 하한 28 px 아래로는 줄이지 않는다.

```ts
interface AdTextSlot {
  text: string | null;   // null 이거나 공백뿐이면 플레이스홀더
  linkUrl: string | null;
  expiresAt: number | null;
}
```

배너는 슬롯 prop 이 바뀔 때만 다시 그린다. 1단계의 `SpaceScene` 은 항상 빈 슬롯을 넘기므로 플레이스홀더만 표시한다. `linkUrl` 이동과 `expiresAt` 만료 처리는 3단계 범위다.

배너 폭은 메인 전광판 **패널 폭(9.6 m)** 에 직접 연결한다. 높이는 0.8 m 를 유지한다. 좁은 화면 축소 가드(§6.4)는 `max(프레임 10.2, 배너 9.6) = 10.2 m` 를 기준으로 삼는다.

### 6.7 가격 숫자 전환

새 시세는 최대 4 Hz 로 채택하고, 이전에 표시하던 가격에서 새 가격까지 250ms 동안 cubic ease-out으로 이동한다. 상승·하락 모두 목표 범위를 벗어나지 않으며, 중간에 목표가 바뀌면 현재 표시값부터 이어 간다. 같은 목표를 반복 수신해도 전환을 다시 시작하지 않는다.

큰 베이스에는 헤더·두 inset 패널의 그라데이션 표면·통화 라벨·등락률·차트·연결 점을 그린다. KRW·USD 가격 두 칸은 800 × 128 투명 텍스처와 평면으로 분리해 최대 30 Hz 로 갱신하며, 포맷된 문자열이 같으면 업로드하지 않는다. 가격 레이어는 매번 투명하게 지운 뒤 숫자만 그리므로 베이스의 패널 배경·테두리·구분선을 가리지 않는다. 두 레이어는 같은 가격 영역 좌표·폰트·자동 축소 규격을 공유해 정적 숫자와 동적 숫자의 위치가 일치한다. 가격 패치는 패널 상하 2 px 안쪽에 들어오고, 옆 열과의 여백도 유지한다. 추가 렌더 배치는 2개이고 프레임마다 React 상태를 갱신하지 않는다.

최초 유효 시세와 결측값 전환은 즉시 표시한다. 앱 설정의 숫자 애니메이션이 꺼져 있거나 `prefers-reduced-motion` 이 켜져 있으면 보간하지 않는다. 탭 가시성이 바뀌거나 프레임 간격이 길어지면 최신 시세로 맞춘다. 실제 시세가 바뀌지 않으면 숫자를 임의로 흔들지 않는다. 24시간 차트의 15분 갱신 정책은 유지한다.

## 7. 블록 현황판 규격

광장 **오른쪽 액자**에 끼우는 비트코인 블록 현황판이다. 원래는 뒷벽 중앙 전광판 좌우에 이미지 광고판 두 장(6 × 4)이 걸려 있었는데, 광고 1차 범위에서 이미지 광고를 빼기로 하면서(광고 계획서 §10) 광고판을 없애고 **전광판과 같은 규격의 현황판 한 장**을 세웠다. 맵이 섬으로 바뀌면서 두 판은 광장 양옆 금장 액자로 갈라졌고, 대칭은 그대로다(§4.3).

| 항목 | 값 |
| --- | --- |
| 패널 | **9.6 × 5.4 (16:9)** — 전광판과 동일 |
| 프레임 | **맵의 금장 액자**. 전광판과 같은 모델이다(§4.3) |
| 텍스처 | `CanvasTexture` **1600 × 900** — 전광판과 동일 |
| 색·여백·행 규격 | `BILLBOARD_COLORS` 와 전광판 `LAYOUT` 좌표를 그대로 사용 |
| 여백 | 좌우·하단 **56 px** 로 동일. 안내 문구를 빼고 지표 패널을 2 × 2 로 넓혀 맞췄다 |
| 바닥 광원 | 전광판과 같은 오렌지 점광원. 액자보다 낮고 광장 안쪽으로 2.5 m |
| 위치 | `(+11.318, 8.625, −8.223)`. 전광판은 `(−11.318, …)` 으로 **좌우 대칭** (§4.3) |
| 회전 | Y축 **−54°** — 액자가 광장 중심을 바라보는 각도. 전광판은 +54° |
| 재질 | 표시 면 `meshBasicMaterial` + `toneMapped={false}` |
| 데이터 | `useBlockStore.blockData` — 전역 `Initializer` 의 mempool.space 소켓을 그대로 구독. 수수료·멤풀은 읽지 않는다 |
| 재그리기 | **소켓 수신 즉시**(다음 프레임). 유휴 시 10초마다 경과 시간만 확인 |

**치수·텍스처·색·격자를 전광판과 공유한다.** 광장을 사이에 두고 마주 보는 두 판이 서로 다른 디자인을 쓰면 광장이 두 개로 쪼개져 보인다. 헤더 높이(82), 구분선(132), 행 패널(x 56, 폭 1488, 높이 132, 반경 16, 중심 220·368), 세로 구분선(252·1104) 좌표가 전광판과 같은 값이라 두 판을 나란히 봤을 때 선과 글자 높이가 어긋나지 않는다.

### 7.1 표시 내용

이 판이 답해야 하는 질문은 둘이다 — **지금 몇 번 블록인가**, **반감기가 얼마나 남았는가**. 전광판이 가격 2행을 두는 자리에 현재 블록을 담고, 24시간 차트가 있던 아래 영역을 반감기에 모두 준다.

```text
┌───────────────────────────────────────────────┐
│ (₿) BLOCK  [MAINNET]              ● 채굴중   │
│ ───────────────────────────────────────────── │
│ │ 블록   │ 919,482          │ 채굴 시각    │ │
│ │ HEIGHT │                  │ 12분 전      │ │
│ │ 채굴   │ Foundry USA      │ 블록 보조금  │ │
│ │ POOL   │                  │ 3.125 BTC    │ │
│                                               │
│ 다음 반감기  2028 예상                 37.9% │
│ ████████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░ │
│ │ 남은 블록 │ 예상 소요  │ 반감 후 보조금  │ │
│ │ 130,518   │ 약 2.5년   │ 1.5625 BTC     │ │
└───────────────────────────────────────────────┘
```

**수수료·미확인 거래·해시레이트는 뺐다.** 그 숫자들은 이 판에서 묻는 질문의 답이 아니고, 넷을 더 깔면 블록 높이와 반감기가 여섯 개 숫자 중 둘로 묻힌다. 멤풀·수수료가 필요하면 `/blocks` 가 이미 그 일을 한다.

**블록 높이를 가장 크게 둔다**(108 px — 전광판 가격과 같은 크기). 이 판에서 사람이 가장 먼저 찾는 값이 "지금 몇 번 블록인가" 이고 나머지는 그 다음이다. 전부 같은 크기로 늘어놓으면 무엇을 보라는 판인지 사라진다.

헤더는 전광판과 같은 구성이다. 비트코인 마크(도형으로 그려 글리프에 기대지 않는다) + 타이틀 + 알약 배지 + 우측 상단 상태 배지. 전광판이 `온라인`/`오프라인` 을 쓰는 자리에 `채굴중`/`지연` 을 둔다.

| 자리 | 값 | 출처 | 비고 |
| --- | --- | --- | --- |
| 1행 주값 | 블록 높이 | `blockData[0].height` | 108 px, 천 단위 구분 |
| 1행 보조 | 경과 시간 | `blockData[0].timestamp` | `방금` / `N분 전` / `N시간 전` / `N일 전`. **초 단위는 보여주지 않는다** |
| 2행 주값 | 채굴 풀 | `blockData[0].poolName` | 자리값 `-` 는 `—` 로. 길면 줄여 그린다 |
| 2행 보조 | 블록 보조금 | `getCurrentBlockSubsidy(height)` | BTC |
| 섹션 제목 | 다음 반감기 + 예상 연도 | `getNextHalvingData(height).date` | `2028 예상` |
| 진행률 | 현재 반감기 구간 진행률 | `calcPercentage` | 소수 한 자리. 제목 줄 **오른쪽 끝**에 붙인다 |
| 진행 바 | 같은 진행률 | 같음 | 채움 색은 오렌지. 반지름보다 짧은 채움은 지름으로 깎아 끝이 뭉개지지 않게 한다 |
| 지표 1 | 남은 블록 | `nextHalvingHeight - height` | |
| 지표 2 | 예상 소요 | 남은 블록 × 10분 | `하루 이내` / `약 N일` / `약 N개월` / `약 N.N년` |
| 지표 3 | 반감 후 보조금 | `getNextHalvingData(height).blockReward` | 2행의 현재 보조금과 짝을 이룬다 |
| 상태 배지 | 채굴중 / 지연 | 경과 시간 | 20분(평균 간격의 두 배) 넘기면 초록 → 회색 |

**예상 소요는 단위를 크게 끊는다.** 10분 간격을 전제로 역산한 값이라 확정된 날짜가 아니다. `906일` 처럼 적으면 확정처럼 읽히므로 `약 2.5년` 으로 뭉갠다.

진행 바는 전광판이 24시간 차트를 두는 자리를 대신한다. 숫자만 늘어놓으면 "얼마나 남았는지" 가 감으로 오지 않아 한 눈에 읽히는 그림이 하나는 필요하다.

- **높이 0 은 "소켓 연결 전"이다.** 그 상태를 실제 값처럼 그리면 블록이 0번이고 반감기가 코앞인 것처럼 읽힌다. 그래서 높이가 없으면 해시레이트·보조금·반감기까지 모두 `—` 로 비운다.
- 경과를 모르면 상태 배지도 회색이다. 데이터 없는 상태를 초록으로 보여주면 살아 있는 것처럼 읽힌다.
- 로컬 시계가 블록보다 앞서면 경과가 음수가 되므로 0으로 깎아 `방금` 으로 읽히게 한다.

### 7.2 갱신 방식

데이터는 **mempool.space 웹소켓**이 밀어 준다. 폴링이 아니다. 전역 `Initializer` 가 띄운 `useMempoolSocket` 이 블록·수수료·멤풀을 받아 `blockStore` 에 넣고, 현황판은 그 스토어의 변경 알림을 받아 **다음 프레임에 바로** 다시 그린다. 새 블록이 뜨는 순간이 화면에 밀리지 않는다.

| 트리거 | 동작 |
| --- | --- |
| 스토어 변경(소켓 수신) | 다음 프레임에 재그리기 |
| 유휴 10초 | 경과 시간만 확인. `12분 전` → `13분 전` 로 넘어가는 순간을 잡는다 |
| 값이 이전과 같음 | 그리지 않는다. 1600 × 900 캔버스 업로드는 공짜가 아니다 |

경과 시간은 **분이 바뀔 때만** 변경으로 본다. 초 단위로 비교하면 10초마다 매번 다시 그리게 된다.

구독은 `useBlockStore()` 훅이 아니라 `useBlockStore.subscribe()` 로 직접 건다. 훅으로 받으면 블록·수수료·멤풀이 각자 다른 주기로 들어올 때마다 씬 전체가 리렌더된다. 변경 알림만 ref 에 받고 그리기는 프레임 루프에서 한다. 전광판 가격과 같은 방침이다.

### 7.3 광고 지면과 노출 스위치

광고로 파는 지면은 이제 **전광판 위 텍스트 배너 하나**다(광고 계획서 §2). 이미지 광고판은 제거했다.

`spaceConfig.isAdEnabled` 가 배너 렌더를 가른다. **현재 값은 코드 상수 `false` 라 배너가 보이지 않는다.** 이전에는 `NEXT_PUBLIC_SPACE_ADS_ENABLED` 환경변수로 끄게 했는데, 값을 지우면 켜지는 기본값이라 빈 액자가 그대로 노출됐다. 아직 광고를 팔지 않으므로 코드에서 끄는 쪽이 맞다. 판매 경로가 생기면 이 상수를 광고 조회 결과로 바꾼다.

**벽면 장비함(하우징·림·하단 상태 바)은 이 값과 무관하게 남는다.** §4.1 에서 장비함은 전광판과 패널이 함께 쓰는 벽 구조로 정의했고, 켜고 끌 때 벽 구성 자체가 바뀌면 안 된다. 장비함은 전광판과 블록 현황판 두 자리에 생긴다.

##### 레이저 아이를 넣는 두 가지 방법

| 방법 | 쓰는 모델 | 내용 |
| --- | --- | --- |
| 변형 glb 이식 | 크루 | `voxel-crew-laser-eyes-soft.glb` 와 정점 순서가 같다는 점을 이용해 눈동자의 UV·발광 마스크만 옮긴다. **아트가 칠한 마스크**라 눈동자 안에서 중앙만 빛난다 |
| 가공 단계 재질 생성 | 황소 | 눈동자 메시를 떼어 **단색 발광 재질**(`emissive [1, 0.07, 0.04]`)을 입힌다. 아틀라스를 고치지 않아도 되고 변형본이 필요 없다 |

황소는 변형 glb 가 없어 두 번째 방법을 썼다. 눈동자 메시 이름(`l/r_bull_eye_dark_pixel`)을 가공 스크립트의 네 번째 인자로 넘기면 `<모델>_pupil_glint` 로 떼어 낸다. 텍스처를 쓰지 않는 이유는 눈동자가 몇 픽셀이라 단색으로 충분하고, 아틀라스에 마스크를 그려 넣으려면 원본 이미지를 고쳐야 하기 때문이다.

곰은 눈동자가 몸통 배색에 섞여 있어 떼어낼 메시가 없다. 넣으려면 원본에서 눈동자를 별도 메시로 분리해야 한다.

**본 수만 같아야 한다.** 22개가 셰이더의 텍셀 조회 폭을 정하므로 어긋나면 엉뚱한 텍셀을 읽어 아바타가 터진다. 반면 **Walk 프레임 수는 모델마다 달라도 된다** — 황소를 넣으면서 셰이더가 프레임 수를 상수로 박지 않고 본 행렬 텍스처의 높이(`uWalkTextureSize.y`)에서 읽도록 바꿨다. 상수로 박으면 모델마다 셰이더 프로그램이 따로 컴파일된다.

색을 받는 면도 모델마다 다르다. 크루·곰은 앞치마 앞판이지만 황소는 턱시도라 **조끼 앞면**이다. 가공 스크립트의 세 번째 인자로 이름을 넘긴다. 옷 전체를 단색으로 빼지 않는 이유는 주머니·끈·단추까지 색에 묻혀 디테일이 사라지기 때문이다.

##### 몸통 재질은 하나여야 한다

glTF 는 **재질마다 primitive 를 쪼개고**, three 는 primitive 가 둘 이상인 메시를 `Mesh` 가 아니라 **`Group`** 으로 만든다. 런타임은 `getObjectByName` 으로 `Mesh` 를 찾아 인스턴싱하므로 `Group` 이 오면 `'<모델>_body' 메시가 없습니다` 로 터진다.

황소가 이 경우였다. 금색 단추·뿔 끝에 `Bull_Gold_Pixel_PBR` 이 따로 붙어 있었는데, **같은 아틀라스를 쓰고 metallic 값만 달랐다**(0.55 vs 0). 가공 스크립트가 **같은 텍스처를 쓰는 재질이면 하나로 합치고**, 다른 텍스처가 섞여 있으면 베이크를 멈춘다 — 색이 통째로 바뀌는 것을 런타임에서 발견하는 것보다 낫다. 금속 광택 540 tri 를 잃지만 아바타 크기에서 단추 광택은 보이지 않는다.

`crewModel.test.ts` 가 모델 목록을 돌며 메시 이름·**primitive 개수**·본 번호 속성·`.bin` 크기·삼각형 수·키/원점을 전부 검사한다. 모델을 추가하면 자동으로 검사 대상이 된다.

##### 삼각형 예산을 80k → 110k 로 올린 이유

황소가 50명이면 98,600 tri 로 처음 잡은 80k 를 넘긴다. 올리기로 한 근거는 셋이다.

1. **80k 는 측정값이 아니다.** 아바타가 1,242 tri 이던 시점에 "78% 쓴다" 로 역산해 둔 설계상의 가정이고, §8.2 는 여전히 전부 미측정이다.
2. 같은 절에서 **실질 병목으로 지목한 것은 드로우 콜**이다. 모델 3종이 모두 쓰이는 최악의 경우에도 12개로 예산(50) 안이다.
3. 50명이 **전원 황소를 고르는 경우**가 최악이고, 섞이면 그 사이 값이다.

그래도 상한을 없애지는 않았다. 110k 는 모델 하나가 약 2,200 tri 를 넘기면 깨지는 선이라, 다음 모델이 더 무거워지면 테스트가 알려 준다. 실측(§8.2)에서 문제가 드러나면 예산을 되돌리는 대신 **황소의 지오메트리를 줄이는 쪽**이 맞다 — 계단식 라펠 8조각·단추처럼 합칠 수 있는 부품이 남아 있다.

##### 삼각형 예산을 110k → 165k 로 올린 이유

머슼크(일론 머스크 복셀)는 3,202 tri 라 50명이면 160,100 tri 로 110k 를 넘긴다. 머리가 1,434 tri 짜리 통짜 복셀 조각이고 면마다 아틀라스 픽셀이 달라, UV 경계를 지키는 평면 합치기(limited dissolve)로도 3,052 까지만 줄었다. 지퍼 이빨·신발끈 같은 부품을 빼도 약 2,650 이라 110k 기준선(모델당 약 2,200)에 못 들어간다.

올린 근거는 110k 때와 같다. 예산은 미측정 가정이고, 실질 병목인 드로우 콜은 모델 6종(글린트 있는 크루·황소 4콜, 나머지 3콜)이 모두 쓰이는 최악에도 **20개**로 예산(50) 안이다(빚탈릭 추가 기준). 160k 는 50명 **전원이 머슼크**일 때만 나온다. 실측(§8.2)에서 문제가 드러나면 머리 조각을 가볍게 다시 만드는 쪽이 맞다.

##### 모델별 인스턴싱

`InstancedMesh` 하나에 서로 다른 지오메트리를 담을 수 없다. 그래서 **사람을 모델별로 묶어** 그룹마다 `InstancedMesh` 4개를 쓴다(`groupPlayersByModel`).

- 사람이 있는 모델만 그룹을 띄우므로, 아무도 황소를 고르지 않았으면 **황소 에셋(178 KB)을 받지도 않는다.**
- 그룹 순서는 모델 번호 오름차순으로 고정한다. 드나들 때 순서가 바뀌면 React 가 `InstancedMesh` 를 다시 만든다.
- 그룹마다 `Suspense` 로 감싼다. 새 모델이 로드되는 동안 씬 전체가 사라지지 않게 한다.
- 세 모델이 섞이면 드로우 콜은 4 → 12 다. 예산(50) 안이고, 삼각형은 섞인 비율에 따라 62k~98.6k 사이다.
- 개발용 더미(`?dummies=50`)는 모델을 번갈아 준다. 한 모델만 띄우면 모델이 둘일 때의 비용을 측정에서 놓친다.

##### 원본을 그대로 쓸 수 없는 이유

원본은 부위마다 메시가 따로 있어 **아바타 한 명에 드로우 콜 94개**가 든다. 50명이면 4,700 콜로 예산(50)의 94배다. 가공 스크립트가 세 가지를 바꾼다.

1. **메시 병합** — 94개를 먼저 몸통·앞판 2개로 합친다. 이후 검은 눈동자만 분리해 소프트 버전의 색상·발광 마스크를 옮긴다. 흰자는 원본 그대로 둔다.
2. **스킨 제거 + 본 행렬 베이크** — `InstancedMesh` 는 스키닝을 못 한다. 지오메트리는 레스트 포즈로 굳히고, Walk 한 사이클의 본 스키닝 행렬을 따로 구워 셰이더가 읽게 한다(§아래).
3. **스튜디오 바닥 제외** — `.blend` 에는 200 x 200 m 바닥과 조명·카메라가 함께 있다. 타입만 보고 고르면 바닥이 아바타마다 딸려 간다. **리그에 묶인 메시만** 캐릭터로 본다.
4. **180° 회전** — 원본은 `+Z` 를 본다. 프로젝트 규약(`-Z`)에 맞춰야 `yaw` 를 그대로 쓸 수 있다. `mesh.transform` 으로 정점과 법선을 함께 돌린다. `transform_apply` 오퍼레이터는 백그라운드 실행에서 선택 상태를 타므로 쓰지 않는다.

##### 플레이어 색은 앞치마 앞판에만

유니폼이 고정색이면 50명이 모두 같아 보여 §2 의 "명찰 범위(25 m) 밖에서는 색만으로 구분한다"가 깨진다.

**아틀라스의 앞치마 색은 `#18171a`(밝기 13%)라 텍스처에 `instanceColor` 를 곱하면 검게 남는다.** 그래서 앞치마 전체가 아니라 **앞판 두 장만** 떼어 텍스처 없는 단색 머티리얼로 그린다. 주머니·끈·빨간 트림은 몸통에 남아 텍스처를 유지한다. 앞판은 0.385 × 0.383 m 로 먼 거리 식별에 충분하다.

##### 걷기 모션: 본 행렬 텍스처

`InstancedMesh` 는 스키닝을 못 해 three 의 스킨 경로를 쓸 수 없다. 대신 Walk 한 사이클의 **본 스키닝 행렬을 미리 구워** 셰이더가 직접 읽는다.

| 항목 | 값 |
| --- | --- |
| 자료 | `crew-walk.bin` — Float32, `[프레임][본][행렬 위 3행]` |
| 크기 | 40 프레임 x 22 본 x 12 float = **41 KB** |
| 텍스처 | `DataTexture` RGBA Float, 66 x 40, `NEAREST` |
| 정점 속성 | `_BONEINDEX` (glTF) → `_boneindex` (three) |
| 인스턴스 속성 | `aWalkPhase`(0~1), `aWalkBlend`(0~1) |

**정점 하나가 본 하나에 100% 묶여 있어서**(리지드 바인딩, 정점 960개 전수 확인) 행렬을 한 번만 곱하면 된다. 정점 위치를 통째로 굽는 VAT 보다 자료가 훨씬 작다.

사이클은 **시간이 아니라 걸은 거리**로 돌린다. 시간 기준이면 속도가 바뀔 때 발이 미끄러진다. `metersPerCycle` 은 실제 보폭(약 0.52 m x 2 걸음)보다 길게 잡았는데, 보폭 그대로 쓰면 이동 속도 4.5 m/s 에서 초당 4.3 사이클이 되어 다리가 과하게 빨라진다. 약간의 미끄러짐과 읽히는 속도를 맞바꾼 값이다.

멈추면 `aWalkBlend` 를 0 으로 당겨 **레스트 포즈**로 돌아간다. `Idle` 클립은 전 본 0° 로 움직임이 없어서, 서 있는 자세는 모델 그대로가 정답이다.

프레임은 두 장을 선형 보간해 읽는다. 40 프레임을 1.67초에 재생하면 24 fps 라 끊어 쓰면 다리가 덜컥거린다.

##### 내보내기에서 애니메이션이 사라지는 함정

`.blend` 에 멀쩡한 Walk 가 있어도 glTF 로 내보내면 **키프레임 2개만 남는 일**이 있다. 루프 애니메이션은 첫·끝 포즈가 같아서, 그러면 정지한 것처럼 보인다.

원인은 익스포터의 키프레임 최적화다. 내보낼 때 `export_force_sampling=True`, `export_optimize_animation_size=False` 를 줘야 매 프레임이 남는다. 가공 스크립트는 `.glb` 가 아니라 `.blend` 에서 직접 행렬을 구우므로 이 함정을 아예 피한다.

##### 아틀라스 필터

샘플러의 확대 필터는 `NEAREST`(9728)다. `LINEAR` 로 바뀌면 픽셀 아트가 뭉개진다. 머티리얼을 직접 만들지 않고 glTF 가 만든 것을 그대로 쓰는 이유다.

##### 프러스텀 컬링을 끈 이유

아바타 `InstancedMesh` 에는 **`frustumCulled={false}` 가 필수다.**

three 는 `InstancedMesh` 의 바운딩 스피어를 `boundingSphere === null` 일 때만 계산하고, 인스턴스가 움직여도 다시 계산하지 않는다. 그래서 두 가지가 생긴다.

1. 접속자가 없을 때(`count` 0) 첫 컬링 검사가 돌면 **빈 구(반지름 -1)** 로 굳는다. 이후 들어온 아바타가 통째로 사라진다.
2. 굳은 구는 아바타가 걸어 나가도 따라가지 않는다.

굳은 빈 구는 중심이 원점이라 컬링 통과 여부가 "원점이 화면에 들어오는지"로 갈린다. 증상이 **가끔** 나타나는 이유다. 명찰·말풍선은 DOM(`<Html>`)이라 컬링과 무관하게 보이므로 **사람은 투명한데 닉네임만 뜨는** 상태가 된다.

월드는 40 × 32 m 이고 아바타 50명이 드로우 콜 4개에 담긴다. 컬링으로 아낄 것이 없다. `avatarCulling.frustum.test.ts` 가 three 의 이 동작을 고정하므로, 상류에서 고쳐지면 테스트가 깨져 알려 준다.

##### 공유 지오메트리 해제 방지

GLTF 지오메트리·머티리얼을 쓰는 메시에는 **`dispose={null}` 이 필수다.** r3f 는 언마운트 때 객체의 모든 속성을 훑어 `dispose()` 를 부르는데, 그러면 `useGLTF` 캐시가 들고 있는 공유 자원이 해제되어 `/space` 에 다시 들어왔을 때 아바타가 사라진다.

로딩은 `<Canvas>` 가 children 을 `Suspense` 로 감싸므로 별도 경계가 필요 없다. `useGLTF.preload` 로 라우트 진입과 함께 받아둔다.

##### 모델을 바꿀 때

기본 가공으로 `crew.glb` 를 재생성한 뒤 `python3 scripts/blender/apply-laser-eyes-to-crew.py` 를 실행한다. 소프트 버전의 편집 원본은 `assets/avatars/voxel-crew-laser-eyes-soft.blend` 이고, 스크립트는 함께 보관한 `.glb` 에서 검은 눈동자의 UV·색상·발광 마스크를 가져온다. 흰자와 눈동자 형상, 걷기 동작은 원본 그대로이며 눈 주변 번짐 효과는 사용하지 않는다.

`crewModel.test.ts` 가 `.glb` 를 직접 파싱해 메시 개수·이름·삼각형 예산·원점·전방·아틀라스 필터를 고정한다. 가공 스크립트가 출력하는 `[anchor] headCenterY` 값은 명찰·말풍선이 매달리는 높이이므로 `SPACE_AVATAR.headCenterY` 에 옮겨 적는다.

##### 삼각형 예산을 60k → 80k 로 올린 이유

60k 는 아바타가 캡슐+구 프리미티브(1인 226 tri, 50명 11,300)이던 시절의 값이고, 복셀 모델로 바꾸면서 아바타만 62,100 이 됐다. 아바타 밖 씬은 바닥·전광판·현황판·벽 부품·펄스 링을 다 합쳐 **약 1,000 tri** 로 무시할 수준이라, 60k 중 48k 가 쓰이지 않고 남아 있던 셈이다.

실질 병목은 삼각형이 아니라 **드로우 콜**이다. 50명을 콜 3개에 담고 있고 예산은 50 이다. 모바일 GPU 가 62k 삼각형을 한 프레임에 그리는 것 자체는 문제가 되지 않는다. 80k 는 아바타 62k + 씬 1k 에 헤드룸을 둔 값이다.

원격 아바타는 개별 `<mesh>` 로 만들지 않는다. 50명이면 몸통·앞판·그림자로 **150 드로우 콜**이 되어 바닥·전광판·현황판·조명까지 올라간 모바일 씬에서 예산을 세 배 넘게 초과한다. `InstancedMesh` 3개로 고정하고, 슬롯 인덱스 0~49 를 플레이어에 배정한다. 빈 슬롯은 `count` 를 줄여 숨긴다.

명찰과 말풍선은 `<Html>` DOM 이라 개수가 곧 레이아웃 비용이다. 거리순 선별은 `avatarCulling.ts` 의 순수 함수로 분리해 테스트한다.

`/space` 외 라우트의 번들 크기가 변하지 않아야 한다.

### 8.0 렌더 해상도

모바일 기기는 `devicePixelRatio` 가 3 인데 캔버스를 1.5 로 그리면 **기기 해상도의 50%** 다. 같은 화면의 DOM HUD 는 3 으로 또렷하게 나오므로 나란히 두면 캔버스만 흐려 보인다.

393×852 CSS px, 기기 dpr 3 을 예로 들면 다음과 같다. 패널·글자의 실제 화면 크기는 스폰 위치와 카메라 거리에 따라 달라진다.

| 렌더 dpr | 캔버스 해상도 | 기기 대비 선형 해상도 |
| --- | --- | --- |
| 1.5 | 약 590×1278 | 50% |
| 2.0 | 786×1704 | 67% |
| 3.0 | 1179×2556 | 100% (현재 상한 밖) |

1.5 로 시작해 `PerformanceMonitor` 의 측정값에 따라 `[1, 2]` 사이를 오간다. 처음부터 최대로 올리면 약한 기기의 첫인상이 끊기고, 고정하면 기기 편차를 감당할 수 없다. 해상도는 0.25 단위로 끊는다. 미세하게 계속 바뀌면 화면이 들썩인다.

캔버스 텍스처에는 **이방성 필터를 최대로** 올린다. 기본값 1 로 두면 비스듬히 볼 때 글자가 뭉개진다.

### 8.1 번들 측정 결과 (2026-10-31)

**초기 기록(v0.4)**: 아래는 당시의 단일 three 포함 청크와 라우트 참조 검사 결과다. 이후 변경을 포함한 최신 기본 빌드 결과로 취급하지 않는다.

| 항목 | 측정값 |
| --- | --- |
| three 포함 청크 | 936 KB(비압축) / **246 KB(gzip)** |
| 이 청크를 참조하는 라우트 | `/space` 만 (`react-loadable-manifest`) |
| 전 라우트 초기 HTML 참조 | 0건 (24개 프리렌더 HTML 검사) |
| 공용 `rootMainFiles` | 429 KB(비압축), three 도입 전후 변화 없음 |

초기 검사에서는 three 청크가 `/space` 의 캔버스 마운트 때만 로드되고 공용 번들·초기 HTML 에는 포함되지 않았다. 당시 gzip 목표를 200 KB 에서 260 KB 로 바꾼 근거는 `<Canvas>` 내부의 `extend(THREE)` 가 THREE 네임스페이스를 JSX 카탈로그에 등록한다는 점과 246 KB 단일 청크 측정값이었다. `createRoot` 와 제한된 `extend` 목록으로 전환하는 최적화는 리사이즈·이벤트·컨텍스트 브리지를 직접 관리해야 해 1단계에 도입하지 않았다.

**현재 변경분의 빌드 확인**:

| 실행 | 결과 |
| --- | --- |
| `pnpm build` (기본 Turbopack) | 컴파일 단계에서 수분 동안 추가 출력이 없어 중단. 완료 여부·최신 청크 크기 미확인 |
| `pnpm exec next build --webpack` | 컴파일 16.6초·TypeScript 검사 2.5초 성공. 이후 `/cagr` 의 blockchain.com 2026년 시세 조회가 `fetch failed` 로 끝나 프리렌더 실패 |
| `pnpm exec next build --webpack --experimental-build-mode compile` | v0.23 코드 컴파일 10.3초·페이지 데이터 수집·트레이스 생성 성공. 정적 페이지 생성은 별도 단계이므로 전체 빌드 완료와 구분 |
| v0.23 webpack compile 산출물의 `SpaceCanvas` 비동기 청크 | `react-loadable-manifest` 기준 9개 파일 합계 1,051,689 B(비압축), 289,995 B(gzip, **283.2 KiB**) |

이번 webpack 수치는 **SpaceCanvas 비동기 청크 9개의 합**이고 이전 246 KB 는 **three 포함 단일 청크** 기록이다. 측정 범위와 번들러 조건이 다르므로 증가량을 직접 비교하거나 gzip 260 KB 목표를 최신 코드에서 달성했다고 판단하지 않는다. webpack 수치는 컴파일 산출물의 참고값이며 성공한 전체 프로덕션 빌드 결과가 아니다. 외부 시세 조회가 가능한 환경에서 전체 빌드를 완료하고, 기본 Turbopack의 라우트·공용 청크 참조와 같은 범위의 gzip 크기를 다시 측정해야 한다.

### 8.2 렌더 성능 실측 (미측정 — 실행 환경 차단)

개발용 계측 코드는 추가했지만 실제 브라우저 수치는 아직 없다. 2026-10-31 검증 환경에서 Chromium 실행은 macOS sandbox의 MachPort 권한 오류로 차단됐고, 연결 가능한 Chrome·인앱 브라우저도 확보하지 못했다. 이 상태를 성능 검증 완료로 취급하지 않는다.

재현 절차:

1. `pnpm dev` 로 개발 서버를 띄우고 `http://localhost:3002/space?dummies=50&stats=1` 을 연다. 운영 환경에서는 더미와 계측 패널이 비활성화된다.
2. 원격 더미 50명과 로컬 아바타 1명이 함께 렌더되는지 확인한다. 50명 목표보다 로컬 1명을 더한 상태로 여유를 측정한다.
3. 탭을 활성 상태로 유지한다. 셰이더·텍스처 준비 5초를 제외하고 10초 동안 표본을 모아 화면에 `측정 완료` 가 표시될 때까지 기다린다. 새로고침이나 탭 가시성 변경은 측정을 초기화한다.
4. 평균 FPS, 프레임 시간 p95, 최대 드로우 콜·삼각형 수, dpr 범위를 기록한다. 기기·브라우저·뷰포트·그림자 설정도 남기고 실제 중급 모바일 기기에서 같은 절차를 반복한다.

`SpacePerformanceStats` 는 `useFrame` 이후의 `addAfterEffect` 에서 `renderer.info.render.calls`·`triangles` 를 읽는다. 현재 씬의 프레임당 render 1회 기준으로 그림자 패스를 포함한 렌더 값을 수집한다. 요약값은 패널의 `data-space-performance` 속성에도 남긴다. 모바일 뷰포트 에뮬레이션은 실제 중급 모바일 기기의 GPU 성능 검증을 대신하지 않는다.

| 측정 환경 | 뷰포트 / dpr 범위 | 원격 / 로컬 | FPS / p95 | 최대 드로우 콜 | 최대 삼각형 | 판정 |
| --- | --- | --- | --- | --- | --- | --- |
| 데스크톱 브라우저 | 미측정 | 50 / 1 | 미측정 | 미측정 | 미측정 | 실행 환경 차단 |
| 중급 모바일 실제 기기 | 미측정 | 50 / 1 | 미측정 | 미측정 | 미측정 | 실기기 확인 대기 |

번들 수치(§8.1)와 geometry 계산값(§8)은 렌더 성능 실측과 구분한다. 실측과 필요한 기기 검증이 끝나기 전에는 작업 `1-20` 을 완료로 바꾸지 않는다.

## 9. HUD

캔버스 위에 떠 있는 2D 레이어다. 상태와 조작을 DOM 으로 제공한다. 캔버스 안 텍스트에만 의존하면 확대·스크린리더·WebGL 실패 상황에서 모두 읽히지 않는다.

| 위치 | 내용 |
| --- | --- |
| 좌측 상단 | 접속 표시 (상태 점 + 문구) |
| 우측 상단 | 버튼 묶음 (세로로 쌓임) + 조작 안내 패널 |
| 좌측 하단 | 채팅 버튼 (손가락 기기 전용) |
| 하단 중앙 | 가상 조이스틱 (손가락 기기 전용) |
| 하단 우측 | 점프 버튼 (손가락 기기 전용) |

**손가락 기기에서는 채팅 버튼만 좌측 하단으로 내린다.** 우측 상단은 엄지에서 가장 먼 자리인데, 채팅은 이 화면에서 가장 자주 누르는 버튼이다. 조이스틱 반대쪽(좌 1.5 rem)에 두어 점프 버튼(우 1.5 rem)과 좌우 대칭을 이루고, 두 버튼의 아랫변을 같은 높이(4.5 rem)에 맞춘다. 마우스 환경에서는 커서가 어디든 같은 비용이라 묶음을 쪼개지 않는다.

버튼 모양·배지·접근성 처리는 `SpaceActionBar` 한 곳에 둔다. 좌측 하단 버튼도 같은 컴포넌트를 쓰고 `align` 만 다르다. 채팅 패널이 열리면 조이스틱·점프와 함께 내려간다 — 하단 시트가 덮는 자리라 남겨 두면 눌리지 않는 버튼이 된다.
| 그 외 전체 | 시야 회전·줌 (캔버스가 직접 처리) |

전체 화면 페이지라 브라우저가 노치를 대신 비켜주지 않는다. HUD 전체를 `safe-area-inset` 만큼 안쪽으로 들인다.

### 9.0 모바일 조작

조이스틱은 **하단 중앙에 고정**하고, 차지하는 면적을 제 크기(지름 120 px)로 제한한다. 나머지 화면 전체가 캔버스의 시야 회전·줌 영역이다.

넓은 터치 영역을 두는 방식(화면 왼쪽 절반을 이동 영역으로 쓰는 모바일 게임 표준 배치)을 먼저 시도했다가 되돌렸다. 그 영역이 캔버스를 덮어 **왼쪽 절반에서 시야 드래그와 두 손가락 줌이 동작하지 않았다**. 조작 영역을 나누는 대신 조이스틱을 작게 두는 쪽이 이 화면에는 맞는다.

같은 이유로 HUD 에서 터치를 받는 요소는 **버튼과 조이스틱뿐**이다. 접속 표시와 조작 안내 패널은 읽기 전용이라 `pointer-events: none` 으로 통과시킨다.

손가락 기기는 카메라를 **최대 거리(18 m)에서 시작**한다. 세로로 긴 화면은 세로 시야가 넓고 가로가 좁다. 가까이 붙으면 전광판은 커지지만 위아래가 잘려 전광판 위 텍스트 배너까지 한 화면에 들어오지 않는다. 물러나면 벽면 전체가 잡힌다. 시작값일 뿐이라 핀치로 다가갈 수 있다.

| 카메라 거리 | 카메라→벽 | 아이폰 세로 전광판 점유 | 스폰 중심 가시 상단 |
| --- | --- | --- | --- |
| 5 (최소) | 22.9 m | 93% | 약 9.1 m — 배너(10.0) 잘림 |
| 11 (기본) | 28.8 m | 74% | 약 12.0 m |
| 18 (손가락 기기 시작) | 35.6 m | 60% | 약 15.4 m |

위 표는 스폰 중심·기본 피치에서 축소 전 전광판 **프레임(10.2 m)** 의 점유율과 가시 상단을 계산한 예시다. §6.4의 축소 가드도 텍스트 배너(9.6 m)보다 넓은 이 프레임을 기준으로 삼는다.

띄울지·가까이 붙일지는 화면 폭이 아니라 `(pointer: coarse)` 로 판단한다. 폭으로 가르면 세로로 세운 태블릿(820 px)이 데스크톱으로 분류된다. 첫 렌더에서 동기로 읽어 시작 거리가 한 박자 늦게 바뀌지 않게 한다.

### 9.0.1 제스처 해석

| 입력 | 동작 |
| --- | --- |
| 손가락 하나 — 좌우 | yaw (시야 좌우 회전) |
| 손가락 하나 — 상하 | 피치 (시야 상하 조절) |
| 손가락 둘 | 줌. 사이 거리 변화만 쓴다 |
| 휠 | 줌 (데스크톱) |

손가락이 둘일 때는 시야 회전이 일어나지 않는다. 그때의 이동은 줌 제스처의 일부라 시야까지 같이 돌면 조작이 뒤섞인다.

핀치는 **프레임마다 한 번만** 두 손가락 사이 거리를 비교한다. 포인터 이벤트는 손가락마다 따로 오므로 이벤트마다 비교하면, 두 손가락을 나란히 끌어도 한쪽만 움직인 중간 상태에서 거리가 변해 줌이 걸린다. 프레임 시점에는 두 손가락의 최신 위치가 모두 반영돼 있어 나란한 이동이 정확히 상쇄된다.

손가락이 닿아 있는 동안 들어오는 휠 이벤트는 흘려보낸다. 일부 브라우저가 두 손가락 팬에서 휠을 합성해 보내는데, 핀치와 겹쳐 두 배로 줌이 걸린다.

제스처 해석은 `pointerGesture.ts` 의 순수 함수로 분리해 테스트로 고정한다. 이벤트 핸들러 안에 두었을 때 줌·회전 방향이 뒤섞이는 문제가 반복됐다.

### 9.0.2 점프 버튼

| 항목 | 값 |
| --- | --- |
| 위치 | 하단 우측. `right: 1.5rem + safe-area`, `bottom: 4.5rem + safe-area` |
| 크기 | 지름 72 px |
| 입력 | `pointerdown` 에 누름, `pointerup`·`pointercancel`·캡처 상실에 해제 |
| 쓰는 채널 | `inputSource.joystick.isJumping` |

조이스틱이 하단 중앙이라 점프는 **반대쪽 엄지**가 닿는 자리에 둔다. 한 손으로 이동과 점프를 같이 눌러야 하면 조이스틱에서 엄지를 떼게 된다.

조이스틱과 같은 `joystick` 채널을 쓰지만 건드리는 필드가 `isJumping` 하나뿐이라 두 입력이 서로 값을 덮지 않는다. 조이스틱의 초기화 경로도 `forward`·`strafe`·`isRunning` 만 비운다. 채널을 더 쪼개면 `resolveMergedMovementInput` 의 합산 대상이 늘어나는데, 손가락 입력끼리는 겹치는 필드가 없어 그럴 이유가 없다.

누름 상태는 프레임 루프가 매 프레임 읽으므로 React 상태로 들지 않는다. 눌린 모양만 상태로 둔다. 손가락이 버튼 밖으로 미끄러져도 떼는 순간을 받도록 `setPointerCapture` 로 잡고, 창 이탈·탭 전환·언마운트에서는 눌린 점프를 비운다. 조이스틱과 같은 조건(채팅·닉네임 입력 중)에 함께 내린다.

데스크톱에는 띄우지 않는다. `Space` 가 있고, 마우스로 버튼을 누른 채 WASD 를 쓰는 조작은 없다.

### 9.1 접속 표시

숫자만 띄우면 서버 미설정·접속 실패 중에도 접속자가 있는 것처럼 읽힌다. 상태를 함께 들고 다니며 문구 자체를 바꾼다.

| 상태 | 문구 | 점 |
| --- | --- | --- |
| `online` | `12 / 50` | 초록 |
| `connecting` | 연결 중 | 오렌지, 깜빡임 |
| `offline` | 오프라인 | 회색 |

`SpaceRoom`의 입장 완료·연결·단절 상태를 표시한다. 서버 미설정과 개발 더미 모드도 `offline`이다. 채팅창이 닫혀 있어도 오류 사유와 수동 재접속 버튼을 표시한다.

### 9.2 버튼 묶음

버튼이 늘어나도 배치·크기·접근성 처리를 각자 다시 쓰지 않도록, 모양은 `SpaceActionBar` 에서만 정의한다. 추가할 때는 `SpaceHudAction` 을 만족하는 항목을 배열에 넣는다.

```ts
interface SpaceHudAction {
  id: string;
  label: string;        // 스크린리더 이름이자 툴팁. 아이콘만으로는 뜻이 안 전달된다
  icon: ReactNode;
  isActive?: boolean;   // 토글 버튼이 켜진 상태
  isDisabled?: boolean;
  badgeCount?: number;  // 읽지 않은 수 등. 0 이면 표시하지 않음
  onClick: () => void;
}
```

현재 버튼:

| 버튼 | 동작 | 비고 |
| --- | --- | --- |
| 뒤로 가기 | `router.back()` | 히스토리가 없으면 `/orange` 로 보냄 |
| 공간 채팅 | 대화창 토글 | 닫힌 동안 안 읽은 메시지 배지 |
| 조작 안내 | 안내 패널 토글 | 데스크톱·모바일 조작을 함께 적음 |

설정·소리 버튼은 후속 확장 시 같은 배열에 추가한다.

전체 화면 버튼은 제거했다. iOS 사파리는 Fullscreen API 를 지원하지 않아 그 환경에서는 버튼이 아예 없었고, 브라우저 자체 전체 화면과 중복이었다.

### 9.3 접근성·폴백

- WebGL 컨텍스트 생성 실패 시 `SpaceFallback` 을 띄우고 `/overview` 로 가는 링크를 제공한다.
- `webglcontextlost` 이벤트를 받아 복구를 시도하고, 실패 시 폴백으로 전환한다.
- 키보드만으로 이동과 시야 회전이 모두 가능해야 한다(드래그 없이 `Q`/`E` 로 yaw).
- yaw 가 커지면 시야는 **왼쪽**으로 돈다(전방 `(-sin θ, -cos θ)` 가 `-Z` 에서 `-X` 로 간다). 따라서 왼쪽 키가 양수다. 이 부호는 `followCamera.test.ts` 에서 고정한다.
- 아이콘 버튼은 모두 `aria-label` 을 가지고, 토글 버튼은 `aria-pressed` 를 함께 준다.
- `prefers-reduced-motion` 은 §5 대로 처리한다.
- 입장 상한 초과 시 "지금은 빈자리가 없어요" 안내와 재시도 버튼을 보여준다.

## 11. 2단계 구현 — 위치 동기화와 공간 채팅

`workers/chat/src/SpaceRoom.ts`와 `features/space-session`을 연결했다. 기존 전체 채팅의 `ChatRoom`과는 별도 방이며, `/space`는 일반 브라우저와 PWA 모두 이용한다. `NEXT_PUBLIC_CHAT_WS_URL`의 호스트를 그대로 쓰고 경로만 `/v1/space/ws`로 바꾸므로 새 프런트 환경변수는 필요 없다. Worker 배포가 선행돼야 운영 연결이 된다.

### 11.1 전송·렌더 구조

| 항목 | 구현 |
| --- | --- |
| 위치 상향 | JSON `move`, 좌표·회전이 바뀔 때만 최대 10 Hz |
| 서버 전송 | 이동이 들어오면 100 ms 고정 틱으로 변경 좌석만 모아 전원에게 전송. 타임스탬프는 예정 틱 시각. 멈춘 뒤 빈 꼬리 틱 2개를 더 보내고 끔 |
| 바이너리 헤더 | 버전 uint8 + 종류 uint8 + 인원 uint16 LE + 서버 시각 uint32 LE = 8 B |
| 플레이어 레코드 | 좌석 uint8 + x/z int16 LE(0.01 m) + yaw uint8 + 달리기 플래그 uint8 = 7 B |
| 최대 위치 페이로드 | 50명 동시 변경 시 358 B/회, 최대 10 Hz 기준 약 3.5 KB/s/수신자(프레임 헤더 제외) |
| 직렬화 | 전송 배치당 1회, 같은 버퍼를 전원에게 공유 |
| 원격 렌더 | 서버 시각 기준 지연 보간(2칸 + 지터, 200~300 ms, 재생 속도 5% 안에서 조정), 최단 회전 경로, 스트림 전체가 끊겼을 때만 최대 120 ms 감속 외삽 |
| 상태 갱신 | 좌표는 가변 객체에서 처리. 입퇴장·메시지·접속 상태만 React 구독에 반영 |

거리 기반 전송 AOI는 두지 않는다. 렌더 시에는 기존의 50 슬롯 인스턴싱과 명찰·말풍선 거리/개수 제한을 적용한다. 희소 스냅샷에서 빠진 좌석은 이전 위치를 유지하며 `leave`만 퇴장으로 처리한다. 순서가 뒤집힌 스냅샷을 버리고 32비트 시각의 순환을 처리한다. 개발용 `?dummies=N` 측정 중에는 실제 공간 연결을 열지 않는다.

### 11.2 서버와 비용 관리

- Worker의 기존 Origin 검사·IP 프리픽스 해시·업그레이드 rate limiter를 재사용한다. limiter key에 경로를 포함해 전체 채팅과 공간의 접속 횟수를 구분한다.
- `SPACE_ROOM` 바인딩과 `v2` 마이그레이션을 추가하고 **SQLite-backed DO**로 등록한다. SQLite 등록은 저장 방식의 선택이며, 위치나 채팅 본문을 SQL에 쓰지 않는다. Free 플랜도 SQLite-backed DO를 지원한다([Cloudflare 요금 문서](https://developers.cloudflare.com/durable-objects/platform/pricing/)).
- 50석, 입장 대기 연결 최대 10개, 전체 소켓 최대 60개. **IP guard 키당 연결은 운영에서 2개**다. 1개였을 때는 재접속이 자기 자신의 죽은 소켓에 막혔다 — 모바일 백그라운드 복귀나 네트워크 전환처럼 서버가 FIN을 못 받는 끊김에서는 유령 소켓이 `STALE_CONNECTION_MS` 동안 슬롯을 들고 있어 재접속이 60초 내내 429를 맞고, 그 429가 업그레이드 리미터까지 포화시켜 장애가 분 단위로 늘어났다. 좌석 중복은 이 숫자가 아니라 입장 때의 `stableActorKey` 교체가 막는다. 로컬 Worker(`localhost`/`127.0.0.1`)에서만 `.dev.vars` 의 `SPACE_DISABLE_IP_CONNECTION_LIMIT=true` 로 제한을 해제해 한 기기에서 여러 창을 띄워 검증한다(`lib/spaceConnectionLimit.ts`). 입장 프레임은 10초 내에 보내야 한다. 서버가 좌석·색·스폰을 결정한다.
- 같은 사용자 키로 다시 입장하면 기존 좌석과 위치를 새 소켓으로 넘기고 이전 탭을 종료한다. 이전 소켓의 지연 close가 새 좌석을 제거하지 않도록 소유권을 확인한다. 하이버네이션 이후 close에서 종료 메타데이터까지 사라진 경우에는 살아 있는 로스터를 다시 보내 유령 아바타를 제거한다.
- 클라이언트는 15초마다 raw `ping`을 보내고 런타임 auto-response가 `pong`으로 답한다. 이 응답은 DO를 깨우지 않는다. 클라이언트는 45초 무응답 시 재연결하고, 서버는 실제 이벤트가 있을 때 auto-response 시각까지 확인해 60초 이상 비활성 연결을 정리한다.
- **상시 10 Hz 루프나 주기적인 SQL 쓰기가 없다.** 이동이 없으면 배치 타이머도 없으므로, 사람이 접속해 있어도 유휴 상태에서는 하이버네이션 조건을 만족한다. 런타임이 객체를 다시 생성할 때 WebSocket attachment에서 좌석·위치를 복원한다([WebSocket 하이버네이션](https://developers.cloudflare.com/durable-objects/best-practices/websockets/), [수명주기와 타이머 조건](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)).
- 프레임 크기·초당 입력 수·유한 좌표·월드 경계·이동 거리 예산을 서버에서 검증한다. 잘못된 이동에는 서버 좌표를 다시 보내 클라이언트를 보정한다.

위 구조는 불필요한 요청과 실행 시간을 줄이는 구현이며 무료 운영을 보장하지 않는다. 실제 요금은 전체 계정 사용량·활동 인원·이동 빈도·접속 시간에 따라 달라진다.

### 11.3 실제 프로토콜

공유 타입·파서는 `entities/space/model/spaceProtocol.ts`, 바이너리 코덱은 `lib/spaceSnapshot.ts`에 둔다. 버전은 `v: 1`이다. 클라이언트는 텍스트 JSON을 보내고 서버 위치 배치만 바이너리다.

| 방향 | 타입 | 내용 |
| --- | --- | --- |
| C→S | `join` | 기존 채팅과 공유하는 `clientKey`, `nickname` |
| C→S | `move` | `x`, `z`, `yaw`, `isRunning` |
| C→S | `say` | UUID `rid`, `body` |
| S→C | `welcome` | 자기 `self`와 자신을 제외한 `peers` |
| S→C | `peer` | 신규 입장·메타데이터·자기 위치 보정 |
| S→C | 바이너리 배치 | 변경된 좌석들의 좌표와 회전 |
| S→C | `leave` | 반납 좌석 |
| S→C | `say` | 메시지 ID·rid·좌석·닉네임·본문·서버 시각 |
| S→C | `error` / `full` | 오류 또는 정원 초과 |
| C→S | `kick` | 찰 좌석 `target`(없으면 허공). `features` 에 `kick` 을 알린 경우만 보냄 |
| S→C | `kick` | `from`·`to`(없으면 허공)·단위 방향 `dirX/dirZ`. 발차기를 아는 클라이언트에만 보냄 |

소켓 세대 번호로 끊긴 연결의 늦은 이벤트를 무시한다. 연결 실패에는 지터가 있는 지수 백오프(최대 30초)를 적용한다. 방이 가득 차거나 다른 탭으로 교체된 경우 자동 재시도를 중단하고 HUD에서 수동 재연결한다. 브라우저가 숨겨지면 위치 전송과 재시도는 쉬며, 복귀 시 최신 상태를 전송하거나 끊긴 연결을 복구한다.

### 11.4 채팅 UI와 말풍선

- HUD의 채팅 버튼으로 대화창을 열고 닫으며, 닫힌 동안 도착한 메시지는 숫자 배지로 표시한다. 데스크톱에서는 `Enter` 로도 열고 바로 입력칸에 포커스한다(열려 있으면 입력칸으로 되돌린다). 손가락 기기에는 물리 키보드가 없고 자판이 화면 절반을 덮으므로 단축키와 자동 포커스를 모두 적용하지 않는다. 입력창·버튼에 포커스가 있을 때는 `Enter` 를 흘려보낸다 — 글자를 치는 중이면 그 키는 입력창 몫이고, 버튼이면 브라우저가 기본 활성화를 처리한다. 판별은 `shouldIgnoreSpaceHotkey` 한 곳에서만 한다. 이 페이지에서 받은 최근 100개만 메모리에 유지하고 과거 메시지를 서버에서 조회하지 않는다.
- 닉네임과 본문은 기존 `textValidation.ts`로 정규화한다. 입력창도 같은 100 grapheme 에서 더 받지 않아, 서버가 거절할 글자를 치게 두지 않는다(`SPACE_CHAT_MAX_GRAPHEMES` 공유). 공간 채팅 본문은 최대 100 grapheme, 3초에 한 번, 링크·연락처 제한과 선정성 필터를 적용한다. 별도 Turnstile 인증이나 기존 전체 채팅의 관리자 차단 상태는 공간에 연동하지 않았다.
- 서버가 자기 발화를 echo해야 전송 성공으로 처리해 입력을 비운다. 오류·타임아웃에는 입력을 남긴다. 서버는 최근 32개의 요청 ID와 본문 해시를 attachment에 두고 같은 요청 ID의 중복 방송을 막는다. 이 보장은 하이버네이션·기존 연결 교체까지 유지되며, 연결이 완전히 종료된 뒤의 새 세션에는 이어지지 않는다. 프런트는 발화를 자동 재전송하지 않는다. 채팅 본문은 attachment에 저장하지 않는다.
- 캐릭터 위 말풍선은 로컬 수신 시각부터 5초, 25 m 이내 가까운 12명까지 표시한다. 한 좌석은 최신 발화 하나만 표시한다. **본인 말풍선과 명찰도 함께 표시한다** — 자기 발화가 남들에게 어떻게 보이는지 확인할 수 없으면 거리·TTL 감각을 잡을 수 없다. 본인 말풍선은 좌석 좌표가 아니라 매 프레임 로컬 변환을 따라간다. 말풍선 위에는 작성자 닉네임을 한 줄로 덧붙여, 가까운 사람이 여럿일 때 누구 말인지 구분한다. DOM 말풍선에는 입력 이벤트가 잡히지 않으며 작성자 닉네임과 본문은 일반 텍스트로 렌더한다.
- 명찰은 퇴장한 좌석을 **다음 선별 주기(200 ms)를 기다리지 않고 즉시** 렌더 목록에서 뺀다. 고정 길이 슬롯 풀에 좌석을 배정하던 방식에서는 로스터에 없는 좌석이 한 주기 동안 남아 유령 명찰이 보였다. 좌석별 `Map` 으로 바꿔 선별 결과와 로스터를 교차해 렌더한다.
- **명찰 거리 상한은 36 m 다.** 25 m 로 뒀더니 스폰 직후 서로 이름이 안 보이는 경우가 생겼다 — 스폰 링 반지름이 최대 14 m 라 두 사람이 링 양쪽에 떨어지면 28 m 이고, 각도차 150° 부터 상한을 넘긴다. 접속만 하고 가만히 있으면 상대 이름을 못 보는 상태가 된다. DOM 비용을 정하는 것은 거리가 아니라 **개수 상한(16)** 이므로 거리를 늘려도 노드 수는 그대로다. 링 지름에 여유를 더한 값으로 올렸고, 이 불변식은 `spaceWorld.test.ts` 에서 고정한다.
- 새로 보이게 된 좌석의 `<group>` 은 **ref 가 붙는 순간 제자리로 보낸다.** 원점에서 마운트되면 `<Html>` 이 그 프레임에 이미 화면 좌표를 계산해, 명찰이 공간 중앙에서 한 번 깜빡인다.
- 이름이 빈 문자열이면 명찰을 그리지 않는다. 글자 없는 검은 알약만 뜬다.
- 손가락 기기에서는 명찰 `distanceFactor` 를 18 → 12 로 낮춘다. 같은 값이면 좁은 화면에서 글자가 너무 작아 닉네임을 읽을 수 없다. `(pointer: coarse)` 판정을 명찰까지 내려보낸다.
- 입력창·버튼·키보드로 스크롤 중인 채팅 로그에서는 WASD·방향키·Q/E를 이동으로 처리하지 않는다. 입력 포커스·창 이탈·탭 전환 시 눌린 키를 비우고, 채팅 포커스 중 모바일 조이스틱을 숨겨 잔류 이동을 막는다. 한글 조합 중 Enter는 전송하지 않는다.
- 화면 우측 상단의 닉네임 변경 버튼을 눌러 이름을 바꾼다. 클라이언트는 비어 있는지만 보고 길이·금지어 판정은 서버 `normalizeNickname` 에 맡긴다(8 grapheme, `#` 금지). 서버가 좌표까지 담은 `peer` 프레임을 모두에게 보내 확정하며, **10초에 한 번**만 바꿀 수 있다. 자주 바꾸면 다른 사람이 누가 누군지 못 따라간다. 확정된 이름은 채팅 위젯과 같은 저장소(`saveChatNickname`)에 넣는다.
- 이름 변경은 **연결을 끊지 않는다.** `useSpaceSession` 의 컨트롤러 의존성에 닉네임을 넣으면 바꿀 때마다 재접속해 좌석과 위치를 잃는다. 같은 이유로 이름만 바뀐 `peer` 프레임에는 위치를 되감지 않는다. 서버가 이동을 거절했을 때만 좌표가 실제로 달라지므로 양자화 오차(5 cm)로 가른다.
- `rid` 가 붙은 오류는 한 요청에 대한 답이라 연결을 끊지 않는다. 같은 코드라도 입장 때 오면(`rid` 없음) 영구 오류다. 닉네임 거절이 그 예로, 입장이면 재시도해도 소용없지만 이름 변경이면 입력만 고쳐 다시 보내면 된다. 단 `JOIN_REQUIRED` 는 좌석을 잃었다는 뜻이라 `rid` 가 있어도 다시 접속한다.
- 모바일 키보드가 뜨면 visual viewport에 맞춰 대화창 높이와 하단 위치를 조정한다. 스크롤로 예전 대화를 읽는 중에는 새 메시지로 강제 이동하지 않는다.

### 11.4.1 발차기

유저끼리 서로 찰 수 있다. 맞은 사람은 **살짝**(약 1 m) 밀리고 0.2 m 쯤 뜬다. 규칙 값은 `entities/space/model/kick.ts` 의 `SPACE_KICK` 하나에 모아 서버 판정과 클라이언트 연출이 같이 쓴다.

| 항목 | 값 | 이유 |
| --- | --- | --- |
| 조작 | 데스크톱 `F`, 손가락 기기는 점프 버튼 바로 왼쪽 발 버튼 | 누른 순간 한 번만 참. 누르고 있으면 쿨다운이 끝날 때마다 저절로 차서 |
| 대상 | 정면 ±60° 안, 몸 중심 사이 1.2 m 안, 높이 차 1.2 m 안에서 가장 가까운 사람. 없으면 허공에 참 | 다리 길이 약 0.9 m + 몸 반지름 약 0.3 m. 1.6 m·±78° 일 때 범위가 넓게 느껴졌음. `kickTarget.ts` |
| 쿨다운 | 찬 사람 2.5 초. 서버는 0.5 초 여유를 둬 2 초부터 받음 | 다구리를 허용해서 한 사람이 얼마나 자주 끼어드나를 정함. 5 초는 몰려 차도 듬성듬성 맞았고 2 초 아래는 괴롭힘에 가까움. 서버도 같은 값으로 보면 도착 지연이 달라 정상 발차기를 버림 |
| 다구리 | 맞는 쪽 무적 없음. 밀리는 중에 또 맞으면 넉백을 더하고 14 m/s(약 2 m)에서 자름 | 여럿이 몰려 차는 재미. 한 사람 연타는 찬 사람 쿨다운이 막음 |
| 서버 거리 | 2.8 m | 대상 거리 1.2 m 에 보간 지연 여유 1.6 m 를 더함. 클라이언트는 200~300 ms 늦게 보간한 위치로 고르고 서버는 최신 위치로 봐서 어긋남. |
| 넉백 | 초속 7 m, 지수 감쇠 7/s, 위로 2.5 m/s | 약 1 m. 밀리는 속도가 2.5 m/s 아래로 떨어질 때까지(약 0.15 초) 조작을 안 받음 |

- **넉백은 입력 속도와 따로 둔다**(`LocalPlayerState.knockbackX/Z`). 입력 속도는 25~30 m/s² 로 목표를 따라가서 거기에 넣으면 0.25 초 만에 멈춰 거의 안 밀린다. 벽에서는 입력 속도와 같은 규칙(법선 성분만 지움)으로 미끄러진다. 밀리는 방향으로 몸을 돌리지 않는다.
- **판정은 서버가 한다.** `kick` 요청을 받으면 쿨다운·거리를 보고, 통과하면 찬 사람에서 맞은 사람 쪽 단위 방향을 실어 알린다. 맞은 사람에게는 이동 예산을 2 m 더 얹는다. 밀리는 동안 순간 속도가 8.5 m/s 를 넘어도 순간이동으로 보고 되돌리지 않게 하려는 것이다. 거리 조건이 안 맞으면 허공 차기로 바꿔 알린다. 버리면 찬 사람 화면에만 발차기가 나가고 다른 사람은 아무것도 못 본다.
- **연출은 누른 순간 내 화면에서 바로 재생한다.** 서버 왕복을 기다리면 조작이 굼떠 보인다. 다른 사람의 발차기는 서버가 알린 순간부터 재생한다. 맞은 쪽 반응은 넉백으로 인한 위치 변화로 보인다.
- **맞은 사람은 발이 닿는 시점(`impactSeconds` 0.28 초)까지 기다렸다 밀린다.** 받자마자 밀면 상대 다리가 아직 뒤로 당겨져 있을 때 먼저 날아갔다. 다른 사람·찬 사람 화면에서는 맞은 사람 움직임이 보간 지연(약 0.2~0.3 초)만큼 늦게 보여 비슷하게 맞물린다.
- **기능 협상**: 클라이언트는 `join` 에 `features: ["kick"]`, 서버는 `welcome` 에 같은 목록을 싣는다. 서버는 아는 클라이언트에만 `kick` 프레임을 보내고, 클라이언트는 서버가 지원할 때만 요청을 보낸다. 옛 서버는 모르는 요청을 받으면 연결을 끊고, 옛 클라이언트는 모르는 프레임을 받으면 끊기 때문이다. 같은 이유로 클라이언트는 이제 **모르는 서버 프레임 종류를 끊지 않고 무시**한다(`t: "ignored"`).
- **동작은 걷기에서 자동으로 만든다.** 가공 스크립트가 각 모델의 Walk 에서 오른 허벅지가 가장 앞으로 간 프레임의 회전축(앞차기 축)과 무릎이 가장 굽은 프레임의 회전축을 뽑고, 그 축으로 정해진 각도(당김 −28°·무릎 75° → 차기 82°·무릎 4°)를 준다. 본 방향이 모델마다 달라도 축을 걷기에서 가져와 맞게 나온다. 팔은 걷기의 같은 시점 자세를 1.6배로 키운다. 16 프레임으로 구워 `<prefix>-kick.bin` 에 담고, 셰이더가 걷기 결과 위에 `aKickBlend` 로 섞는다. 첫·끝 프레임은 레스트라 걷다 차도 다리가 안 튄다.
- 이미 구운 모델은 `--kick-only` 로 발차기만 굽는다. 이때 Walk 도 메모리에서 다시 계산해 기존 `-walk.bin` 과 비교한다. 6개 모델 모두 차이 0.0 이라 좌표 변환이 기존 에셋과 정확히 같다. 맥시크루·숏베어·풀롱불 원본은 `7da1c2be^` 에서 되살렸다.

### 11.5 로컬 실행·배포와 남은 검증

로컬에서는 배포 없이 테스트할 수 있다. `pnpm chat:dev`가 `workers/chat/.dev.vars`의 빠진 개발 키 네 개와 localhost/127.0.0.1 Origin을 준비한 뒤 8787 포트에서 Worker를 실행한다. 기존 키는 덮어쓰지 않으며 파일은 Git에서 제외한다. 프런트의 `NEXT_PUBLIC_CHAT_API_URL=http://localhost:8787`, `NEXT_PUBLIC_CHAT_WS_URL=ws://localhost:8787/v1/chat/ws`를 적용해 `pnpm dev`를 실행한다. 일반 창과 시크릿 창에서 `http://localhost:3002/space`로 접속한다. Worker의 키 파일을 변경했다면 Worker도 재시작한다. 자세한 설정은 `workers/chat/README.md`를 따른다.

1. 기존 Worker 환경에서 `pnpm chat:typecheck`, `pnpm build:chat`로 확인한다.
2. 운영 반영 시 `pnpm chat:deploy`로 `SpaceRoom` 마이그레이션과 `/v1/space/ws`를 배포한다. 기존 secret과 Origin 설정을 재사용한다.
3. 프런트를 배포한 뒤 서로 다른 사용자 키를 가진 브라우저 두 개에서 입퇴장·이동·채팅을 확인한다. 같은 브라우저의 여러 탭은 한 사용자로 취급해 앞 탭이 종료된다.
4. 50석·네트워크 끊김/복귀·모바일 키보드/백그라운드·실제 FPS와 비용 지표를 확인한다. 현재 실행 환경에서는 실제 브라우저 렌더와 Cloudflare 배포 후 통합 검증이 남아 있다.

## 12. 3단계 사전 설계 — 라이트닝 광고

> 구현 계획은 [`btc-space-ads-lightning.md`](./btc-space-ads-lightning.md) 로 분리했다. 제공자는 **Blink 비수탁 계정**(`onlybtcapp@blink.sv`)으로 확정했고, 비수탁 계정에 API 키·웹훅이 없어 LNURL-pay + LUD-21 verify 폴링으로 설계했다. **1차 범위는 §6.6 텍스트 배너 1슬롯**이며, §7 의 이미지 패널 2장은 2차로 미뤘다. 아래는 1단계 당시의 사전 설계이고 상세·단가·범위는 분리한 문서를 따른다.

- 결제: 비트코인 라이트닝 인보이스 발행 → 결제 확인 → 광고 슬롯 예약. 제공자 선택과 콜백 검증은 분리한 계획서에서 다룬다.
- 입력: 사용자 이미지 업로드. 비율 3:2, 용량 상한, 심사 절차가 필요하다.
- 심사: 이미지가 최대 50명이 동시에 보는 공개 공간에 노출되므로 자동 통과는 두지 않는다. 기존 채팅 관리자 인증(`ADMIN_EMAIL_ALLOWLIST`, Google OAuth)을 재사용한 수동 승인 경로를 기본으로 본다.
- 만료: `expiresAt` 경과 시 플레이스홀더로 되돌린다.
- 좌석 50석은 광고 단가의 근거가 되므로, 동시 접속 상한을 바꿀 때 광고 가격 정책도 함께 재검토한다.

이 단계는 결제·업로드·심사·환불이 모두 얽혀 있어 1단계와 설계 결합을 만들지 않는다. 1단계에서는 §7 의 `AdSlot` 타입과 이미지 광고판 플레이스홀더, §6.6의 빈 텍스트 광고 배너만 둔다. 결제·예약·심사·링크·만료·환불 경로는 아직 없다.

## 13. 테스트 전략

- 순수 로직은 vitest 로 검증한다: 이동 적분·경계 클램프, 카메라 감쇠·피치 클램프, 스폰 산포의 결정성·링 범위, 거리순 컬링, 전광판 숫자 포맷·변동률 색.
- 핀치 입력은 순수 계산과 실제 포인터 이벤트 연결을 함께 검증한다. 두 손가락 평행 이동, 벌리기·모으기, 손가락 추가·해제·취소와 프레임당 1회 소비를 회귀 대상으로 둔다.
- 핀치 거리 변화는 프레임 단위로 계산한다. 정상 `pointerup` 이 다음 프레임보다 먼저 오면 마지막 미소비 줌을 보관해 한 번 적용하고, 같은 프레임에 새 핀치가 시작돼도 이어서 합산한다. `pointercancel`·캡처 상실·blur·연결 해제에서는 미소비 입력을 버린다.
- 점프 입력은 `resolveMergedMovementInput` 이 키보드·조이스틱 어느 채널의 `isJumping` 이든 그대로 넘기는지로 검증한다. 버튼의 포인터 처리와 안전 영역 배치는 브라우저에서 확인한다.
- 50명 렌더 비용은 `1-11` 의 더미 하니스로 수동 측정한다. 자동 성능 회귀 테스트는 두지 않는다.
- 3D 렌더 결과는 자동 검증하지 않는다. 사용자가 직접 브라우저에서 확인한다.
- 품질 게이트: `pnpm check`, `pnpm exec tsc --noEmit`, `pnpm test`, `pnpm check:cycles`.
