## 1. 개요

### 1.1 한 줄 정의

대한민국 랜드마크 아파트의 **실거래가를 비트코인 개수로 환산**해 시계열 차트로 보여주는 페이지.

### 1.2 사용자 시나리오

1. 사용자가 `/btc2apartment` 진입
2. 랜드마크 아파트 목록에서 단지 선택 (기본: 래미안원베일리)
3. 평형(전용면적) 선택 — 기본 84㎡
4. "지금 이 아파트를 사려면 **N BTC**" 헤드라인 확인
5. **년도별 막대 차트**로 추이 확인 — **BTC로 환산한 아파트 가격이 해가 갈수록 줄어드는 것**을 시각화
6. **BTC ↔ KRW 단위 토글**로 같은 아파트의 가격 추이를 두 화폐 기준으로 대조

### 1.3 이 페이지가 전달하는 메시지

법정화폐 기준으로는 아파트 가격이 계속 올랐지만, 비트코인 기준으로는 **지속적으로 하락**했다.
즉 비트코인의 구매력이 부동산 대비 우상향해 왔다는 것을 데이터로 보여준다.

#### 메시지 전달 장치 — BTC ↔ KRW 단위 토글

이 주장을 말로 설명하지 않고 **사용자가 직접 뒤집어 보게** 만든다.

| 단위 | 같은 아파트, 같은 기간 | 그래프 방향 |
| --- | --- | --- |
| **KRW** | 원화 실거래가 | 📈 우상향 — "아파트값이 올랐다" |
| **BTC** | 실거래가 ÷ 당시 BTC 시세 | 📉 우하향 — "비트코인으로는 싸졌다" |

**데이터는 하나도 바뀌지 않았는데 분모만 바꾸니 결론이 정반대가 된다.**
토글 전환 시 차트를 애니메이션으로 다시 그려서 이 반전을 체감하게 한다.
(ApexCharts는 `series` 갱신 시 자체 전환 애니메이션을 제공하므로 추가 구현 부담 없음)

> 부수 효과: KRW 모드는 BTC 시세 데이터가 필요 없다.
> BTC 일별 시세 조회가 실패하면 `medianPriceInBtc` 만 `null` 이 되고
> **KRW 차트는 정상 동작**하므로,
> BTC 시세 소스 장애가 페이지 전체를 죽이지 않는 안전판이 된다.

## 2. 사전 조사 결과 (실호출 검증 완료)

### 2.1 API 스펙 확인

```
GET https://apis.data.go.kr/1613000/RTMSDataSvcAptTrade/getRTMSDataSvcAptTrade
  ?serviceKey={인증키}
  &LAWD_CD=11650      # 법정동코드 앞 5자리 (시군구)
  &DEAL_YMD=202505    # 계약 년월 (YYYYMM)
  &pageNo=1
  &numOfRows=999
```

응답: XML (`<response><body><items><item>...`)

| 필드 | 설명 | 예시 |
| --- | --- | --- |
| `aptNm` | 단지명 | `래미안원베일리` |
| `umdNm` | 법정동 | `반포동` |
| `jibun` | 지번 | `1682` |
| `excluUseAr` | 전용면적(㎡) | `84.99` |
| `dealAmount` | 거래금액(만원, 콤마 포함) | `403,000` |
| `dealYear` / `dealMonth` / `dealDay` | 계약일 | `2025` / `5` / `31` |
| `floor` | 층 | `17` |
| `buildYear` | 건축년도 | `2003` |
| `sggCd` | 시군구코드 | `11650` |
| `dealingGbn` | 거래유형 | `중개거래` / `직거래` |
| `cdealType` | 해제여부 | `O` = 계약해제 |
| `totalCount` | 해당 월 전체 건수 | `175` |

### 2.2 ⚠️ 치명적 제약 — 조회 단위가 "시군구 + 1개월"

**단지명으로 조회하는 API가 아니다.** 래미안원베일리 하나를 보려면
서초구(11650) 전체를 월 단위로 긁어서 `aptNm`으로 필터링해야 한다.
2006-01 ~ 현재 = **단지 하나당 240회 이상 호출**.

> 뒤집어 말하면, 서초구 한 달치 응답 안에 반포자이·래미안퍼스티지·아크로리버파크·원베일리가
> **모두 들어있다**. 따라서 호출 비용은 `단지 수`가 아니라 **`(구 × 월)` 수에 비례**한다.
> → 캐시 유닛을 `(지역코드 × 월)`로 잡는 것이 설계의 핵심.

### 2.3 데이터 가용 범위

- **시작**: 2006-01 (정상 응답 확인)
- **최신**: 2026-03 (확인 시점)
- 최근 월은 신고 지연으로 데이터가 계속 추가됨 → 재검증 주기를 짧게 가져가야 함

### 2.4 ⚠️ 래미안원베일리는 막대가 4개뿐

직접 스캔 결과 **첫 매매 실거래가 2023-04**. (입주 2023-08, 그 이전은 분양권이라 별도 API 소관)

| 년월 | 202301 | 202304 | 202307 | 202308 | 202309 | 202310 | 202311 | 202312 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 거래건수 | 0 | 1 | 1 | 1 | 8 | 3 | 2 | 1 |

년도별이면 2023 / 2024 / 2025 / 2026 = **막대 4개**.

**→ 차트 타입을 막대로 잡아 해소한다.** 라인 차트에서 4점은 빈약해 보이지만,
막대 4개는 그 자체로 완결된 그래프다. 년도는 이산값이므로 의미상으로도 막대가 맞다.

원베일리 4개 구간의 BTC 환산값은 대략 `110 → 60 → 40 → 38 BTC` 로,
막대 4개만으로도 "BTC로는 3분의 1 값이 됐다"는 서사가 성립한다.

> 장기 이력 단지(은마·압구정현대·반포자이 등)를 함께 제공하면 막대가 13개까지 늘어
> 추세가 더 뚜렷해진다. 원베일리는 e2e 검증용, 서사의 완성은 랜드마크 확장에서.

### 2.5 BTC 원화 시세 히스토리 확보 방안

거래일 단위 환산(7.1)을 하려면 **일별** 원화 시세가 필요하다. 실제로 조회해 확인한 결과:

| 구간 | 소스 | 검증 결과 |
| --- | --- | --- |
| 2017-10 ~ 현재 | Upbit KRW-BTC 일봉 | ✅ 원화 직접. 프로젝트에 `upbit.ts` 기존 존재 |
| 2014-01 ~ 2017-09 | blockchain.com USD 일별 × 연평균 환율 상수표 | ✅ 아래 주의사항 참고 |
| 현재 시점 값 | 기존 실시간 `useBitcoinStore` | 헤드라인 "지금 N BTC"에만 사용 |

**⚠️ 확인된 함정 3가지**

| 소스 | 함정 |
| --- | --- |
| **Upbit** | **2017-10 이전 데이터가 없다.** 2017-06 조회 시 빈 응답, 2018-05 부터 정상 |
| **blockchain.com** | `timespan=all` 은 **4일 간격**으로만 내려온다 (17년치가 1,609건). 거래일 매칭에 못 씀 → **`timespan=1year&start=YYYY-01-01` 로 연 단위 요청해야 366건 일별**로 온다 ✅ |
| **Bithumb** | 최근 200건만 반환. 과거 이력 조회 불가 → **사용 불가** |

> 2014~2017 구간의 환율은 **연평균 상수**를 쓴다.
> 환율은 연중 ±5% 수준인데 같은 기간 BTC 변동은 수백 %라 오차 기여도가 무시할 수준이다.

### 2.6 차트 시작 연도를 2014년으로 고정

년도별 막대에서는 오래된 구간이 Y축을 통째로 잡아먹는다. 은마 84㎡ 기준 실제 스케일:

| 연도 | 아파트가 | BTC 시세 | **BTC 개수** |
| --- | --- | --- | --- |
| 2011 | ~8억 | ~1만원 | **80,000 BTC** |
| 2014 | ~9억 | ~50만원 | **1,800 BTC** |
| 2021 | ~26억 | ~6,000만원 | **43 BTC** |
| 2025 | ~30억 | ~1.4억 | **21 BTC** |

2011년을 포함하면 편차가 4,000배라 최근 15년이 바닥에 깔려 안 보인다.
2014년 시작이면 그보다 훨씬 낫지만, **선형 축으로 충분하다는 판단은 구현 후 실측에서 뒤집혔다** (13.1).

세 가지가 한 번에 해결된다.

| 효과 | 내용 |
| --- | --- |
| **가독성** | 극단적 편차 억제 ( 다만 로그 축 회피에는 실패 — 13.1 참고 ) |
| **데이터 신뢰도** | 국내 거래소(코빗 2013~) 이전 원화 시세는 신뢰 구간이 아님 |
| **호출량** | 수집 범위 21년 → **13년, 호출량 35% 절감** (구당 240회 → 156회) |

> KRW 모드는 2006년까지 표시해도 무리가 없지만, 두 단위의 X축 범위가 달라지면
> 토글 전환 시 축이 흔들려 비교가 어려워진다. **두 모드 모두 2014년 시작으로 통일.**

## 4. 아키텍처 — 런타임 프록시를 성립시키는 2단 캐시

### 4.1 캐시 유닛을 `(지역코드 × 월)`로 잡는다

공공 API 응답 자체의 단위와 캐시 단위를 일치시킨다.

```ts
// entities/apartment/api/aptTrade.server.ts
const DAYS_30 = 60 * 60 * 24 * 30;
const HOURS_6 = 60 * 60 * 6;

fetch(buildAptTradeUrl(lawdCode, dealYearMonth), {
  next: { revalidate: isSettledMonth(dealYearMonth) ? DAYS_30 : HOURS_6 },
});
```

- **마감된 과거 월**: 데이터가 불변 → 30일 재검증 (사실상 영구 캐시)
- **최근 3개월**: 신고 지연분 반영 → 6시간 재검증
- **같은 구의 다른 단지는 외부 호출 0회**
  서초구 캐시가 차면 반포자이·퍼스티지·아크로리버파크·원베일리가 전부 공짜

### 4.2 🔄 요청은 단지당 한 번 ( 연도 분할에서 뒤집힘 )

초안은 연도별로 라우트를 나눠 13개 요청을 병렬로 보내고, 도착하는 대로 막대를 채우는
점진 로딩이었다. 구현 후 뒤집었다 — **13.8 참고**.

```
GET /api/apartment/raemian-one-bailey   → 전 기간 한 번에
```

| | 값 |
| --- | --- |
| 콜드 ( 그 구 캐시 없음 ) | 약 **7초** (152개월 × 40ms 페이싱) |
| 웜 | **24~63ms** |
| 응답 크기 | **3.5~12.9KB** |

콜드는 구당 한 번뿐이고, 같은 구의 다른 단지는 전부 웜이다.

### 4.2.1 캐시 계층 ( 클라이언트 · 엣지 · 서버 )

연 단위 집계라 하루는 묵어도 값이 달라지지 않는다. 세 층 모두 **24시간**으로 맞춘다.

| 층 | 수단 | 주기 |
| --- | --- | --- |
| 클라이언트 메모리 | TanStack `staleTime` | 24시간 |
| 클라이언트 영속 | `gcTime` + `PersistQueryClientProvider` ( localStorage ) | 24시간 |
| 엣지 · CDN | `Cache-Control: public, s-maxage=86400, stale-while-revalidate=86400` | 24시간 |
| 서버 데이터 | `unstable_cache` (지역코드 × 월) | 확정 월 30일 / 최근 3개월 6시간 |
| 확정 과거 연도 | `archive.json` ( 리포에 커밋 ) | 영구 — 스크립트 재실행 시에만 갱신 |

- `gcTime` 은 `PersistQueryClientProvider` 의 기본 `maxAge`( 24시간 )와 **같은 값**으로 맞춘다.
  `gcTime` 이 더 짧으면 localStorage 에서 복원한 데이터가 예상보다 빨리 정리된다.
- `stale-while-revalidate` 덕분에 만료 직후 요청도 기존 값을 즉시 받고 갱신은 뒤에서 돈다.

**⚠️ 불완전한 응답은 어느 층에서도 캐시하지 않는다**

| 층 | 처리 |
| --- | --- |
| 엣지 | `isIncomplete` 이면 `Cache-Control: no-store` |
| 클라이언트 | `isIncomplete` 이면 `staleTime: 0` + `refetchOnMount: true` |
| 서버 | 실패한 달은 `unstable_cache` 에 보관되지 않음 ( 13.3 ) |

세 층 중 하나라도 빠지면 초당 제한으로 생긴 빈 달이 그 층에 눌러앉는다.
오류 응답( 404 · 500 )도 `no-store` 다.

> 엣지 캐시가 24시간이므로 최근 3개월의 서버 캐시 6시간 주기는 그만큼 자주 노출되지 않는다.
> 신규 신고분이 화면에 반영되기까지 최대 하루가 걸린다는 뜻인데,
> 연 중앙값은 몇 건으로 움직이지 않으므로 감수한다.

### 4.4 보안

- `apartmentId`는 `landmarks.ts` **화이트리스트에서만** 해석한다

### 6.0 BTC 환산은 서버에서 수행한다

> ⚠️ **이 항목은 7.1 의 거래일 매칭 방식을 채택하면서 뒤집힌 결정이다.**
> 이전 초안은 "라우트는 KRW 만 내려주고 클라이언트가 BTC 로 나눈다" 였다.
> 거래일 단위 환산은 **개별 거래 목록**이 있어야 가능한데, 그걸 클라이언트로 내리면
> 연도당 수십~수백 건의 원시 거래가 페이로드에 실린다. 집계의 의미가 사라진다.

| | 결정 |
| --- | --- |
| **환산 위치** | 서버 ( 라우트 핸들러 ) |
| **응답** | `medianPriceInKrw` 와 `medianPriceInBtc` 를 **둘 다** 내려줌 |
| **클라이언트** | 계산 없음. 토글에 따라 필드만 골라 씀 |

이렇게 해도 원래 노리던 이점은 그대로 유지된다.

- **토글 전환 시 재요청 없음** — 두 값이 한 응답에 함께 들어있으므로
- **BTC 시세 장애 안전판** — 시세 조회가 실패하면 `medianPriceInBtc: null` 로 내려가고
  **KRW 모드는 정상 동작**한다 (1.3 의 부수 효과 유지)
- **캐시 친화적** — 과거 연도는 아파트 실거래도 BTC 시세도 모두 불변이라
  환산 결과 역시 불변이다. 오히려 서버 캐시 적중률이 올라간다

### 6.1 진행 중인 연도 처리

당해 연도는 아직 12개월이 다 차지 않았다. 월별 차트에서는 자연스러웠지만
**막대 하나로 뭉뚱그리는 년도별에서는 오해를 부른다.**
(2026년 막대가 낮으면 "값이 떨어졌나?" 로 읽힘 — 실제로는 8월까지의 데이터일 뿐)

| 처리 | 내용 |
| --- | --- |
| 데이터 | `isPartialYear: true` 로 표시해 내려보냄 |
| 시각 | 마지막 막대를 **반투명 + 점선 테두리** 로 렌더 |
| 라벨 | X축에 `2026 (8월까지)` 로 표기 |
| 툴팁 | `진행 중 · 8월까지 집계` 문구 노출 |

신고 지연(계약 후 최대 30일)까지 감안하면 최근 1~2개월은 계속 채워지므로,
서버가 판단한 **집계 완료 월**을 응답에 함께 내려준다.

## 7. 집계 규칙

| 항목 | 규칙 | 이유 |
| --- | --- | --- |
| **평형 버킷** | `Math.floor(excluUseAr)` 로 정수 ㎡ 그룹핑 (84.38 / 84.99 → `84`) | 7.5 참고 — `round` 는 국민평형을 84/85 로 쪼갠다 |
| **기본 평형** | 84 버킷이 **전체 거래의 10% 이상**이면 84, 아니면 거래 최다 버킷 | 10.2 참고 — 단순히 "84 있으면 84" 로는 타워팰리스가 깨진다 |
| **대표값** | 해당 **연도** 거래 전체의 **중앙값(median)** | 7.4 참고 — 평균은 증여성 저가·직거래 이상치에 흔들림 |
| **거래 0건 연도** | `null` 로 내려 막대를 그리지 않음 | 0으로 찍으면 "그 해에 공짜였다"로 읽힘 |
| **계약해제 건** | `cdealType === 'O'` 인 거래 **제외** | 실제 성사되지 않은 거래 |
| **직거래** | 포함하되 중앙값이 이상치를 흡수 | 7.4 참고 — 별도 필터는 과설계 |
| **금액 파싱** | `dealAmount` 콤마 제거 후 `× 10,000` (만원 → 원) | |
| **BTC 개수** | `medianPriceInKrw / btcPriceInKrw` | 소수 2자리 표기 |

### 7.1 단위별 값 산출 · 표기

**환산 해상도와 집계 해상도를 분리한다.** 이게 이 페이지 정확도의 핵심이다.

| | 해상도 | 이유 |
| --- | --- | --- |
| **환산** (BTC 개수 계산) | **거래일 단위** | 가장 정밀하게 |
| **집계** (차트 막대) | **연 단위** | 가장 안정적으로 |

```
거래 32건 → 각 거래일 BTC 시세로 나눔 → BTC 개수 32개 → 연 중앙값 1개 → 막대 1개
         └─ 일 단위 정밀도 ─┘              └─ 연 단위 안정성 ─┘
```

| 단위 | 계산식 | 표기 예 |
| --- | --- | --- |
| **BTC** | `median( 거래가_i ÷ btcPriceOn( 거래일_i ) )` | `40.44 BTC` |
| **KRW** | `median( 거래가_i )` | `58.3억` |

- 두 단위 모두 **중앙값을 마지막에 취한다.** BTC 개수를 먼저 구하고 나서 중앙값을 내는 것이지,
  KRW 중앙값을 구한 뒤 대표 시세 하나로 나누는 게 아니다 (7.2 실측 참고)
- 현재 시세로 과거를 나누면 절대 안 된다
  (그러면 KRW 그래프와 모양이 똑같아져서 페이지의 존재 이유가 사라짐)
- 헤드라인 "지금 사려면 N BTC" **만** 실시간 시세(`useBitcoinStore`)를 쓴다
- 거래일의 BTC 시세를 못 구하면 그 거래만 BTC 집계에서 제외 (KRW 집계에는 그대로 포함)

### 7.2 근거 — 거래일 매칭이어야 하는 이유 (실측)

`D = 거래별 당일 시세 매칭 후 중앙값`을 기준으로 다른 방식들의 오차:

| 방식 | 원베일리 2024 | 은마 2021 | 은마 2018 |
| --- | --- | --- | --- |
| A. 연평균 시세로 나눔 | −3.5% | **−15.3%** | −6.1% |
| B. 연중앙값 시세로 나눔 | −1.8% | **−16.1%** | +7.5% |
| C. 연말 종가로 나눔 | **−35.8%** | −15.5% | **+95.5%** |
| **D. 거래별 당일 매칭** | 기준 | 기준 | 기준 |

**은마 2021 — 거래 쏠림이 연평균을 무너뜨린다.**
거래 27건 중 26건이 1~8월에 몰렸는데 BTC는 10~11월에 8,100만원 고점을 찍었다.
연평균에는 그 고점이 섞이지만 **실제 거래는 BTC가 쌌던 시기에 일어났다** → 15% 과소평가.

**은마 2018 — 연말 종가는 실격.**
BTC 폭락 직후인 12월 31일 하루가 그 해 전체를 대표해버려 **+95.5%** 오차.
2018년 BTC 연중 변동폭이 7.58배였던 것을 감안하면 당연한 결과다.

> 참고: 2025년처럼 BTC가 횡보한 해(변동 1.34배)는 A·B·D가 1% 내로 수렴한다.
> 즉 D는 평상시엔 손해가 없고, 변동성이 큰 해에만 이득을 본다. 쓰지 않을 이유가 없다.

### 7.3 월별 차트로 돌아갈 필요는 없다

"거래일 시세로 환산"과 "월별로 차트를 그린다"는 별개다.
D 방식은 **월별보다 더 정밀하다** — 월 평균이 아니라 거래 건별 날짜를 쓰기 때문이다.

월별 집계로 되돌리면 환산 정밀도는 그대로인데 10.1의 표본 문제(4개월 공백, 표본 1건)만 재발한다.
**환산만 일 단위로 올리고 집계는 연 단위로 두면 손해 없이 정확도만 얻는다.**

### 7.4 근거 — 평균이 아니라 중앙값인 이유 (실측)

**평상시에는 둘이 거의 같다.**

| 대상 | 건수 | 평균 | 중앙값 | 괴리 |
| --- | --- | --- | --- | --- |
| 원베일리 84㎡ 2025 | 32건 | 58.99억 | 58.25억 | 1.3% |
| 은마 84㎡ 2024 | 26건 | 27.33억 | 27.07억 | 0.9% |

**문제는 직거래다.** 서초구 2024년 전체 3,105건 중 직거래는 91건(2.9%).
같은 단지·같은 평형의 중개거래 중앙값과 비교하면:

| 벗어난 정도 | 직거래 | 중개거래 중앙값 | 단지 |
| --- | --- | --- | --- |
| **−46.9%** | 14.6억 | 27.5억 | 신반포2 69㎡ |
| **−40.8%** | 6.5억 | 11.0억 | 코오롱 52㎡ |
| **−36.3%** | 25.5억 | 40.0억 | 신반포4 137㎡ |
| **−32.1%** | 9.8억 | 14.5억 | 서초힐스 85㎡ |
| **−30.5%** | 21.0억 | 30.2억 | 래미안 리더스원 85㎡ |

전부 **한 방향(아래)으로만** 쏠려 있다. 가족 간 증여성 거래로 추정되며 **시세가 아니다.**

- 거래 30건인 해에는 직거래 1건이 평균을 약 1% 끌어내린다 (위 표의 1.3% 괴리 정체)
- 그러나 **거래 6건인 해에 −40% 직거래 1건이 끼면 평균이 7% 왜곡**된다
  원베일리 2023년(17건), 아크로리버파크 초기처럼 표본이 얇은 해가 실제로 존재
- 중앙값은 그 1건이 순위 맨 아래로 밀릴 뿐 **값 자체가 흔들리지 않는다**

> 직거래를 아예 제외하는 안도 검토했으나 채택하지 않았다.
> 정상적인 직거래까지 날아가는데, 중앙값이 이미 같은 방어를 비용 없이 해내기 때문이다.

### 7.5 🐛 평형 버킷은 `floor` — `round` 는 국민평형을 쪼갠다

초안의 `Math.round` 는 버그다. 실측으로 확인했다.

4개 구 2년치 표본에서 83~86㎡ 구간 전용면적 분포:

| 실제 전용면적 | 건수 |
| --- | --- |
| 84.00 ~ 84.99 | **5,312건** |
| 85.00 이상 | 36건 |

국민평형의 실제 전용면적은 **84.xx 가 압도적**인데,
`Math.round` 는 84.50 을 경계로 84 와 85 로 갈라버린다.

**마포래미안푸르지오가 정확히 깨지는 사례:**

| 전용면적 | 건수 | `round` | `floor` |
| --- | --- | --- | --- |
| 84.3884 | 14건 | `84` | `84` |
| 84.5978 | 61건 | **`85`** | `84` |
| 84.8919 | 40건 | **`85`** | `84` |
| 84.9603 | 2건 | **`85`** | `84` |

같은 국민평형 117건이 두 버킷으로 쪼개져 **평형 칩이 `84㎡` 와 `85㎡` 두 개로 뜨고,
각 버킷의 표본이 반토막 난다.** `Math.floor` 는 전부 `84` 로 모인다.

> 원베일리·아크로리버파크·헬리오시티는 84.9x 대라 `round` 시 전량 `85` 로 뜬다.
> 은마만 84.43 이라 `84` 로 떠서, **단지마다 칩 라벨이 84/85 로 뒤죽박죽이 된다.**

**에러**: 화이트리스트에 없는 `apartmentId` → `404`

### 8.2 BTC 일별 시세는 내부 모듈로 (라우트 아님)

거래일 매칭이 서버에서 일어나므로 BTC 시세를 클라이언트에 노출할 이유가 없어졌다.
**공개 라우트를 만들지 않고 서버 내부 모듈로 둔다.**

```
src/entities/bitcoin/api/btcDailyKrw.server.ts
  getBtcDailyKrwMap( year ) → Map<'YYYY-MM-DD', number>
```

| 항목 | 내용 |
| --- | --- |
| 캐시 단위 | **연도 1개** (`fetch` 의 `next.revalidate`) |
| 과거 연도 | 30일 재검증 — 시세가 확정되어 불변 |
| 당해 연도 | 6시간 재검증 |
| 소스 분기 | `year >= 2018` → Upbit / 그 이전 → blockchain.com × 연평균 환율 (2.5) |

> 2017년은 10월을 경계로 소스가 갈리므로 **두 소스를 병합**한다.
> 경계 처리를 피하려면 2017년만 blockchain.com 으로 통일하는 것도 방법 — 구현 시 결정.

### 10.0 검증에서 드러난 3가지 함정

**① 압구정 현대는 `압구정현대` 라는 단지가 존재하지 않는다**

압구정동은 **25개 단지로 파편화**되어 있다 (현대1~14차 / 신현대9~12차 / 한양1~8 / 미성1~2차).
차수별 중앙값이 **43억 ~ 80억**으로 벌어져 통합하면 값이 왜곡된다.
→ 압구정동에서 두 번째로 거래가 많고(33건) 상징성이 큰 **`현대6차` 단독 채택**.
84㎡가 없으므로 7장의 "84 없으면 거래 최다 평형" 규칙이 적용되어 **144㎡가 기본값**이 된다.

**② 한 단지가 여러 `aptNm` 으로 쪼개져 있는 경우가 있다**

| 단지 | 실제 표기 | 처리 |
| --- | --- | --- |
| 마포래미안푸르지오 | `~1단지` `~2단지` `~3단지` `~4단지` | 지번이 모두 `아현동 777` 로 동일한 하나의 단지 → **4개를 통합** |
| 타워팰리스 | `타워팰리스1` `타워팰리스2` `타워팰리스3` | 별개 단지이고 **84㎡는 1차에만 존재** → **1차만 채택** |

**③ 부분일치로 매칭하면 엉뚱한 단지가 섞인다**

| 의도 | 부분일치 시 함께 걸리는 단지 |
| --- | --- |
| `아크로리버파크` | `아크로리버뷰신반포`(잠원동) · `방배아크로리버`(방배동) |
| `반포자이` | `신반포자이`(잠원동) |

### 10.1 근거 — 월별을 버린 이유 (실측)

래미안원베일리 84㎡ 2025년 실거래를 월별로 쪼개본 결과:

| 월 | 01 | 02 | 03 | 04 | 05 | 06 | 07 | 08 | 09 | 10 | 11 | 12 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 건수 | 2 | 10 | 7 | **0** | **0** | 8 | **1** | **1** | **0** | 2 | **1** | **0** |
| 중앙값(억) | 55.9 | 53.0 | 57.5 | — | — | 63.7 | 60.0 | **71.5** | — | 62.1 | 60.0 | — |

- **12개월 중 4개월이 거래 0건**, 3개월은 표본이 1건뿐
- 7월 60.0억 → 8월 **71.5억 (+19%)** → 10월 62.1억 (−13%)
  시장이 움직인 게 아니라 **8월에 우연히 고층 1건이 팔린 것**. 표본 1건 중앙값은 통계가 아니라 우연
- 같은 데이터를 연 단위로 합치면 **32건 → 중앙값 약 57~58억**으로 안정

**BTC 모드에서는 이 노이즈에 BTC 변동성이 곱해진다.**
`아파트 노이즈 × BTC 노이즈` 라 톱니가 두 배로 심해지고,
정작 보여주려던 우하향 추세가 톱니에 파묻힌다.

> 아파트 실거래는 주식 시세와 다르다. 한 단지 한 평형은 월 0~2건 거래되므로
> **연 단위가 이 데이터의 자연스러운 최소 해상도다.**

### 10.2 🐛 "84 있으면 84" 규칙은 타워팰리스에서 깨진다

초안 규칙은 *84 버킷이 존재하면 무조건 기본값* 이었다. 실측하니 타워팰리스1이 무너진다.

| 단지 | 84 버킷 표본 | 전체 표본 | 비중 |
| --- | --- | --- | --- |
| 헬리오시티 | 205건 | 366건 | 56% |
| 마포래미안푸르지오 | 117건 | 254건 | 46% |
| 은마 | 29건 | 71건 | 41% |
| 래미안원베일리 | 24건 | 68건 | 35% |
| **타워팰리스1** | **1건** | 26건 | **3.8%** |

타워팰리스1은 대형 위주 단지라 84㎡가 사실상 없다.
84를 기본값으로 잡으면 **13개 연도 중 대부분이 거래 0건이 되어 막대가 거의 안 그려진다.**

**보완 규칙**: `84 버킷 비중 >= 10%` 일 때만 84 를 기본값으로 쓰고, 아니면 거래 최다 버킷.

| 단지 | 판정 | 기본 평형 |
| --- | --- | --- |
| 타워팰리스1 | 3.8% < 10% | **164㎡** (최다 7건) |
| 현대6차 | 84 버킷 자체가 없음 | **144㎡** (최다 20건) |
| 나머지 9개 | 35~56% | **84㎡** |

> 84㎡ 가 없거나 희소한 단지(현대6차·타워팰리스1)는 어차피 대형 랜드마크다.
> 기본값이 대형 평형인 것이 그 단지의 성격에도 맞다.

> **타워팰리스1 은 이후 목록에서 제외했다.** 규칙( `DEFAULT_AREA_MIN_DEAL_RATIO` )은 그대로 살아 있고,
> 지금은 아크로서울포레스트·현대6차가 같은 경로를 탄다.

### 13.1 🔄 "2014년 시작이면 선형 축으로 읽힌다" — 틀렸다

2.6 에서 은마 84㎡ 추정치로 편차를 90배로 계산하고 선형 축을 확정했다.
구현 후 실제 렌더링에서 뒤집혔다.

| 단지 | 구간 | 실제 편차 |
| --- | --- | --- |
| 잠실엘스 84㎡ | 2015년 약 3,400 BTC → 2026년 21 BTC | **약 160배** |

선형 축에서는 2014~2016 세 막대가 Y축을 독점하고 **2018년 이후가 전부 바닥에 붙어**
"계속 싸졌다" 는 추세 자체가 보이지 않았다. 페이지의 존재 이유가 사라지는 수준이다.

**확정**: `shouldUseLogScale` — 값 범위가 **50배 이상**이면 로그 축.

| 모드 | 축 | 근거 |
| --- | --- | --- |
| BTC · 장기 이력 단지 | **로그** | 잠실엘스 160배, 원베일리는 2.4배라 선형 유지 |
| KRW | **선형** | 8.8억 → 33억 = 3.7배. 로그가 불필요 |

로그 막대의 밑동이 0 이 아니라는 단점은 남지만, 읽히지 않는 차트보다는 낫다.
데이터 범위로 판단하므로 신축 단지는 그대로 선형이다.

### 13.2 🔄 일일 한도만 봤고 **초당 제한**을 놓쳤다

4.3 은 일일 10,000회만 계산했다. 실제로는 **초당 요청 제한**이 따로 있다.

```
LIMITED_NUMBER_OF_SERVICE_REQUESTS_PER_SECOND_EXCEEDS_ERROR (코드 23)
```

장기 이력 단지를 선택하면 클라이언트가 **13개 연도를 동시에** 요청하고,
각 라우트가 동시성 8로 월별 호출을 뿌려 **순간 100회 이상**이 나간다. 그대로 막힌다.

**확정**: 요청당 동시성 제한만으로는 부족하다. **프로세스 전역 발사 간격 제한**을 둔다.
( `scheduleRateLimited`, 최소 70ms 간격 ≈ 14 req/s )

### 13.3 🔄 실패를 빈 배열로 흡수하면 안 된다

이 API 는 초당 제한 초과를 **`HTTP 200` + 에러 XML 본문**으로 돌려준다.
Next 의 `fetch` 캐시는 본문을 보지 않으므로 **에러를 정상 응답으로 캐시**한다.
프로덕션에서 일시적 제한 한 번이 그 달을 30일 동안 "거래 없음" 으로 굳힐 수 있다.

**확정**
- `cache: "no-store"` 로 받아 Next 가 원본 응답을 캐시하지 못하게 한다
- 캐싱은 **성공했을 때만 값을 보관하는** `unstable_cache` 에 맡긴다
- 실패한 달은 캐시를 오염시키지 않고 다음 요청에서 재시도된다
- 일부 월이 빠지면 숨기지 않고 `isIncomplete` 로 응답에 드러낸다

### 13.4 🔄 불완전한 응답이 localStorage 에 굳는다

이 앱은 쿼리 캐시를 localStorage 에 영속화하고 `refetchOnMount` 가 전역으로 꺼져 있다.
서버를 고쳐도, 한 번 들어온 불완전한 응답이 **최대 12시간 동안 화면에 남는다.**

**확정**: `staleTime` 을 함수로 주어 `isIncomplete` 인 결과는 항상 stale 로 취급하고,
이 쿼리만 `refetchOnMount: true` 로 되돌린다.

### 13.5 🔄 서비스 키를 이중 인코딩했다

공공데이터포털은 키를 **인코딩 / 디코딩 두 형태**로 발급한다.
인코딩된 키(`%2B`, `%3D%3D`)를 `encodeURIComponent` 하면 `%` 가 `%25` 가 되어 인증이 깨진다.
( 첫 실호출이 조용히 빈 결과를 반환했다 )

**확정**: `normalizeServiceKey` — 한 번 디코딩해 원본으로 되돌린 뒤 다시 인코딩한다.
어느 형태로 넣어도 동작하고, 여러 번 적용해도 값이 변하지 않는다.

### 13.6 🔄 기본 평형을 연도별로 계산하면 흔들린다

"84 비중 10% 이상이면 84" 규칙을 연도마다 적용했더니 타워팰리스1 이
**2021→164, 2022→84, 2024→164** 로 오갔다. 연도별 응답을 합치는 구조에서
기본 평형이 연도마다 다르면 클라이언트가 어느 값을 쓸지 알 수 없다.

**확정**: 기본 평형은 단지 고유 속성이므로 `landmarks.ts` 에 고정한다.

### 13.7 ✅ 뒤집히지 않은 판단

실측으로 오히려 강화된 것들.

| 판단 | 검증 |
| --- | --- |
| `(지역코드 × 월)` 캐시 유닛 | 서초구 단지 2번째부터 61~68ms (warm) vs 강남구 첫 조회 261ms |
| 년도별 막대 | 원베일리 4개 막대로도 서사 성립 |
| 중앙값 | 직거래가 −25~−47% 로 한 방향 쏠림 |
| 거래일 단위 BTC 환산 | 라우트 실측 40.37 BTC = 독립 계산 40.44 BTC |
| 화이트리스트 | 알 수 없는 식별자 404, 잘못된 연도 400 |

### 13.8 🔄 연도별 점진 로딩 → 단일 요청

4.2 의 초안은 13개 연도를 13개 요청으로 나눠 병렬 조회하고 막대를 하나씩 채우는 것이었다.
콜드 스타트에서 1~2초 만에 첫 막대가 보인다는 장점이 있었지만, 두 가지가 걸렸다.

**① 전역 rate limiter 가 서버리스에서 무력화된다**

13.2 에서 넣은 `scheduleRateLimited` 는 **프로세스 전역** 변수로 발사 간격을 잡는다.
그런데 요청을 13개로 나누면 서버리스에서 인스턴스가 분리될 수 있어,
각 요청이 서로의 발사 시각을 모른 채 자기 페이스로 쏜다. 페이싱이 사실상 사라진다.
**한 요청 안에서 전체 월을 하나의 큐로 흘려보내야 제한이 실제로 동작한다.**

**② 라우트 호출이 13배**

공공 API 호출 수는 (구 × 월) 이라 어느 쪽이든 152회로 같다.
줄어드는 것은 우리 라우트 호출이다 — 서버리스 인스턴스 기동 13회 → 1회.

**실측 트레이드오프**

| | 연도 분할 (초안) | 단일 요청 (확정) |
| --- | --- | --- |
| 콜드 첫 화면 | 1~2초 (부분 렌더) | **약 7초** (전체 대기) |
| 웜 | 약 200ms | **24~63ms** |
| 라우트 호출 | 13회 | **1회** |
| rate limiter | 인스턴스마다 분리 → 무력 | **정상 동작** |

콜드 7초는 **구당 한 번뿐**이다. 서초구를 한 번 채우면 그 구 단지 4개가 모두 웜이 된다.
페이싱 신뢰성과 웜 응답 속도를 얻는 대가로 받아들인다.

**발사 간격 실측** ( 152개월 연속 발사, 마포구 )

| 간격 | 소요 | 실효 속도 | 초당 제한 |
| --- | --- | --- | --- |
| 70ms | 12.3초 | 12.4 req/s | 0건 |
| **40ms** | **6.9초** | **22.0 req/s** | **0건** |
| 25ms | 4.4초 | 34.4 req/s | 0건 |

25ms 도 통과했지만 서버리스에서 인스턴스가 N개면 합산이 N배가 된다.
안전 마진을 두고 **40ms** 로 확정.

## 14. 아카이브 ( 확정 연도 사전 수집 )

### 14.1 배경

런타임 프록시만으로는 콜드 스타트에 구당 152회를 태워야 했다.
과거 확정 연도는 **실거래도 BTC 시세도 변하지 않으므로** 매번 받을 이유가 없다.

| | 아카이브 이전 | 이후 |
| --- | --- | --- |
| 구당 콜드 조회 | 152개월 → 152회 | **8개월 → 8회** ( 약 95% 감소 ) |
| 콜드 응답 | 약 7초 | **0.3초** |
| 웜 응답 | 24~63ms | **10~30ms** |
| 아카이브 크기 | — | **90.5KB** ( gzip 약 12KB ) |

### 14.2 구성

```
scripts/build-apartment-archive.ts          # 수동 실행 ( pnpm build:apartment-archive )
scripts/ts-loader.mjs                       # 확장자 없는 상대 import 해석 훅
scripts/ts-extension-hook.mjs
src/entities/apartment/model/archive.json   # 생성물, 커밋 대상
src/entities/apartment/lib/archive.ts       # 읽기 + 런타임 시작 연도 계산
```

스크립트는 **앱과 같은 집계 모듈을 그대로 import** 한다 ( Node 24 의 타입 스트리핑 ).
로직을 복제하지 않으므로 아카이브와 런타임 결과가 어긋날 수 없다.

### 14.3 낡아도 깨지지 않는다

```
런타임 조회 범위 = ( 아카이브의 마지막 연도 + 1 ) ~ 현재
```

`archive.json` 갱신을 잊어도 빈 구간이 실시간으로 메꿔진다. 호출량만 늘어난다.
연도가 겹치면 **런타임 쪽이 아카이브를 덮는다** — 아카이브가 낡았을 수 있기 때문이다.

### 14.4 신고 지연 경계

부동산 거래는 계약 후 30일 이내 신고라 12월 계약이 다음 해 1월 말까지 들어온다.
스크립트가 1~2월에 실행되면 직전 연도가 아직 확정되지 않았으므로 한 해 더 물러선다.
( `SETTLED_PREVIOUS_YEAR_FROM_MONTH = 3` )

### 14.5 다시 돌려야 할 때

- 해가 바뀌고 **2월이 지난 뒤**
- 랜드마크를 추가했을 때
- 집계 로직을 바꿨을 때

### 13.9 🔄 BTC 시세 실패도 삼키고 있었다 ( 아카이브가 47% 오염됨 )

13.3 에서 아파트 API 의 "실패를 빈 배열로 흡수" 를 고쳤지만,
**BTC 시세 경로에는 같은 패턴을 그대로 남겨 뒀다.**

```ts
if (!response.ok) { continue; }   // ← 실패를 건너뛰고 부분적으로 채워진 Map 을 반환
```

첫 아카이브 생성 때 스크립트가 12개 연도 × 2회 = **24개 Upbit 요청을 `Promise.all` 로
동시 발사**해 초당 제한에 걸렸고, 그 실패가 조용히 버려졌다.

| 증상 | 값 |
| --- | --- |
| 시세 결측 버킷 | **622개 중 290개 (47%)** |
| 원베일리 2023년 84㎡ | 거래 10건 중 **2건만** 환산 |
| 그 결과 | 96.8 BTC → **87.1 BTC** ( 표본 2건짜리 중앙값 ) |

빈 배열보다 나쁘다. **부분적으로 채워진 Map 은 "조용히 틀린 중앙값" 을 만든다.**
차트는 멀쩡해 보이는데 값만 잘못된다.

**확정**

| 조치 | 내용 |
| --- | --- |
| 실패 처리 | `continue` → **던진다** ( 재시도 3회 + 지수 백오프 ) |
| 커버리지 검증 | 그 해 기대 일수의 **95% 미만이면 던진다** |
| 캐시 | `lib/btcDailyKrw` ( 순수 ) + `api/btcDailyKrw.server` ( `unstable_cache` ) 로 분리 |
| 스크립트 | Upbit 를 **순차** 조회 + 호출 간 250ms 간격 |
| 생성 게이트 | `btcConvertedDealCount !== dealCount` 인 버킷이 하나라도 있으면 **저장하지 않고 종료** |
| 회귀 방지 | `btcDailyKrw.test.ts` 6종 — 부분 실패·커버리지 부족을 테스트로 잠금 |

> 교훈: 같은 종류의 버그를 한 경로에서 고쳤다면 **다른 경로도 함께 훑어야 한다.**
> 아파트 API 는 고쳤는데 BTC API 는 놓쳤고, 그 사이 아카이브가 오염된 채 생성됐다.
> 생성물에 대한 검증 게이트가 없었다면 커밋되어 영구히 박혔을 것이다.
